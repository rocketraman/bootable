= Wiring Bootable

Bootable's core embeds no dependency-injection framework. Its runtime, `Bootable`, takes two sets — your
application services and your lifecycle controllers — and runs them:

[source,kotlin]
----
class Bootable(
  appServices: Set<AppService>,
  lifecycleControllers: Set<LifecycleController> = defaultLifecycleControllers(),
  startOrder: StartOrder = DefaultStartOrder,
  tiebreaker: StartOrder.Tiebreaker = StartOrder.Tiebreaker.ByName,
)
----

*How you assemble those two sets is entirely your choice.* This document covers the three wiring styles Bootable
documents and ships helpers for — plain Kotlin, Kodein-DI, and Metro — but nothing stops you using any other
mechanism (a service loader, Guice, Koin, …) or none at all. There is one runnable example project per style
under `examples/` (`wiring-vanilla`, `wiring-kodein`, `wiring-metro`); copy the one that matches your choice.
Experimental helpers for a fourth, Inara, are described in <<inara-experimental>>, with its example in `wiring-inara`.

The entry point is the same in every style:

[source,kotlin]
----
fun main() = boot { /* return the Bootable to run */ }
----

`boot` initializes logging first, then runs the lambda, so config loading and component construction happen with
logging already set up. `Bootable`'s `lifecycleControllers` argument defaults to `defaultLifecycleControllers()`
— the built-in start/stop and signal-handling controllers — so you pass it only to run a custom lifecycle (e.g.
starting/stopping services on command from an RPC or web request rather than at boot).

`startOrder` and `tiebreaker` decide the order the services start in (see link:service-ordering.adoc[Service
ordering]), and are optional too. With Kodein, `bootableModule` uses a `StartOrder` or `StartOrder.Tiebreaker`
binding if there is one; with Metro, `BootableDefaultBindings` does the same, as optional bindings. Without a
`StartOrder.Tiebreaker` binding, both read it from the `boot.service.order` config section (`ServiceOrderConfig`) if
there is a `ConfigBinder`; with vanilla wiring, pass `tiebreaker = serviceOrderConfig(binder).tiebreaker`.

== Choosing a wiring style

[cols="1,3", options="header"]
|===
| Style | When it fits

| *Vanilla* (no DI)
| Small or single-module apps, or anyone who dislikes DI frameworks. You list your services explicitly. No extra
  dependencies, no annotations, no compiler plugin; works on any Kotlin version Bootable supports.

| *Kodein-DI* (runtime)
| You want multibinding aggregation across modules without a compiler plugin. Kodein is an ordinary jar; wiring
  is runtime code.

| *Metro* (compile-time)
| You want the wiring validated by the compiler (missing/duplicate bindings are build errors) with no runtime
  reflection. Metro is a Kotlin compiler plugin: it requires Kotlin 2.3+ and you apply its Gradle plugin.

| *Inara* (compile-time, experimental)
| You want Kodein's successor: explicit, compile-checked wiring with no annotations beyond one `@DIModule`.
  Inara is a KSP processor, so you apply KSP. It has no multibindings, so you add your own services to Bootable's yourself.
|===

Vanilla needs nothing special — the plain `boot` artifact carries no DI framework. For a DI style, depend on a
module's `-kodein` or `-metro` *artifact* instead of its plain coordinate. Each DI artifact bundles that
module's bindings, pulls in the DI framework, and depends on the plain artifact — so one ordinary dependency per
module gives you everything, with no attribute, capability, or Gradle plugin to configure, and it resolves
identically from Gradle and Maven:

[source,kotlin]
----
dependencies {
  // Kodein style — the -kodein coordinate of each module you wire through DI:
  implementation("com.github.rocketraman.bootable:boot-kodein:$v")
  implementation("com.github.rocketraman.bootable:boot-config-hoplite-kodein:$v")

  // ...or Metro style — the -metro coordinate of each module (also apply Metro's Gradle plugin + Kotlin 2.3+):
  implementation("com.github.rocketraman.bootable:boot-metro:$v")
  implementation("com.github.rocketraman.bootable:boot-config-hoplite-metro:$v")

  // ...or vanilla — the plain coordinate, no DI framework:
  implementation("com.github.rocketraman.bootable:boot:$v")
}
----

A module ships a `-metro`/`-kodein` artifact only when it has bindings for that framework; otherwise depend on
its plain coordinate. Modules you don't wire through DI (e.g. `boot-logging-log4j2`) are always the plain
coordinate.

== Vanilla

Construct the shared dependencies and services, build the set, and return a `Bootable`:

[source,kotlin]
----
fun main() = boot {
  val binder = hopliteConfigBinder()
  // lifecycleControllers defaults to defaultLifecycleControllers(); pass it only for a custom lifecycle
  Bootable(
    appServices = setOf(ExampleServer(binder.config("server"), binder.config("hello"))),
  )
}
----

Tests need no DI at all — construct services directly. The trade-off is that in a multi-module app the
composition root lists every service by hand; if you want that list assembled for you, use a DI style below.

== Kodein-DI

Import Bootable's Kodein modules, contribute your services with Kodein's multibindings, and hand the resolved
`Bootable` to `boot`:

[source,kotlin]
----
fun main() = boot {
  val di = DI {
    import(bootableModule)      // Bootable + default controllers + the multibinding sets
    import(hopliteConfigModule) // binds ConfigBinder (boot-config-hoplite:kodein)
    bindSingleton { instance<ConfigBinder>().config<ServerConfig>("server") }
    bindAppService { singleton { ExampleServer(instance(), instance()) } }
  }
  di.direct.instance<Bootable>()
}
----

`bootableModule`, `hopliteConfigModule`, `environmentModule` and the `bindAppService` / `bindLifecycleController`
helpers come from the modules' `-kodein` artifacts (`boot-kodein`, `boot-config-hoplite-kodein`,
`boot-env-kodein`).

== Metro

Declare a `@DependencyGraph` that extends `BootableGraph`, contribute your services with `@ContributesIntoSet`,
and boot the graph's `bootable`:

[source,kotlin]
----
@ContributesIntoSet(AppScope::class)
@SingleIn(AppScope::class)
class ExampleServer(config: ServerConfig, hello: HelloConfig) : NettyKtorService("test", config)

@ContributesTo(AppScope::class)
interface ServerConfigBindings : ConfigBinderProvider {  // config bindings are just a type and a key
  @Provides fun serverConfig(): ServerConfig = config("server")
  @Provides fun helloConfig(): HelloConfig = config("hello")
}

@DependencyGraph(AppScope::class, additionalScopes = [BootScope::class])
interface AppGraph : BootableGraph

fun main() = boot { createGraph<AppGraph>().bootable }
----

`BootableGraph`, `BootScope`, `BootableDefaultBindings` come from `boot-metro`; `ConfigBinderProvider` from
`boot-config-common-metro` (re-exposed by `boot-config-hoplite-metro`). The rest of this section is the one
concept in Metro worth understanding before you rely on it.

=== The one thing to understand: discovery vs. lifetime

Metro has two orthogonal concerns that are both spelled with a *scope* (a marker type like `AppScope`). Because
the same scope type shows up in both, they are easy to conflate — but they answer different questions:

[cols="1,1,3", options="header"]
|===
| Concern | Annotation | Question it answers

| *Discovery*
| `@DependencyGraph(Scope::class)` argument, `additionalScopes`, `@ContributesTo(Scope)`, `@ContributesIntoSet(Scope)`
| _Which graph does this binding end up in?_

| *Lifetime*
| `@SingleIn(Scope::class)`
| _One instance per graph, or a fresh one every time it's requested?_
|===

CAUTION: Metro's own documentation calls `@DependencyGraph(AppScope::class)` and `@SingleIn(AppScope::class)` on
a graph "functionally equivalent". That is true *for scoping only*. Passing the scope as the `@DependencyGraph`
**argument** additionally turns on *discovery* (aggregation of every `@ContributesTo` / `@ContributesIntoSet`
for that scope on the compile classpath). Declaring the scope with `@SingleIn` gives the same singleton lifetime
*without* turning discovery on.

A place this bites: `@ContributesIntoSet(AppScope::class)` puts a service in the set (discovery) but does *not*
make it a singleton. Without `@SingleIn(AppScope::class)` as well, every read of the set constructs a fresh
instance — so the instance you inspect is not the one Bootable started. Always pair the two on a stateful
service.

=== Bootable's scope, and yours

`BootScope`:: Declared by Bootable, for Bootable's own bindings (the runtime, the default controllers, the config
binder). You never scope your own code to it.

Your application scope:: You declare it (`sealed interface AppScope`), name it whatever you like, and pass it as
the `@DependencyGraph` argument. Your own contributions therefore always apply.

A graph may only host bindings whose scope it declares, and Bootable's bindings are `@SingleIn(BootScope)`.
`BootableGraph` carries that `@SingleIn(BootScope::class)` declaration, so your graph *inherits* it by extending
`BootableGraph` and never has to mention `BootScope` — it declares only your own scope. Bootable brings its own
scope.

=== Magic vs. explicit

The magic/explicit choice is only about how *Bootable's* containers reach your graph:

.Magic — discovered; your graph names nothing
[source,kotlin]
----
@DependencyGraph(AppScope::class, additionalScopes = [BootScope::class])
interface AppGraph : BootableGraph
----

.Explicit — every container is named; nothing is discovered from the classpath
[source,kotlin]
----
@DependencyGraph(
  AppScope::class,
  bindingContainers = [BootableDefaultBindings::class, HopliteConfigBindings::class],
)
interface AppGraph : BootableGraph
----

The absence of `additionalScopes = [BootScope::class]` is what keeps discovery off and the graph closed to
classpath contributions. Mixing is harmless: naming a container that is also discovered does not produce a
duplicate binding.

=== Testing with Metro

Unit tests need no DI (domain classes take plain constructor parameters). To override a binding in an
integration test, `createDynamicGraph<AppGraph>(FakeBindings)` builds the real graph with one container
substituted, still at compile time. See `examples/server-ktor`'s tests.

== Inara (experimental)

https://kosi-libs.org/inara/[Inara] is the compile-time successor to Kodein-DI, from the same authors, who are https://kodein-koders.com/en/blog/inara-inject-your-dependencies-at-compile-time/[sunsetting Kodein] in its favour.
Bootable's Inara support is experimental, as is Inara itself (0.2.0 at the time of writing): its shape may change, and if it settles, the Kodein bindings will be deprecated in its favour.

An Inara module is an interface whose members are its dependencies.
Inara's KSP processor generates a builder for each interface annotated `@DIModule`, taking one `Binding` per member, and a member without a default needs one, so a missing binding is a compile error.
Each binding's body has the module as its receiver, so it reaches the other members by name.

Each Bootable module's `-inara` artifact contributes a `@DIModule` (`BootableModule`, `ConfigModule`, `EnvironmentModule`, `JdbcDataSourceModule`, `FlywayMigrationModule`, `ExposedDatabaseModule`), with a builder function of the same name that binds all of its members.
`BootableModule` is itself composed over the `ConfigModule` it is built with, so an application that extends `BootableModule` has the config too.
The other builders take the modules they use, such as the `JdbcDataSourceModule` that Flyway migrates, and a _context_: the `BootableModule`, from which they read their config and to which they add their services.
Your application's module is a _composed_ `@DIModule` that extends the modules it uses and adds its own members.
Its generated builder takes each parent as a built module, plus a binding for each of its own members, and reuses the parents' bindings, so a singleton is shared between a parent and your module.

[source,kotlin]
----
@DIModule(composed = true)
interface AppModule : BootableModule {
  val greetingConfig: GreetingConfig
  val greetingService: GreetingService
}

fun main() = boot {
  val bootable = BootableModule(HopliteConfigModule())
  val app = AppModule(
    bootableModule = bootable,
    greetingConfig = bootable.config("greeting"),
    greetingService = Binding.single { GreetingService(greetingConfig) },
  )
  app.addAppService { app.greetingService }
  app.bootable
}
----

`bootable.config("greeting")` binds a config section, decoded once, in any module, like Metro's `ConfigBinderProvider.config`.
It works on any `ConfigModule`, and the Bootable modules' builders bind their own sections the same way, from their context.

A larger application can give its own code a module of its own, built like the Bootable modules, and compose them all, as Kodein imports modules.
The database is `JdbcDataSourceModule` with the application's two choices, a driver module's config (`SqliteConfigSource`, `PostgresqlConfigSource`, `MysqlConfigSource`, or `JdbcGenericConfigSource` for any database by URL) and a pool (`HikariPool()`), as Kodein imports a driver config module and a pool module:

[source,kotlin]
----
@DIModule
interface EntriesModule {
  val entryRepository: EntryRepository
  val entryServer: EntryServer
  …
}

fun <C> EntriesModule(exposed: ExposedDatabaseModule, context: C): EntriesModule
  where C : ConfigModule, C : AppServiceAcceptor {
  val module = EntriesModule(
    entryRepository = Binding.single { EntryRepository(exposed.database) },
    …
  )
  context.addAppService { module.entryServer }
  return module
}

@DIModule(composed = true)
interface AppModule : BootableModule, JdbcDataSourceModule, FlywayMigrationModule, ExposedDatabaseModule, EntriesModule

fun appModule(): AppModule {
  val bootable = BootableModule(HopliteConfigModule())
  val jdbc = JdbcDataSourceModule(SqliteConfigSource, HikariPool(), bootable)
  val exposed = ExposedDatabaseModule(jdbc, setOf(EntryTable), bootable)
  return AppModule(
    bootableModule = bootable,
    jdbcDataSourceModule = jdbc,
    flywayMigrationModule = FlywayMigrationModule(jdbc, bootable),
    exposedDatabaseModule = exposed,
    entriesModule = EntriesModule(exposed, bootable),
  )
}
----

Composing the modules into an `AppModule` is optional: each builder has already added its services to the `BootableModule`, so `boot { bootable.bootable }` runs them too.
The composed module gives the application, and its tests, one module to reach everything from.

Apply KSP, and add Inara's processor to it:

[source,kotlin]
----
plugins {
  id("com.google.devtools.ksp") version "2.3.13"
}

dependencies {
  implementation("com.github.rocketraman.bootable:boot-inara:$v")
  implementation("com.github.rocketraman.bootable:boot-config-hoplite-inara:$v")
  ksp("org.kodein.di.inara:inara-processor:0.2.0")
}
----

Bootable's `-inara` artifacts ship their modules' generated builders, so the processor only runs on your own modules.
`boot-config-hoplite-inara` adds `HopliteConfigModule()`, a `ConfigModule` with the default Hoplite `ConfigBinder`, like Kodein's `hopliteConfigModule`.
To pass Hoplite options, build the module yourself: `ConfigModule(configBinder = Binding.single { hopliteConfigBinder(report = false) })`.
Inara 0.2.0's runtime is built with Kotlin 2.4, so your compiler must be Kotlin 2.3 or later to read it; its first release may move to Kotlin 2.5.

=== What differs from Kodein and Metro

No multibindings:: Inara resolves everything at compile time, through generated code, and has no equivalent of Kodein's `inBindSet` or Metro's `@IntoSet`.
Instead, `BootableModule` is an `AppServiceAcceptor`, and each Bootable module's builder adds its own services to the context it is given, so the application adds only its own, with `app.addAppService { … }` once its module is built.
The builders' context is typed `C where C : ConfigModule, C : AppServiceAcceptor`, so they see only the config and `addAppService`, not the rest of the `BootableModule`.
Each `BootableModule(…)` has its own services, so tests and several applications in one process don't share them.
Forgetting one of those is not a compile error: the module is wired, but the service never starts.
`EnvironmentModule(context)` adds its initializer to the context, a `LifecycleControllerAcceptor`, in the same way.
Tables and customizers, which only the application provides, are plain parameters: `ExposedDatabaseModule(jdbc, tables, context, customizers)`.

No optional bindings:: Inara never looks up a type, so where Kodein uses a binding only if there is one, the builder function takes a nullable parameter instead.
`BootableModule(configModule)` reads the tiebreaker from the `boot.service.order` config section, as Kodein and Metro do whenever there is a `ConfigBinder`.
`BootableModule()` has the `EmptyConfigModule`, whose binder fails every read, and the tiebreaker is `ByName`.
Pass `startOrder` or `tiebreaker` to set them in code.
A member with a default body, such as `startOrder` or `dataSource`, is optional too, and runs on every access.

No diamonds:: A composed module rejects two parents that share an ancestor, so only `BootableModule` extends `ConfigModule`, and the other Bootable modules don't extend each other: `FlywayMigrationModule(jdbc, context)` takes the `JdbcDataSourceModule` it migrates, and the context it reads its config from, as parameters instead.

Singletons are per module:: `Binding.single` builds once per module instance, which is what Metro's `@SingleIn` gives; the builder functions use it for every stateful member.

See `examples/wiring-inara`, and `examples/server-ktor-db/inara` for the database modules.

== A note on performance

None of these styles was chosen for speed, and you should not pick one for that reason. On a native image the
difference between them is noise; on the JVM the DI-construction cost differs, but in a real service the rest of
the stack (config loading, ktor, logging, JVM warmup) dominates cold start regardless.
Choose on ergonomics and safety, not startup.
