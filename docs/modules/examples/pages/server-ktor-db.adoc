= Server with a database
:description: A key/value store over HTTP, with a database, telemetry, an HTTP client, health probes, and background work, wired four ways.

`server-ktor-db` is a Ktor server that stores named entries in a SQLite database, and traces and measures itself with OpenTelemetry.
Its `+GET /relay/{name}+` calls the server back through a lifecycle-managed Ktor `HttpClient`, as a call to another service would be made.
In the background, a periodic loop logs the entry count, on the leader only, and a db-scheduler task logs a digest of the entries.

It is the example that puts most of Bootable's functions together, and it is wired each of the four ways: the server, repository, table, migrations, and config are shared, in `common`, and `vanilla`, `kodein`, `metro`, and `inara` are each a runnable application.
`jib` builds the vanilla application into a container image, with its JVM AOT cache in it.

== What it uses

* xref:database:index.adoc[Database]: SQLite (xref:database:drivers.adoc[`boot-db-jdbc-sqlite`]) through a HikariCP pool (xref:database:hikari.adoc[`boot-db-pool-hikari-otel`]), migrated by xref:database:flyway.adoc[Flyway], and queried with xref:database:exposed.adoc[Exposed], which verifies the `entry` table against the migrated schema; `boot-db-jdbc-otel` traces each query.
* xref:http:server.adoc[HTTP server]: `EntryServer`, a `CioKtorService`, on Ktor's CIO engine.
* xref:http:client.adoc[HTTP client]: the named client `entries`, from `boot-client-http-ktor-cio`, traced by `boot-client-http-ktor-otel`.
* xref:http:health.adoc[Health]: liveness and readiness, served by the server as JSON, with readiness down while the database doesn't answer, and the xref:http:health.adoc#build-info[build info].
* xref:telemetry:index.adoc[Telemetry]: the OpenTelemetry SDK, a Prometheus scrape at `/metrics`, the server's request traces and metrics, the pool's metrics, and a trace of the application's start, with a span for each service's start.
* xref:background:periodic.adoc[Periodic work]: the entry count's loop, gated on xref:background:leader.adoc[leader election] through a Kubernetes Lease, which the config skips outside Kubernetes (`leader.kubernetes.assumeLeader = true`).
* xref:background:scheduler.adoc[Scheduled tasks]: the entry digest, a recurring db-scheduler task, whose table Flyway migrates with the application's.
* xref:configuration:index.adoc[Configuration] and xref:logging:index.adoc[Logging], as in every example.

`SeedEntriesService` stores two sample entries on a first run.
It starts after the `DbMilestones.SchemaMigrated` milestone, in the `Initialization` phase, so it runs on a migrated schema, and before the server takes a request.

== Wire

[tabs,sync-group-id=di]
======
Vanilla::
+
`EntriesApp`, in `vanilla/src/main/kotlin/App.kt`, constructs every service and lifecycle controller in plain Kotlin, and `main` hands them to `Bootable`:
+
[source,kotlin]
----
fun main() = boot {
  val app = EntriesApp(hopliteConfigBinder())
  Bootable(app.services, app.lifecycleControllers)
}
----
+
The order of the set doesn't matter: each service declares where it starts, and Bootable logs the start plan.

Kodein::
+
`appDI()`, in `kodein/src/main/kotlin/App.kt`, imports each module's Kodein module, and `entriesModule`, the application's own bindings:
+
[source,kotlin]
----
fun appDI() = DI {
  import(bootableModule)
  import(hopliteConfigModule)
  import(openTelemetryModule)
  // ... telemetry, server, health, and client modules
  import(jdbcDataSourceModule)
  import(sqliteConfigModule)
  import(hikariPoolModule)
  import(flywayMigrationModule)
  import(exposedDatabaseModule)
  // ... leader election, periodic, and db-scheduler modules
  import(entriesModule)
}

fun main() = boot {
  appDI().direct.instance<Bootable>()
}
----

Metro::
+
The `-metro` modules contribute their bindings on their own; `EntriesBindings`, in `metro/src/main/kotlin/App.kt`, contributes the application's, and the graph adds two binding containers:
+
[source,kotlin]
----
@DependencyGraph(
  AppScope::class,
  additionalScopes = [BootScope::class],
  bindingContainers = [ServiceStartTracingBindings::class, JdbcHealthCheckBindings::class],
)
interface AppGraph : BootableGraph

fun main() = boot {
  createGraph<AppGraph>().bootable
}
----
+
Leaving out the driver or the pool fails the compilation with a missing binding.

Inara::
+
`EntriesModule`, in `inara/src/main/kotlin/App.kt`, is the application's own module, which requires the Bootable modules it uses; `AppModule` composes it with them, each once:
+
[source,kotlin]
----
@DIModule(composed = true)
interface AppModule :
  ConfigModule, BootableModule, OpenTelemetryModule,
  // ... telemetry, server, health, and client modules
  JdbcDataSourceModule, HikariPoolModule, FlywayMigrationModule, ExposedDatabaseModule,
  // ... leader election, periodic, and db-scheduler modules
  EntriesModule

fun appModule(): AppModule = AppModule(
  configModule = hopliteConfigModule(),
  bootableModule = bootableModule(),
  openTelemetryModule = openTelemetryModule(),
  // ...
  jdbcDataSourceModule = jdbcDataSourceModule(SqliteConfigSource),
  hikariPoolModule = hikariPoolModule(),
  flywayMigrationModule = flywayMigrationModule(),
  exposedDatabaseModule = exposedDatabaseModule(setOf(EntryTable)),
  // ...
  entriesModule = entriesModule(),
)

fun main() = boot {
  appModule().bootable
}
----
+
Leaving out the driver or the pool, or any module another requires, fails the compilation.

From the repository root:

======

+
[source,shell]
----
./gradlew :examples:server-ktor-db:vanilla:run
----

Kodein::
+
[source,shell]
----
./gradlew :examples:server-ktor-db:kodein:run
----

Metro::
+
[source,shell]
----
./gradlew :examples:server-ktor-db:metro:run
----

Inara::
+
[source,shell]
----

----

Each serves http://localhost:8001, and keeps its database in its own directory, at `build/entries.db`.
The config is in `common/src/main/resources/application.conf`.

== Endpoints

http://localhost:8001 is an index page, with a form to try each operation, the API, and the entries stored so far.

`GET /entries`:: Lists every entry, one `name=value` per line.
`+GET /entries/{name}+`:: Returns an entry's value, or 404.
`+PUT /entries/{name}+`:: Stores the request body as the entry's value.
`+DELETE /entries/{name}+`:: Removes an entry, or answers 404.
`+GET /relay/{name}+`:: Gets an entry by calling `+GET /entries/{name}+` on this server through the `entries` HTTP client, configured under `http.client.named.entries`.
`GET /metrics`:: The Prometheus scrape.
`GET /health/live`:: Liveness: 200 until the application has stopped.
`GET /health/ready`:: Readiness: 200 while the application is running and the database answers, 503 otherwise.
`GET /health/info`:: The build info, from the `build` config section.

For example, store an entry, and get it back through the HTTP client:

[source,shell]
----
curl -X PUT --data 'hello' http://localhost:8001/entries/greeting
curl http://localhost:8001/relay/greeting
----

The health endpoints answer in JSON, with the lifecycle state, and readiness with its one check, the database's, by name:

[source,shell]
----
$ curl -s http://localhost:8001/health/live
{"status":"UP","state":"Running"}
$ curl -s http://localhost:8001/health/ready
{"status":"UP","state":"Running","checks":{"jdbc":{"status":"UP"}}}
----

So a script can check the database:

[source,shell]
----
curl -s http://localhost:8001/health/ready | jq -e '.checks.jdbc.status == "UP"'
----

To see readiness go down before the server stops, set a drain delay, as `HEALTH_READINESS_DRAINDELAY=10s`, stop the application with Ctrl-C, and ask for readiness during the delay.

Start the application with a version, such as `BUILD_VERSION=1.4.2`, and a test can check which build answered it:

[source,shell]
----
curl -s http://localhost:8001/health/info | jq -e '.version == "1.4.2"'
----

== Metrics and traces

As configured, the example has no OTLP endpoint, so it pushes nothing: its metrics are only pulled, from its Prometheus scrape, which needs nothing else running.
After a few requests, the scrape has the server's request metrics, the pool's, the JVM's, and the example's own counter, `entries_stored_total`:

[source,shell]
----
curl -s http://localhost:8001/metrics | grep -E 'entries_stored|http_server_request_duration_seconds_count|db_client_connections_usage'
----

Traces are only pushed, so they need a collector, and an OTLP endpoint to reach it.
With one set, the example pushes its metrics there too, every `metrics.interval`, and still serves the scrape.
Grafana's `otel-lgtm` image runs a collector, with Tempo, Prometheus, Loki, and Grafana, in a single container:

[source,shell]
----
podman run --rm -p 3000:3000 -p 4318:4318 docker.io/grafana/otel-lgtm
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 TELEMETRY_SDK_METRICS_INTERVAL=5s ./gradlew :examples:server-ktor-db:vanilla:run
----

In Grafana, at http://localhost:3000, search Tempo for the service `entries`.
Each request is a trace, with a span for the database operation, such as `entries.put`, and a span for each of its queries within that.
`+GET /relay/{name}+` has a client span, with the server's own `+GET /entries/{name}+` within it, since the client carries the trace in a `traceparent` header.
The application's start is a trace too, `start application`, with a span for each service's start.

Jaeger takes OTLP as well: run `docker.io/jaegertracing/jaeger:latest` with ports 16686 and 4318, and open http://localhost:16686.

Log lines written within a request carry its `trace_id` and `span_id`.

== Start faster, with an AOT cache

The `vanilla` application has an `aotCache` task, which runs the installed application once, serving a few requests, to write its JVM AOT cache; run the application with it:

[source,shell]
----
./gradlew :examples:server-ktor-db:vanilla:aotCache
cd examples/server-ktor-db/vanilla
JAVA_OPTS=-XX:AOTCache=build/aot/vanilla.aot build/install/vanilla/bin/vanilla
----

The `jib` project builds the vanilla application into a container image, `bootable-examples/server-ktor-db-jib`, with the cache in it.
The JVM only uses a cache with the same JDK build and the same jars as the run that trained it, so the training runs in a container of the image itself, and the final image adds the cache as one more layer:

[source,shell]
----
./gradlew :examples:server-ktor-db:jib:jibDockerBuild -PcontainerCli=podman
podman run --rm -p 8001:8001 bootable-examples/server-ktor-db-jib
----

Leave out `-PcontainerCli=podman` to use Docker.
The repository's `server-ktor-db` https://dagger.io[Dagger] module builds the same image as a CI pipeline.
`mise run demo` uses it to run the image with the `otel-lgtm` stack, in containers, with the OTLP endpoint set, so its traces and metrics are pushed to Grafana at http://localhost:3000.
