= Web app with Kilua
:description: A todo list with a Kilua client, rendered on the server by a Node.js process that Bootable starts before the Ktor server.

`kilua` is the same todo list as xref:compose-html.adoc[Compose HTML] and xref:htmx.adoc[htmx], written with https://kilua.dev[Kilua], a web framework built on JetBrains' Compose runtime.
The client runs in the browser, as in compose-html, but with server-side rendering, so each page arrives with its content, as in htmx.

Kilua renders on the server by running the client itself, in Node.js.
It shows how Bootable runs a process that the server depends on: `SsrRenderer`, an `AppService`, starts the renderer, and the server, in a later phase, starts only once it is up.

It is in three projects, as compose-html is: `shared`, the models and the title rule; `client`, the Kilua UI, bundled for the browser and, as `ssr.zip`, for Node.js; and `server`, which serves the rendered page at `/`, the client's files, and the JSON API under `/api/todos`.
Todos are kept in memory; xref:server-ktor-db.adoc[] stores data in a database.

== What it uses

* `boot`, for the order of the two services: `SsrRenderer` declares no phase, so it is in `Application`, and `TodoServer`, as a `KtorService`, is in `Serving`, which starts after it and stops before it.
* `boot-server-http-ktor-netty`, for `TodoServer`, a `NettyKtorService`; see xref:http:server.adoc[].
* `boot-config-hoplite`, for the `server` and `ssr` config sections; see xref:configuration:index.adoc[].
* `boot-logging-log4j2`, for the log; see xref:logging:index.adoc[].

The two services are wired with plain Kotlin, in `server/src/main/kotlin/App.kt`:

[source,kotlin]
----
fun appServices(binder: ConfigBinder): Set<AppService> {
  val serverConfig = binder.config<ServerConfig>("server")
  val renderer = SsrRenderer(binder.config("ssr"), serverConfig.localUrl())
  return setOf(
    renderer,
    TodoServer(serverConfig, TodoRepository(), renderer),
  )
}
----

`SsrRenderer.start()` starts Kilua's `SsrEngine`, which runs the renderer in Node.js, and returns once the renderer has rendered a first page, so the server never takes a request it can't render.
It has no `shutdown()`: `SsrEngine` stops Node.js only from a JVM shutdown hook, after Bootable has stopped the server.

== Run it

The server needs Java 25, since Kilua's `kilua-ssr-server` is built for it, and Node.js; `run` uses the Node.js that the Kotlin Gradle plugin downloads.
From the repository root:

[source,shell]
----
./gradlew :examples:kilua:server:run
----

Then open http://localhost:8004.
To see what server-side rendering adds, look at the first response, before any script runs:

[source,shell]
----
curl http://localhost:8004/
----

The log shows the renderer start before the server, and stop after it.

Run from the server's jar or distribution, it runs `node` from the `PATH`; set `SSR_NODE` to use another.

=== Live reload

As in compose-html, run the server in one terminal, and the client's development server in another:

[source,shell]
----
./gradlew :examples:kilua:server:run
./gradlew --continuous :examples:kilua:client:jsBrowserDevelopmentRun
----

Then open http://localhost:8080, which forwards requests under `/api` to the server.
Pages aren't rendered on the server this way: the client loads the todos and renders them in the browser.

== Tests

[source,shell]
----
./gradlew :examples:kilua:server:test
----

`TodoServerTest` runs the API in Ktor's test host.
`ServerRenderingTest` starts the renderer and the server in Bootable's order, and checks that the first response is the rendered page, with the latest todos; without Node.js it is skipped, except on CI.
