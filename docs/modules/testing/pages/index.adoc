= Testing
:description: Helpers for unit tests: a test clock, captured logs, start plans, and in-memory telemetry, without booting the application.

`boot-test` and `boot-test-otel` are helpers for unit tests, in plain Kotlin, so JUnit, Kotest, and TestBalloon can all use them.
`boot-test` has a test clock, captured logs, a check of the start plan, and config for a test; `boot-test-otel` collects the spans and metrics an OpenTelemetry SDK records, in memory.
An application adds them as test dependencies.

They deliberately don't boot the application.

NOTE: Bootable won't add a way to boot the application in tests.
Where one exists, as in the Spring Boot ecosystem, it tends to become the way every test is written, because it is the easy way out: nobody has to think about injecting fakes.
That makes tests slow and brittle, and replaces unit tests rather than complementing them.
If this style of testing makes sense for your project, it is easy to implement yourself.

Instead, a test constructs what it tests, as the wiring does:

* *A class*: construct it, with a fake for each thing it uses.
* *A Ktor server's routes*: run its module in Ktor's `testApplication`, with the server constructed the same way.
* *The wiring*: build the application's graph, or call its vanilla wiring, and check the services it builds and their start plan, without starting anything.

== Install

Add them as test dependencies, in the flavour of your wiring style:

install::testImplementation[boot-test, boot-test-otel]

`boot-test` has no flavours, since nothing in it is wired; `boot-test-otel` has `-kodein`, `-koin`, `-metro`, and `-inara` flavours, for its <<telemetry,module and bindings>>.

[#clock]
=== The clock

`TestClock` is a `kotlin.time.Clock` that stands still until the test moves it, with `advanceBy` or `set`.
It starts at `TestClock.DEFAULT_START`, 2026-01-01T00:00:00Z, so a test's times are the same on every run, and it is safe to read and move from any thread.

[source,kotlin]
----
include::ROOT:example$vanilla/testing/Helpers.kt[tag=clock]
----

Pass it to whatever takes a `Clock`, such as `OpenTelemetryService`, `ServiceStartTracing`, or `PeriodicAppService`, or, with Kodein, Koin, or Metro, bind it as the `Clock`, which they then take their time from; with Inara, which has no optional bindings, pass it to each module's builder, such as `openTelemetryModule(clock)`.
For a monotonic `TimeSource`, use the standard library's `kotlin.time.TestTimeSource`.

=== Logs

`captureLogs(loggerName) { ... }` runs the block, and returns the Log4j2 events logged meanwhile to that logger and its descendants, the root logger by default:

[source,kotlin]
----
include::ROOT:example$vanilla/testing/Helpers.kt[tag=logs]
----

The result is a `LogCapture`, closed, with these to assert on:

* `events`: every event captured, in the order they were logged, and `events(level) { ... }`, those at a level that match.
* `messages(level)`: the formatted messages of the events at a level, or at any level.
* `single(level) { ... }`: the one event that matches, or an `AssertionError` that lists what was captured.
* `describe()`: what was captured, one event per line, such as for an assertion's message.

Each event is Log4j2's own `LogEvent`, copied, with its level, logger, message, thrown, and context data, such as the trace and span ids that `boot-telemetry-otel` puts there.
`fields` has the structured fields of a map message, such as a `StringMapMessage`.

A `LogCapture` captures from when it is created until it is closed, so a test can use it around more than one block.
It captures what the logger's level lets through; a `level` lowers the logger's level while it captures, such as to `Level.DEBUG`, and its other appenders then get those events too:

[source,kotlin]
----
include::ROOT:example$vanilla/testing/Helpers.kt[tag=log-capture]
----

Both initialize Bootable's logging for the test first, with `testLoggingInit()`, as `boot` does for an application: Bootable's base Log4j2 configuration, merged with the test's own `log4j2.xml`, if it has one, at the level of `LOGGING_LEVEL`, or `logging.level`, or `INFO`.
Unlike `boot`, it leaves standard out and error alone, so the test framework's output is too.
A test that logs without capturing can call `testLoggingInit()` itself; only the first call has any effect.
See xref:logging:index.adoc[] for the configuration it loads.

[#suspend-failures]
=== Failures in suspending code

A service's `start` and `shutdown` suspend, so a test that checks that one fails calls it in a coroutine.
`runSuspendCatching { ... }` is `runCatching` for a block that suspends, such as to assert that a service's start fails.
It catches what the block throws, but not the cancellation of the test's own coroutine, which `runCatching` would swallow, so a cancelled test stops rather than carrying on.

== Test a Ktor server's routes

Run the server's module in Ktor's `testApplication`, from `io.ktor:ktor-server-test-host`, with the server constructed as the wiring constructs it, and its dependencies either fakes or real ones the test starts by hand.
The test's `client` then calls the routes without opening a port.
`captureLogs` and `InMemoryTelemetry` work there as anywhere else.

`examples/server-ktor-db` tests its routes this way, against a SQLite database in a temporary directory; see <<example>>.

The config comes from the test's resources, as it does for the application.
Constructing `OpenTelemetryService` builds the SDK, so a test's config doesn't register it as the global `OpenTelemetry`, and leaves out the runtime metrics:

[source,hocon]
----
telemetry.sdk {
  registerGlobal = false   # <1>
  metrics.runtime = false  # <2>
}
----
<1> Keeps each test's SDK out of the process's `GlobalOpenTelemetry`, which only the first SDK in a process can be, so a test doesn't depend on which test ran first.
<2> Leaves out the JVM's runtime metrics, which a test doesn't check.

A test that wires the application with a DI flavour can do without config files: `StaticConfigBinder` is a `ConfigBinder` that the test gives its config sections to, already decoded, by prefix, such as `StaticConfigBinder("health.ktor" to KtorHealthConfig(hostPort = "127.0.0.1:0"))`.
Asked for a section it doesn't have, or for one of another type, it fails, naming the prefix.

[#start-plans]
=== The start plan

`checkShuffledStartPlans(services) { plan -> ... }` computes the services' start plan, the order Bootable would start them in, and runs the check on it, without starting anything.
It does so twenty times, by default, each with the ties between services that their orderings leave unordered broken by a different `StartOrder.Tiebreaker.Shuffled`.
A service that relies on an order its ordering doesn't declare fails the check in some of them.

A check that fails is rethrown as an `AssertionError` that names the tiebreaker's seed and lists the plan, so `startPlan(services, tiebreaker = StartOrder.Tiebreaker.Shuffled(seed))` replays it.
`rounds`, `startOrder`, and `random` change how many plans it checks, the start order they follow, and where the seeds come from.

`indexOfService<T>()` is where the first service of type `T` is in a plan, or -1 if there is none.

With Kodein, Koin, Metro, and Inara, the SDK's config comes from the test's resources, as in <<wiring>>.

* `spans`: the spans that have ended so far, in the order they ended, and `spans(name)`, those with a name.
* `metrics()`: every metric recorded so far, collected now, and `metric(name)`, the one with a name, or null.
* `resetSpans()`: forgets the spans ended so far, such as those of what the test set up, so it sees only its own.
* `spanExporter` and `metricReader`: OpenTelemetry's in-memory exporter and reader, for anything else.

A `TestClock`, passed to `OpenTelemetryService` or bound as the `Clock`, is the SDK's clock, so the spans' and measurements' times are the test's.
See xref:telemetry:index.adoc#customizers[] for the SDK's customizers.

== Example

`examples/server-ktor-db` is tested as this page describes, without booting it:

* `common/src/test/kotlin/EntryServerTest.kt` runs the server's routes in `testApplication`, against a SQLite database in a temporary directory, with the services it needs started by hand, and captures the server's log with `captureLogs`.
* `vanilla/src/test/kotlin/AppTest.kt` checks the vanilla wiring's services, and its start plan with `checkShuffledStartPlans`: the seed entries after the migrations, and before the server.
* `kodein/src/test/kotlin/AppTest.kt`, `koin/src/test/kotlin/AppTest.kt`, and `metro/src/test/kotlin/AppTest.kt` check the services that the Kodein `DI`, the Koin application, and the Metro graph build.
