= Start order
:description: How Bootable orders services: phases, milestones within a phase, the tiebreaker, the logged start plan, and custom start orders.

Services start phase by phase, and, within a phase, after the services that provide the milestones they wait for.
Services that neither orders are tied, and a tiebreaker orders them.
They stop in exactly the reverse order.

Each service says where it starts with its `ordering()`, an `Ordering` of its phase and its milestones.
Bootable computes the order, the _start plan_, from the set of services it is given, before anything starts, and logs it.
The order is the same whether the services were wired by hand, by Kodein, by Koin, or by Metro, since it comes from the services themselves.

[#phases]
== Phases

Bootable's default phases, in start order:

[cols="1,3,3",options="header"]
|===
| Phase | Holds | Bootable's modules

| `Telemetry`
| What every other service records into, so it can record from its first moment, and what it records while it stops is still exported.
| The OpenTelemetry SDK; the xref:http:health.adoc#listener[health probes' own listener], so liveness answers while the others start.

| `Infrastructure`
| Connections to the systems the application needs, and the plumbing the rest relies on.
| The xref:database:index.adoc[database pool], and Exposed's `Database`; the xref:http:client.adoc[HTTP clients]; xref:background:leader.adoc[leader election].

| `Initialization`
| Work that brings shared state into shape before the application uses it, such as migrations, schema checks, seed data, and cache warm-up.
| xref:database:flyway.adoc[Flyway's migrations]; Exposed's xref:database:exposed.adoc[schema verification].

| `Application`
| The application's own services: what the work needs, but not what brings the work in.
The default phase.
| None: this phase is the application's.

| `Serving`
| Whatever brings work in: HTTP and gRPC servers, queue consumers, schedulers.
It starts last, once what it uses is running, and stops first, so work in flight can finish.
| The xref:http:server.adoc[Ktor server]; xref:background:periodic.adoc[periodic work]; the xref:background:scheduler.adoc[db-scheduler].
|===

To choose a phase, ask, in this order:

. Does every other service record into it? `Telemetry`. Applications rarely write one.
. Does it bring work in? `Serving`, whatever the protocol: a timer firing is work arriving, as a request is.
. Is it a connection, or plumbing, that others use? `Infrastructure`: the application's own handle on a system, such as its pool, not the system itself.
. Does it change or check shared state once, before anyone uses it? `Initialization`.
. Otherwise, `Application`.

A service that is both used by others and brings work in, such as one that consumes messages, is usually two services: the part others use in `Application`, and the consumer in `Serving`.

The `Initialization` phase isn't a lifecycle controller's `appInit`, logged as `=> Initializing`, which runs before any service starts; see xref:lifecycle.adoc#start[the start].

[#milestones]
== Milestones

Within a phase, a milestone orders one service after another.
A milestone is a named point that a service reaches once its `start` returns.
A service `provides` milestones, and starts `after` the ones it waits for:

[source,kotlin]
----
include::ROOT:example$vanilla/concepts/StartOrder.kt[tag=milestones]
----

A service waits for every provider of a milestone, and a milestone can have several, or none.
A provider in an earlier phase has already started, so a milestone matters only between services in the same phase.

A milestone names a role, not a class, so a service orders itself after a role, whichever module fills it.
Bootable's own:

* `DbMilestones.DataSourceReady`, when the connection pool has started, and `DbMilestones.SchemaMigrated`, when the migrations have run: Exposed's schema verification runs after the migrations without knowing which tool ran them, or whether there is one.
* `HttpClientMilestones.ClientsReady`, when the HTTP clients have started, which leader election waits for.

`Phase` and `Milestone` are interfaces with only a `name`, so an `enum` or an `object` is one with no code; `milestone(name)` makes one that is just a name.

[#tiebreaker]
== Unordered services

Two services in the same phase, with no milestone between them, are unordered.
Bootable may start them in either order, and which it is isn't part of the contract: if the order matters, a milestone is missing.
There is deliberately no priority number to break ties, since a number would be easier to write than the milestone it stands for.

A `StartOrder.Tiebreaker`, given to `Bootable`, decides how ties are broken:

`ByName`, the default::
By `name()`, so the start plan, and the logs, are the same on every run and every machine.
`Shuffled`::
At random, from a seed that is logged with the plan, so a missing milestone that a fixed order would hide shows up, and `Shuffled(seed)` replays the order.

Set it in config, in `boot.service.order`:

[source,hocon]
----
boot.service.order {
  tiebreaker {
    _type = Shuffled  # <1>
    seed = 42         # <2>
  }
}
----
<1> `ByName` if unset; `BOOT_SERVICE_ORDER_TIEBREAKER=Shuffled` as an environment variable.
<2> Optional: replays a logged shuffle; `BOOT_SERVICE_ORDER_TIEBREAKER_SEED=42` as an environment variable.

A good approach is to shuffle in `application-local.conf`, for development, and in the tests' config, where a surprise is cheap, and to keep the default in production, so it starts in the same order on every run.
Kodein's `bootableModule`, Koin's `bootableModule()`, and Metro's `BootableDefaultBindings` read the section when there is a `ConfigBinder`; wired by hand, pass `tiebreaker = serviceOrderConfig(binder).tiebreaker` to `Bootable`, as <<custom>> shows.
A test can check the start plan under many shuffles, without starting anything; see xref:testing:index.adoc#start-plans[the start plan].

[#shutdown]
== Shutdown order

Services stop in the reverse of the start plan, which is what makes the phases useful at shutdown:

. `Serving` stops first, so no new work comes in, and work in flight finishes while what it uses still runs.
. `Application` stops next, once nothing calls into it.
. `Initialization` usually has nothing to stop.
. `Infrastructure` stops next: the pools close once nothing uses them.
. `Telemetry` stops last, so its exporters flush what the other phases recorded as they stopped.

Within a phase, a service stops before the providers of the milestones it waited for.

[#start-plan]
== The start plan

Bootable logs the plan before anything starts, each phase with its services, in order, leaving out empty phases, as for an application with a database and a server:

----
Start plan: Infrastructure[JdbcDataSourceService, ExposedDatabaseService] Initialization[FlywayMigrationService, SchemaVerificationService] Serving[EntryServer]
----

With a shuffled tiebreaker, it names the seed: `Start plan (ties shuffled, seed 42): ...`.

The same computation is a public function, `startPlan(services, startOrder, tiebreaker)`, which returns the services in the order they would start, without starting them.

[#validation]
=== Validation

Bootable computes the plan before any lifecycle controller runs, so a plan that can't be met fails the boot before anything has started.
It lists every problem it finds, such as:

* A service in a phase the start order doesn't have:
+
----
SecretsLoader is in phase Secrets, which is not one of the start order's phases: [Telemetry, Infrastructure, Initialization, Application, Serving]. Pass Bootable a StartOrder that includes Secrets.
----
* A required milestone that no service provides:
+
----
ReportService requires milestone 'db.schema.migrated', but no service provides it. Add a service that provides it, or use 'after' if it is optional.
----
* A milestone whose provider is in a later phase:
+
----
PriceCalculator (Application) must start after 'pricing.rates.loaded', but its provider ExchangeRates is in Serving, which starts later
----
* A cycle, with its path:
+
----
Start-order cycle in phase Application: ExchangeRates (after 'pricing.prices.ready') -> PriceCalculator (after 'pricing.rates.loaded') -> ExchangeRates
----
* A start order that repeats a phase, or whose default phase isn't one of its phases.

== Custom start orders
