= Logging (Log4j2)
:description: Log4j2 to the console, as plain or coloured text, Elastic Common Schema JSON, or Google Cloud's JSON, with structured fields, set up before anything else runs.

`boot-logging-log4j2` makes https://logging.apache.org/log4j/2.x/[Log4j2] the application's logging, with a console appender in one of several output types: coloured or plain text, Elastic Common Schema JSON, or Google Cloud's structured JSON.
It routes the other logging APIs to Log4j2 too: SLF4J, `java.util.logging`, and the standard output and error streams.

`boot { }` initializes logging before anything else, before it builds the application, so config loading and the application's construction log with the chosen output.
Logging isn't a service, and isn't part of the lifecycle; it is set up before the lifecycle begins.

== Modules

`boot-logging` holds `BootLoggingLevel`, the log levels, with no logging library.
It comes with `boot-logging-log4j2`.

modules::logging[]

== Install

`boot` brings `boot-logging-log4j2` at runtime, since `boot { }` initializes it.
Add it as a dependency to use its API in your code: `LoggingType`, `loggingInit`, `StructuredMessage`, and Log4j's Kotlin API.

install::[boot-logging-log4j2]

It has no DI flavours: logging is set up before the application's graph is built, so the wiring is the same in every style.

=== Structured fields

A `StructuredMessage` is a message with typed fields beside its text, for a backend to index and query, such as an order's id and total:

[source,kotlin]
----
include::ROOT:example$vanilla/logging/Logging.kt[tag=fields]
----

The JSON output types write each field as a top-level field of the event, and `message` holds the text alone:

[source,json]
----
{"@timestamp":"2026-11-25T09:30:00.000Z","ecs.version":"1.2.0","log.level":"INFO","message":"order 42 placed","process.thread.name":"main","log.logger":"com.example.Orders","order.id":"42","order.total":1250}
----

A number or a boolean stays a JSON number or boolean; any other value is written as its `toString()`.
A field whose value is `null` is left out.
The text output types write the fields after the text, as `{order.id=42, order.total=1250}`, with the `%fields` pattern converter, which a pattern of your own can use too.

Name the fields as the backend expects them, such as the https://www.elastic.co/guide/en/ecs/current/ecs-field-reference.html[Elastic Common Schema]'s `http.request.method` or `event.duration` for `JSON`.
A field must not have the same name as an existing output field, such as `message`.
The event would then have two fields with that name.
The output types write these fields:

[cols="1,4"]
|===
| Output type | Fields

| `JSON`
| `@timestamp`, `ecs.version`, `log.level`, `message`, `process.thread.name`, `log.logger`, `tags`, `trace.id`, `span.id`, `log.origin.file.name`, `log.origin.file.line`, `log.origin.function`, `error.type`, `error.message`, `error.stack_trace`, and the logging context's keys

| `GCLOUD`
| `timestampSeconds`, `timestampNanos`, `severity`, `message`, `logging.googleapis.com/labels`, `logging.googleapis.com/sourceLocation`, `logging.googleapis.com/trace`, `logging.googleapis.com/spanId`, `logging.googleapis.com/trace_sampled`, `exception`, `thread`, `logger`
|===

The JSON output types write the entries of any of Log4j's map messages this way, such as a `StringMapMessage`.

Fields belong to one event; for fields that every event logged during a request should carry, such as a request id, put them in Log4j's `ThreadContext` instead, with `withLoggingContext` from Log4j's Kotlin API.
`JSON` writes the context's entries as top-level fields too.

==== From a serializable value

`structuredMessageOf`, in `boot-logging-log4j2-serialization`, makes a `StructuredMessage` from a `@Serializable` value, with each of its properties as a field:

[source,kotlin]
----

The event has the fields `refund.orderId`, `refund.amount`, and `refund.reason`.
A nested object's properties are fields too, named with a dot: a `customer` property with an `id` is the field `refund.customer.id`.
A list stays a list, which `JSON` writes as an array.
The `prefix` is optional; without it, the fields are named for the properties alone.
The value is encoded with kotlinx.serialization's `Json`, or with a `json` of your own, so `@SerialName` names a field.

[#output-types]
== Output types

`LoggingType` chooses the output:

[cols="1,3"]
|===
| `LoggingType` | Output

| `DEFAULT`, `COLOR`
| Text, one line for each event, with the level and logger in ANSI colours.
`LOGGING_ANSI_DISABLE=true` turns the colours off.

| `PLAIN`
| The same text, without colours.

| `JSON`
| One JSON object for each event, in the https://www.elastic.co/guide/en/ecs/current/index.html[Elastic Common Schema]: the logging context's entries, and the <<fields,structured fields>>, as top-level fields, and the trace and span from the logging context's `trace_id` and `span_id` as ECS's `trace.id` and `span.id`.

| `GCLOUD`
| One JSON object for each event, in the layout Google Cloud Logging reads as structured logs: the severity in Google Cloud's levels, the trace and span from the logging context's `trace_id` and `span_id`, so Cloud Logging links each event to its trace, and the <<fields,structured fields>> as top-level fields, which Cloud Logging puts in the entry's `jsonPayload`.

| `EMPTY`
| Nothing: every event is discarded.
|===

`DEFAULT` is the type when none is chosen, and is the same output as `COLOR`.

Choose the type, in order of precedence:

. as an argument, `boot(loggingType = ...)`, or `loggingInit(loggingType = ...)`;
. with the `LOGGING_TYPE` environment variable, such as `LOGGING_TYPE=json`, in any case; a value that isn't a `LoggingType` logs a warning, and the default is used;
. or leave it to the default.

[source,kotlin]
----
include::ROOT:example$vanilla/logging/Logging.kt[tag=boot]
----

Choosing the type in the environment lets one build log text on a developer's machine and JSON in production.

== Settings

The output types read these environment variables, or the system properties after them, at the start:

[cols="2,2,1,3"]
|===
| Environment variable | System property | Default | Sets

| `LOGGING_LEVEL`
| `logging.level`
| `info`
| The root logger's level: `trace`, `debug`, `info`, `warn`, `error`, `fatal`, or `off`.

| `LOGGING_ANSI_DISABLE`
| `logging.ansi.disable`
| `false`
| Whether `COLOR` and `DEFAULT` leave out the colours.

| `LOGGING_LOCATION_ENABLED`
| `logging.location.enabled`
| `false`
| Whether `JSON` and `GCLOUD` record each event's source location, its file, method, and line, which is costly.

| `LOGGING_CONSOLE_DIRECT`
| `logging.console.direct`
| `true`
| Whether the console appender writes to the process's standard output directly, rather than through `System.out`.
Leave it on while <<standard-streams,the standard streams are redirected>>; off, the appender can race with the redirection.
|===

An environment variable wins over its system property.

[#levels]
=== Log levels

`LOGGING_LEVEL` sets the root logger's level, which every logger has unless it sets its own.
For the level of one logger, or of a package, add a `log4j2.xml` of your own; see <<your-config>>.

`loggingInit(overrideLoggingLevel = ...)` takes a `BootLoggingLevel` as the default for the root level, in place of `info`; `LOGGING_LEVEL` and `logging.level` still win over it.

[#your-config]
== Your own Log4j2 config

Bootable's config for the output type is the base, and merged over it, if they are on the classpath, are:

. `log4j2-<type>.xml`, for one output type only, such as `log4j2-json.xml`;
. `log4j2.xml`, for every type.

Each is a Log4j2 configuration that adds to the base or changes it, such as a logger's level.
The base's appender is named `Console`, so a logger can refer to it:

[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="error">
  <Loggers>
    <Logger name="com.example.orders" level="debug" additivity="false">
      <AppenderRef ref="Console"/>
    </Logger>
    <Logger name="org.eclipse.jetty" level="warn"/>
  </Loggers>
</Configuration>
----

`loggingInit(allowMerging = false)` uses the base alone.
To replace Bootable's config altogether, set the `log4j.configurationFile` system property: Bootable sets it only when it isn't set.

[#standard-streams]
== Standard output and error

Once logging is initialized, what is written to `System.out` is logged by the `STDOUT` logger at `INFO`, and what is written to `System.err` by the `STDERR` logger at `WARN`, so a library that prints rather than logs still logs in the chosen output.

Logging is initialized once: a second call to `loggingInit`, such as the one `boot { }` makes, does nothing.
So an application that calls `loggingInit` before `boot { }`, to pass a level or turn off the redirection, gets its own settings.

== Example

`examples/wiring-vanilla`, `examples/wiring-kodein`, `examples/wiring-koin`, and `examples/wiring-metro` each have a `log4j2.xml` that sets Bootable's own loggers to `info`, merged over the base.
From the repository root, run one with JSON output:

[source,shell]
----
LOGGING_TYPE=json ./gradlew :examples:wiring-vanilla:run
----
