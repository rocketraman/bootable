= Scheduled tasks (db-scheduler)
:description: db-scheduler's persistent tasks, recurring and one-time, over the application's database, run once across its instances.

`boot-scheduler-db` runs https://github.com/kagkarlsson/db-scheduler[db-scheduler] over the application's database, with `DbSchedulerService`.
Its tasks, recurring and one-time, are kept in a table, so they survive restarts, and run once across all the application's instances: each execution runs on whichever instance locks its row first.
So, unlike a periodic loop, a task needs no leader election.

The service builds db-scheduler's `Scheduler` over ``boot-db-jdbc``'s `DataSource`, and starts and stops it with the application.
It is in the `Serving` phase, after the `DbMilestones.SchemaMigrated` milestone, so it starts once its table is migrated and the services its tasks use have started, and stops before them.
Creating it opens no connection.

== When to use it

Use a task for work that must happen once, at a time or on a schedule, such as a reminder an hour from now, or a nightly report, and that must not be lost when the application restarts.
Use a xref:periodic.adoc[periodic loop] for work that polls, such as sending what is pending: it runs in the process, needs no table, and runs on every instance, or, with its leader gate, on one.

=== Task data

A task's data, of the class given to its task, such as `Tasks.oneTime("send-reminder", Reminder::class.java)`, is stored as JSON with kotlinx-serialization, by `KotlinxSerializationTaskDataSerializer`, rather than with db-scheduler's default Java serialization.
The data's class must be `@Serializable`, and can't be generic: wrap a `List<String>` in a class of its own.
A subclass of a sealed `@Serializable` type is stored with its discriminator, and must have a `@SerialName`, so that renaming or moving it doesn't strand the data already stored.
Unknown keys are ignored, so an older instance reads data that a newer one wrote.

For a recurring task whose schedule is chosen at runtime, `Tasks.recurringWithPersistentSchedule`, a `SerializableSchedule` (`Cron`, `FixedDelay`, or `DailyAt`) is stored with the data: implement `PersistentScheduleData` in the data's class.

[#table]
== Its table

The module ships db-scheduler's table as a Flyway migration for PostgreSQL, MySQL 8 (and MariaDB), and SQLite.
Add its location to xref:database:flyway.adoc[Flyway]'s `locations`, alongside your own, which then need naming too:

[source,hocon]
----
db {
  flyway {
    locations = ["classpath:db/migration", "classpath:bootable/db-scheduler/postgresql"]
  }
}
----

The locations are `classpath:bootable/db-scheduler/postgresql`, `…/mysql`, and `…/sqlite`.
Each holds a repeatable migration, `R__bootable_db_scheduler.sql`, whose statements are all idempotent (`CREATE TABLE IF NOT EXISTS`), rather than a versioned one, whose version could clash with the application's own, or be out of order in a database that already has later ones.

It creates the table as `scheduled_tasks`, db-scheduler's default, with its `priority` column.
With another `tableName`, or for another database, create the table with a migration of your own, from db-scheduler's DDL in its repository.

Flyway reaches `DbMilestones.SchemaMigrated`, so the scheduler starts once the table exists.

== Configure

`DbSchedulerConfig` reads `db.scheduler`.
Every setting is optional, and an unset one keeps db-scheduler's default:

[source,hocon]
----
db.scheduler {
  threads = 5                     # <1>
  pollingStrategy = LockAndFetch  # <2>
  shutdownMaxWait = 20s           # <3>
}
----
<1> Caps how many tasks execute at once on this instance, such as to leave the pool connections for the application's requests; 10 by default.
<2> Fetches and locks the due executions in one statement, `SELECT … FOR UPDATE SKIP LOCKED`, for fewer statements on PostgreSQL, MySQL 8, and the other databases that support it.
`Fetch`, the default, works on every database.
<3> Lets shutdown finish within the platform's limit.
db-scheduler's default is 30 minutes, longer than most platforms wait for a process to stop, such as Kubernetes's 30 second grace period: set it to fit.

The others include `pollingInterval`, 10 seconds by default, `immediateExecution`, to run an execution scheduled for now at once rather than at the next poll, `heartbeatInterval`, `missedHeartbeatsLimit`, `deleteUnresolvedAfter`, `tableName`, `schedulerName`, `priority`, `dialect`, and `persistTimestampsInUtc`: see kdoc:boot-scheduler-db:com.github.rocketraman.bootable.scheduler.db.DbSchedulerConfig[all the settings].
The SQL dialect, `dialect`, is `Auto` by default: from the database's JDBC URL when the service is given it, as the DI flavours do, or else detected from the database when the scheduler starts.

For a db-scheduler setting `DbSchedulerConfig` doesn't cover, such as a `SchedulerListener`, an `ExecutionInterceptor`, or another serializer, add a `DbSchedulerCustomizer`, which adjusts db-scheduler's `SchedulerBuilder` after the typed settings, to its set binding, or, with vanilla wiring, pass one to `DbSchedulerService`.

== Readiness

`DbSchedulerHealthCheck` is a readiness check that the scheduler is running: started, and neither paused nor shutting down.
It is opt-in, since readiness that depends on the scheduler takes the instance out of rotation when it isn't running, which helps only when the application's requests depend on its tasks.
Add it to the checks of `HealthLifecycleController`, import `dbSchedulerHealthCheckModule` with Kodein, or name `DbSchedulerHealthCheckBindings` in the graph's `bindingContainers` with Metro.

[#telemetry]
== Telemetry

`boot-scheduler-db` can make each execution a trace of its own, with `dbSchedulerTracing`, a `DbSchedulerCustomizer`: a root span named for the task, such as `db-scheduler send-reminder`, so that the execution's queries and log events belong to it.
The span carries the task's name, the instance's id, and how many executions of it in a row failed before, as `bootable.db_scheduler.task`, `bootable.db_scheduler.instance`, and `bootable.db_scheduler.consecutive_failures`.

The span covers the execution's completion too, such as the statement that deletes a one-time execution's row or reschedules a recurring one.
An execution that fails ends its span with an error status and the exception recorded, before db-scheduler's failure handler reschedules it.
db-scheduler's own statements, such as its polls for due executions and its heartbeats, run outside any execution, so, with xref:database:index.adoc#telemetry[statement tracing], each is still a trace of its own.

It depends only on the OpenTelemetry API, through xref:telemetry:index.adoc#spans[`boot-telemetry-otel-common`]; the application's SDK, such as xref:telemetry:index.adoc[`boot-telemetry-otel`]'s, records the traces.
