= Periodic work
:description: PeriodicAppService: a loop in the background, gated on the leader or the application's health, with a trace for each run.

`boot-periodic` provides `PeriodicAppService`, the loop that an application would otherwise write by hand: every few seconds or minutes, send the notifications that are pending, or sweep what has expired.
The application writes only the work.

It is in the `Serving` phase by default, as something that brings work into the application, so it starts after the services its work uses, and stops before them.

Each run starts a fixed delay, the `interval`, after the previous run ends, so runs never overlap, and a run that takes longer than the interval delays the next rather than piling up behind it.

== Configure

Each loop has a config section of the application's choosing, decoded as a `PeriodicConfig`.
Every setting has a default, so the section is optional:

[source,hocon]
----
notifications.loop {
  interval = 5s                # <1>
  runTimeout = 1m              # <2>
  maxConsecutiveFailures = 10  # <3>
  onFailureLimit = Shutdown    # <4>
}
----
<1> Sets how often the loop runs: the delay between one run's end and the next one's start, so runs never overlap; a minute by default.
<2> Cancels a run that hangs, such as on a call that never returns, and counts it as a failure; no limit by default.
<3> Gives up on a loop that keeps failing, such as on a record that fails every run, rather than failing forever; no limit by default.
<4> Stops the application, with exit code 1, once it gives up, by failing the service's scope, so that its platform restarts it, or an operator notices.
The default, `StopLoop`, stops the loop and logs an error, while the rest of the application runs on.

The others are `enabled`, `initialDelay`, before the first run, and `shutdownTimeout`, how long shutdown waits for a run in progress before cancelling it, 10 seconds: see kdoc:boot-periodic:com.github.rocketraman.bootable.periodic.PeriodicConfig[all the settings].

[#gates]
== Gates

Before each run, the loop asks its `PeriodicGate`, and skips the run when the gate is closed; it asks again an interval later.

* `PeriodicGate.Always`, the default, is always open: every instance runs the loop.
* `PeriodicGate.leader(leaderElection)` is open while this instance is the xref:leader.adoc[leader], so only one instance runs the loop; for a leader that pauses, a run that writes sends its xref:leader.adoc#fencing[fencing token] with each write.
* `PeriodicGate.running(health)` is open while the application is running: once every service has started, and until shutdown begins.
A loop in the `Serving` phase starts with the last services to start, so this holds its runs back only until the others in that phase, such as the HTTP server, have started too.
* `and` combines two gates: open when both are.

----

----

A gate that closes while a run is in progress, as the leader gate does when this instance stops leading, cancels the run, which isn't counted as a failure.
Cancellation is cooperative: work that blocks, such as a JDBC call, stops only at its next suspension point, unless it blocks in `runInterruptible`.

A gate of your own is a `fun interface`: `isOpen()` must return promptly, without blocking.
A gate that can close during a run says so by overriding `awaitClosed()`, which suspends until it closes.

== Failures

A run that throws is handed to the loop's `PeriodicFailureHandler`, and the loop carries on, unless `maxConsecutiveFailures` runs in a row have failed.
The default handler, `PeriodicFailureHandler.Log`, logs the failure as an error.
A handler of your own runs on the loop's coroutine, so it must return promptly; what it throws is logged.

[source,kotlin]
----
include::ROOT:example$vanilla/background/Periodic.kt[tag=failure]

A run the gate skips neither fails nor succeeds, and a run that `runTimeout` cancels fails.
`maxConsecutiveFailures` guards against a poison pill, such as a record that fails every run, which would otherwise fail forever.

== Start and shutdown

The loop's first run is `initialDelay` after it starts.
On shutdown, it starts no further run, and doesn't wait for the interval: it waits up to `shutdownTimeout` for a run in progress to finish, and then cancels it.

To run a loop in another phase, or after a milestone, pass its `ordering`.

[#telemetry]
== Telemetry

`boot-periodic` can make each run a trace of its own, with `periodicTracing`, a `PeriodicRunInterceptor`: a root span named for the loop, such as `periodic notifications`, so that the run's queries and log events belong to it.
The span carries the loop's name as `bootable.periodic.service`, and a run that fails ends it with an error status and the exception recorded.
A run the gate skips isn't traced.

It depends only on the OpenTelemetry API, through xref:telemetry:index.adoc#spans[`boot-telemetry-otel-common`]; the application's SDK, such as xref:telemetry:index.adoc[`boot-telemetry-otel`]'s, records the traces.

=== Sampling, or no tracing

Each run's trace is sampled as the SDK's sampler decides, such as at the configured `sampleRatio`.
For a loop that runs rarely enough that every run's trace is worth keeping, sample them all with `Sample.Always`.
