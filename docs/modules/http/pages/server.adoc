= Server (Ktor)
:description: A Ktor server that starts and stops with the application, on the engine of your choice, traced and measured.

`boot-server-http-ktor` runs a Ktor server as one of the application's services: `KtorService` starts the server when the application starts, and stops it when it stops.
It configures Ktor only as far as the server's address and its shutdown; the plugins and routes are the application's own.

A `KtorService` is in the `Serving` phase, so it starts once the services it uses have started, and stops first, so requests in flight can finish.
It runs in the scope its `start(scope)` gets, and keeps it as `scope`, so a route that finds the server can't go on fails it, with `scope.launch { throw e }`, which xref:concepts:lifecycle.adoc#failure[stops the application], with exit code 1.

== Install

Add an engine's module, which brings `boot-server-http-ktor` and the engine with it, here CIO.
With a DI, add `boot-server-http-ktor` too, for its flavour, which provides `KtorHealth`, and the engine module's flavour, which provides the engine of the <<listener-engine,listeners of their own>>.

install::[boot-server-http-ktor, boot-server-http-ktor-cio]

[#engines]
== Engines

`boot-server-http-ktor` depends on no engine.
Choose one, by its module and the service class you extend:

[cols="2,2,3",options="header"]
|===
| Module | Extend | Engine

| `boot-server-http-ktor-cio` | `CioKtorService` | Ktor's CIO: pure Kotlin, on coroutines, with no native transport, and the engine to use for a GraalVM native image.
| `boot-server-http-ktor-netty` | `NettyKtorService` | Netty.
|===

Any other engine, such as Jetty, works too: depend on `boot-server-http-ktor` and the engine, and extend `KtorService` with the engine's factory, as `KtorService<MyEngine, MyEngine.Configuration>("my-server", config, MyEngine)`.

[#listener-engine]
=== The engine of the listeners

The listeners that modules start on their own, those of the xref:health.adoc#listener[health probes] and the <<scrape,metrics scrape>> when their `hostPort` is set, run on the application's `KtorServerEngine`.
Each engine module's flavour provides one, for its engine:

* With Kodein, import `ktorServerCioEngineModule`, from `boot-server-http-ktor-cio-kodein`, or `ktorServerNettyEngineModule`, from `boot-server-http-ktor-netty-kodein`.
* With Koin, include `ktorServerCioEngineModule()`, from `boot-server-http-ktor-cio-koin`, or `ktorServerNettyEngineModule()`, from `boot-server-http-ktor-netty-koin`.
* With Metro, `boot-server-http-ktor-cio-metro` or `boot-server-http-ktor-netty-metro` contributes it.
* With Inara, compose `ktorServerCioEngineModule()`, from `boot-server-http-ktor-cio-inara`, or `ktorServerNettyEngineModule()`, from `boot-server-http-ktor-netty-inara`, as the `KtorServerEngineModule`, which the Inara health and telemetry modules require, or `NoKtorServerEngineModule` for none.

Use one engine module's flavour: two would be two bindings of `KtorServerEngine`.
For any other engine, bind your own, such as `KtorServerEngine(Jetty)`.
An application that serves its probes and scrape on its own server needs no `KtorServerEngine`; one with a `hostPort` set, and no engine, fails to start, and says so.
With vanilla wiring, there is no `KtorServerEngine`: give the engine to each `listener` itself.

=== Engine options

Every engine is configured the same way: one connector, at the service's `HostPort`, a shutdown grace period of 50 ms, and a shutdown timeout of 1 s.

[#telemetry]
== Telemetry

`boot-server-http-ktor-otel` adds `KtorTelemetry`, which installs OpenTelemetry's Ktor server instrumentation in the server.
It traces every request, continuing the caller's trace when the request carries one, and records the standard HTTP server metrics, such as `http.server.request.duration`.
For a pulled metrics backend, such as Prometheus, it also serves the scrape.
It reports through the application's OpenTelemetry SDK, from xref:telemetry:index.adoc[`boot-telemetry-otel`], which it brings in.

=== Settings

`KtorTelemetryConfig` reads `telemetry.ktor`; every setting is optional:

[source,hocon]
----
telemetry.ktor {
  hostPort = ":9090"                       # <1>
  capturedRequestHeaders = [X-Request-Id]  # <2>
}
----
<1> Keeps the metrics scrape off a public server, on a listener of its own that only the scraper reaches; see <<scrape>>.
Unset, the scrape is served on the application's server.
<2> Records these request headers on each request's span, as `http.request.header.<name>`, so a trace can be found by a value the caller sent.

The others are `path`, the scrape's path, `/metrics` by default, and `capturedResponseHeaders`, recorded as `http.response.header.<name>`: see kdoc:boot-server-http-ktor-otel:com.github.rocketraman.bootable.server.http.ktor.KtorTelemetryConfig[all the settings].

For an instrumentation setting the config doesn't cover, such as a span's name or extra attributes, add a `KtorServerTelemetryCustomizer` to its set binding (Kodein `inBindSet`, Koin a definition with a qualifier of its own, Metro `@IntoSet`), or, with vanilla wiring, pass one to `KtorTelemetry`.

[#scrape]
=== The metrics scrape

With a pulled backend, such as `boot-telemetry-otel-prometheus`, `installTelemetry` serves its scrape at `/metrics` on the application's server, in the format the request's `Accept` header prefers.
With no pulled backend, there is no scrape route.

A public server would serve the metrics to anyone, so to keep them off it, set `telemetry.ktor.hostPort`.
The scrape is then served on a listener of its own, a `MetricsKtorService`, on a port that only the scraper reaches.
With Kodein or Koin, `ktorTelemetryModule` adds it to the application's services, with Metro, `boot-server-http-ktor-otel-metro` does, and with Inara, `ktorTelemetryModule()` does, on the <<listener-engine,application's engine>>.
With vanilla wiring, add `KtorTelemetry.listener(engine)` to the application's services yourself, such as `telemetry.listener(CIO)`.
Without `hostPort`, the listener is a service that does nothing, and needs no engine, so it can be added either way.
Like any `KtorService`, the listener is in the `Serving` phase, so a scrape in flight at shutdown is still answered; it isn't traced.

=== Traces without the probes and scrapes

The platform's probes, and Prometheus's scrapes, would fill the traces with requests nobody wants to see.
The DI flavours keep both out of the traces: the scrape at `telemetry.ktor.path`, and the probes at the paths of `health.ktor`, when they are served on the application's server.
With vanilla wiring, add `excludeScrapeFromTraces()` and `excludeHealthFromTraces()` to ``OpenTelemetryService``'s customizers, as below.
