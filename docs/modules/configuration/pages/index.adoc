= Configuration
:description: Typed config classes, bound from HOCON and the environment by Hoplite, with secrets masked.

An application's config is a set of typed classes, each bound from a section of the config by a `ConfigBinder`.
`boot-config-common` defines the `ConfigBinder`, which Bootable's own modules read their config with, and `boot-config-hoplite` implements it with https://github.com/sksamuel/hoplite[Hoplite], from HOCON files, system properties, and the environment.

Config isn't a service, so it has no lifecycle phase of its own.
It is bound while the application is built, in the `boot { }` block, which runs after logging is initialized, so a config error is logged, and fails the start before any service starts.

== Modules

An application adds the config library, `boot-config-hoplite`.
`boot-config-common` comes with it, and with every module that reads config.

== Configure

Hoplite reads these sources, each overriding the ones below it:

. Environment variables, such as `GREETING_MESSAGE` for `greeting.message`; see <<environment-variables>>.
. System properties with the `config.override.` prefix, such as `-Dconfig.override.greeting.message=hi`.
. `~/.userconfig.conf`, in the user's home directory, and `$XDG_CONFIG_HOME/hoplite.conf`, if they exist.
. `application-local.conf`, on the classpath, if it exists: for settings on a developer's machine, kept out of version control.
. `application.conf`, on the classpath, which must exist.

Each config class reads one section, named by its path:

[source,hocon]
----
greeting {
  message = "hello from Bootable"
  apiKey = ${?GREETING_API_KEY}  # <1>
}

server {
  host-port = ":8080"  # <2>
}
----
<1> From the environment variable, if it is set; see <<substitutions>>.
<2> A key matches its property in any case, and with or without dashes, so `host-port`, as here, and `hostPort`, as the property is spelled, are the same key.

=== Config classes

A config class is a data class, with a property for each key in its section.
A property with a default, or a nullable one, is optional; any other fails the bind when its key is missing.

`HostPort`, from `boot-config-common`, is a `hostPort` string, such as `localhost:8080` or `:8080`, with helpers to read it: `host()`, which defaults to `0.0.0.0`, `port(default)`, `portOrNull()`, and `inetAddress()`.
The Ktor server takes its address as a `HostPort`.

Hoplite decodes the usual types: strings, numbers, booleans, durations such as `5s`, lists, sets, maps, and nested data classes.
An enum value matches its entry's name in any case, so `fail`, `Fail`, and `FAIL` are all `Fail`.
A sealed type is chosen by its subtype's name, in a `_type` key next to the subtype's properties, such as `tiebreaker { _type = Shuffled, seed = 42 }`.

[#secrets]
=== Secrets

The config classes of Bootable's own modules declare a secret, such as a password, an API key, or an auth header, as `Masked`, from `boot-config-common`.
Their config classes depend only on `boot-config-common`, not on a config library, so they can't use the library's own type for secrets.
A ``Masked``'s `toString` is `+****+`, so a config class that holds one prints safely; read the secret with `value`.
`boot-config-hoplite` decodes a `Masked` from a string or a number.

In your own config classes, declare a secret with Hoplite's `Secret`, as `GreetingConfig.apiKey` does above.
Bootable doesn't aim to make config libraries interchangeable, so `Masked` is for its own modules.

[#report]
=== The config report

When it binds a section, `boot-config-hoplite` prints a report of the section's keys, each with its value and where it came from, and the keys in it that its config class doesn't read.
It prints to standard output, which Bootable xref:logging:index.adoc#standard-streams[logs], once logging is initialized.
The report masks these values:

* a `Masked` value, wherever it is: in a data class, a map, or a list;
* a Hoplite `Secret`;
* a value whose name contains `secret`, `credential`, or `pass`;
* a value its source marks as a secret.

The report shows values as they were loaded, before Hoplite's resolvers run, so it shows `${{ env:DB_PASSWORD }}`, not the password.
Turn it off with `report = false`; see <<customize>>.

[#environment-variables]
=== Environment variables

An environment variable overrides the key whose path it spells, in upper case, with `_` in place of each `.`: `GREETING_MESSAGE` sets `greeting.message`.
A camel case key is spelled without a separator: `DB_POOL_MAXIMUMPOOLSIZE` sets `db.pool.maximumPoolSize`.

An environment variable overrides a map entry, or a property of one, keeping the entry's key as config spells it.
With `http.client.named.myClient { baseUrl = "http://localhost:8001/" }` in config, `HTTP_CLIENT_NAMED_MYCLIENT_BASEURL=http://localhost:8002/` changes the `baseUrl` of the `myClient` client, rather than adding a client named `MYCLIENT`.
An entry that only the environment defines is keyed as the environment variable spells it, in upper case.

[#substitutions]
=== Substitutions

A value can name an environment variable, or another value, in two ways.

HOCON's own substitutions work anywhere, in maps and lists too, and are resolved when HOCON parses the file:

[source,hocon]
----
db.jdbc.dataSourceProperties {
  sslmode = ${?DB_SSLMODE}  # <1>
}
greeting.message = ${app.name}  # <2>
----
<1> The environment variable, if it is set; without it, the key is left unset, so a property with a default keeps it.
`+${DB_SSLMODE}+`, without the `?`, fails the parse when the variable isn't set.
<2> Another value in the config.

Hoplite's resolvers name an environment variable, a system property, or another value, with a fallback if you like:

[source,hocon]
----
db.jdbc {
  host = "${{ env:DB_HOST }}"
  port = "${{ env:DB_PORT:-5432 }}"  # <1>
  username = "${{ sysprop:db.user }}"
  database = "${{ ref:app.name }}"
}
----
<1> The fallback, after `:-`, when the variable isn't set.

A resolver that resolves to nothing, and has no fallback, fails the bind, even for a property with a default.
A resolver works only in a property whose value is a single string, which can then be decoded as another type, such as the `Int` port above.
In the entries of a map, a list, or a set, it is left as literal text: use HOCON's `${?VAR}` there.

Hoplite's older preprocessor syntax, `+${VAR}+` in a quoted string, or `+{{key}}+`, is not expanded, and is left as literal text.

=== Bootable's own config

Each Bootable module reads its own section, such as `db` for the database, `http.client` for the HTTP clients, `telemetry` for OpenTelemetry, or `env` for the environment.
A module's page shows its section; xref:database:index.adoc#_configure[the database's], for example.
With a DI, a module's bindings bind its config from the graph's `ConfigBinder`; wired by hand, you bind it, and pass it to the module's constructor.

Bootable itself reads two optional sections, if there is a `ConfigBinder`: `boot.service.order`, how services the start order leaves tied are started, and `health.readiness`, the readiness checks' settings.

[#customize]
== Customize the binder

`hopliteConfigBinder` takes optional parameters:

* `withConfigStage1`, `withConfigStage2`, `withConfigStage3`: hooks on Hoplite's `ConfigLoaderBuilder`, to add sources, resolvers, or anything else.
Sources added in stage 1 override the environment variables; in stage 2, they are between the user settings and `application-local.conf`; in stage 3, below `application.conf`.
Hoplite's modules for secret stores, such as Vault, AWS Secrets Manager, GCP Secret Manager, and Azure Key Vault, add their resolvers this way, with `addResolver`.
* `decoders`: Hoplite decoders for your own types, which can also be registered with Java's `ServiceLoader`.
* `report`: whether to print <<report,the config report>>; `true` by default.
* `secretsPolicy` and `obfuscator`: which values the report masks, and how; Hoplite's `StandardSecretsPolicy` and `StrictObfuscator` by default.
A `Masked` value is masked whatever the policy.
* `strict`: fail a bind when its section has a key the config class has no property for; `false` by default.
* `environmentVariables`: the environment variables, for the environment variable source and `${{ env:VAR }}`; `System.getenv()` by default.
HOCON's own `${?VAR}` substitutions read the process environment, not these.
