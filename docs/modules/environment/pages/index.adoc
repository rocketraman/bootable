= Environment
:description: The deployment environment, such as dev, test, or prod, from config, in a global variable.

`boot-env` sets a global variable, `environment`, to the environment the application is deployed in: `Env.Dev`, `Env.Test`, `Env.Prod`, or `Env.Custom` with any other name.
It reads it from the `env.environment` config key.

WARNING: Over-using this is a code smell.
Code that asks which environment it runs in rather than reading a setting from config is harder to reason about, and can have unintended consequences.

Use it rarely for cross-cutting concerns where sharing a configuration setting would be invasive, or for environment-specific config too complex to express in the xref:configuration:index.adoc[config classes].
For example:

* Tagging metrics, traces, or logs with the environment.
* Refusing to start in `Env.Prod` with settings meant only for development, such as a default password, TLS turned off, or a SQLite database.
A flag in the config couldn't guard against these, since a config that is wrong for prod would be as likely to have the flag wrong too.

`environment` is set by a lifecycle controller, `EnvironmentInitializer`, in its `appInit`, which runs once the application is built, before any service starts.
It has the highest priority, so it runs before every other controller's `appInit`.
Read `environment` from a service's `start`, or later; read while the application is being built, such as in a constructor or a config binding, it isn't set yet, and throws.

== Install

install::[boot-env]

`boot-env` reads its config with a `ConfigBinder`, such as xref:configuration:index.adoc[`boot-config-hoplite`]'s.

== Configure

[source,hocon]
----
env {
  environment = prod  # <1>
}
----
<1> `dev`, `test`, or `prod`, in any case, or any other name, which is an `Env.Custom` of that name.
The key is required.

As an environment variable, it is `ENV_ENVIRONMENT=prod`.
