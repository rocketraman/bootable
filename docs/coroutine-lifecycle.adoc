= Design note: a coroutine lifecycle
:toc: macro

Status: *proposed*, for 3.1.
It follows rocketraman/bootable#96, which fixed a stop that deadlocked when it came before the run thread waited for one; this replaces the hand-off that race was in.

toc::[]

== Problem

`Bootable.run` is thread-based.
It starts the services on the calling thread, then blocks in `awaitTermination()` on a queue that `appTerminate(exitCode)` feeds.
Four callers stop the application, from four kinds of thread:

* the stop signal handler, on the JVM's signal thread;
* the JVM shutdown hook, on a shutdown-hook thread;
* `AdvancedAppService`'s `die` callback, on whatever thread the service noticed its failure on, such as a Ktor request's or a coroutine's;
* a lifecycle controller's `normalStop`, on any thread, including the run thread itself, while it starts.

A `java.util.Timer` per path (`AppStartStopLifecycleController` at shutdown, `Bootable.die` for a dying service) calls `Runtime.halt` when the stop takes too long.

That model has costs:

* The hand-off between those threads and the run thread is hand-written, and it was wrong: #96's race.
* Services that are coroutine-based anyway call `runBlocking` to start or stop: `KubernetesLeaderElection` and `PeriodicAppService` in their `shutdown`, `SeedEntriesService` in its `start`.
  Each builds its own `CoroutineScope`, `SupervisorJob` and `CoroutineExceptionHandler`, outside any structure, and each must remember to cancel it.
* Background work that fails has two ways to say so, `die` or a log line, and neither is structured: nothing stops a scope a service forgot to cancel.
* Halting skips the JVM's shutdown hooks, so an asynchronous logger can lose the very log lines that say why the stop hung.
* The tests of draining and stopping wait in real time and poll (`awaitCondition`, `Thread.sleep`), with tolerances.

== Goals

* `run` is a suspending function that waits for one stop, and returns the exit code.
* Starting and stopping a service suspend, so a service that is coroutine-based calls its suspending code directly.
* The whole lifecycle runs under structured concurrency: a service's background coroutines are children of the application's scope, a failure among them stops the application, and none outlives it.
* Every way to stop is one thread-safe, non-blocking call, from any thread, at any time, the first of which wins.
* The tests of the lifecycle's timing run in virtual time.

Non-goals: restarting an application, or starting and stopping single services at runtime (a custom `LifecycleController` can still do that through `ServiceContext`); suspending health checks (see <<health>>).

== Decisions

=== 1. The stop signal: a `CompletableDeferred<Int>`

[source,kotlin]
----
private val stopRequested = CompletableDeferred<Int>()

/** Asks the application to stop with [exitCode]. Thread-safe, never blocks, and only the first call counts. */
fun stop(exitCode: Int = 0) {
  if (stopRequested.complete(exitCode)) log.info { "=> Stop requested, exit code $exitCode" }
}
----

`complete` is lock-free and returns at once, from any thread, before or after `run` waits, so the four callers above all call it, and #96's race can't arise: there is no hand-off to miss.
It returns `false` to every call after the first, which is the "first stop wins" rule #96 introduced, without an `AtomicBoolean` beside it.

A `Channel` or a `Flow` would model a stream of stops, and nothing needs more than one.
A second stop, such as a second Ctrl-C while the application stops, changes nothing today, and should change nothing here: the shutdown timeout, not a second signal, bounds a stop that hangs.
Should someone later want "a second signal halts at once", the signal handler can do that itself, by seeing that `stop` had been called already.

`run` waits with `stopRequested.await()`.
`normalStop` in `LifecycleController.appStart` and the stop signal handler keep their plain `(exitCode: Int) -> Unit` type, which is `::stop`: the signal thread can't call a suspending function, and needn't.

==== A stop during the start cancels the start

Today a stop that comes while the services start is held until they have all started (#96), and only then stops them.
With a deferred, `run` can do better: it races the start against the stop, and a stop cancels the start.

[source,kotlin]
----
val started = coroutineScope {
  val start = async { appStart(timeline) }
  select {
    start.onAwait { true }
    stopRequested.onAwait { start.cancelAndJoin(); false }
  }
}
----

A service starting at that moment sees a `CancellationException` at its next suspension point; one blocked in plain blocking code, such as a Flyway migration in `withContext(Dispatchers.IO)`, finishes that call first (see <<dispatchers>>).
Then the services that started stop, in reverse, as after a failed start, and `run` returns the stop's exit code.
That matters for an application whose start waits, such as on a database that isn't up yet: today a SIGTERM to it waits for the database, or for Kubernetes's SIGKILL.

#96's regression test keeps passing unchanged in meaning: a controller that stops the application during its start stops it with that exit code, and the services that started stop.

=== 2. The entry point: `boot { }` stays, and `suspend fun run()` becomes public

[source,kotlin]
----
fun boot(maxShutdownTime: Duration = 30.seconds, loggingType: LoggingType? = null, bootable: () -> Bootable) {
  // ...logging, building the application, as today
  val exitCode = runBlocking { application.run(timeline, maxShutdownTime, hook = true) }
  exitProcess(exitCode)
}

class Bootable(...) {
  /** Runs the application until it stops, and returns its exit code. It can be run once. */
  suspend fun run(maxShutdownTime: Duration = 30.seconds): Int

  fun stop(exitCode: Int = 0)
}
----

`boot` remains what a `fun main() = boot { ... }` calls: it blocks the main thread in `runBlocking`, and exits the process with the code `run` returns.

`run` and `stop` become public.
`run` neither exits the process, nor installs the shutdown hook, nor halts; it only runs the application, so a test, or a host that embeds an application, such as a test harness or an IDE plugin, runs one with `run` in a coroutine and stops it with `stop`, or by cancelling that coroutine, which stops the application, as a stop with exit code 1 would.
That is the seam that rocketraman/bootable#84 first added as `runEmbedded` and then dropped; here it is just the API, so it needs no opt-in annotation.
A test of an application's wiring needn't use it, and its documentation says so, so it doesn't invite booting whole applications in unit tests.

The shutdown hook moves from `run` to `boot`, which owns the process.
It calls `stop(0)` and then waits for `run` to return, up to the shutdown timeout, rather than returning at once and letting the JVM exit under the services as they stop.

`maxShutdownTime` becomes a `Duration`, rather than a `Long` of seconds; 3.1 already breaks the API.

=== 3. The suspending lifecycle API: change the interfaces in place

*Recommendation: (a), make the existing interfaces `suspend`.*

[source,kotlin]
----
interface AppService {
  fun name(): String = javaClass.simpleName
  suspend fun start() {}
  suspend fun shutdown() {}
  fun ordering(): Ordering = Ordering()
}

interface LifecycleController {
  fun name(): String = javaClass.simpleName
  fun appInit() {}
  suspend fun appStart(serviceContext: ServiceContext, normalStop: (exitCode: Int) -> Unit) {}
  suspend fun aroundAppStart(serviceContext: ServiceContext, timeline: StartupTimeline, start: suspend () -> Unit) = start()
  fun serviceStartVote(appService: AppService): ServiceStartVote = ServiceStartVote.YES
  suspend fun aroundServiceStart(appService: AppService, start: suspend () -> Unit) = start()
  suspend fun appShutdown(serviceContext: ServiceContext, maxShutdownTime: Duration) {}
  suspend fun appCleanup() {}
  fun priority() = 0
}

data class ServiceContext(
  val appServices: Set<AppService>,
  val startPlan: List<AppService>,
  val serviceStart: suspend (appService: AppService) -> Unit,
  val serviceShutdown: suspend (appService: AppService) -> Unit,
)
----

What stays plain, and why: `name`, `ordering`, `priority` and `serviceStartVote` are queries, called while planning, and shouldn't do IO.
`appInit` stays plain too: it runs before anything starts, to set state, as `EnvironmentInitializer` does.
`appShutdown` loses its `exitProcess` callback, since controllers no longer halt (see <<forced-shutdown>>).

The options:

(a) Change the interfaces in place::
One API, and every implementation changes by adding `suspend` to its overrides, which the compiler finds for it.
A service with nothing to suspend on still compiles once `suspend` is added: a suspending function may call only blocking code.
Java can't implement a `suspend` function (it sees a `Continuation` parameter), so a Java service would need a Kotlin adapter.
No implementer here, in the examples, or in the applications we know of is in Java.

(b) Add suspending interfaces beside the blocking ones, and adapt::
`SuspendingAppService`, `SuspendingLifecycleController`, and adapters that run a blocking one in `withContext(Dispatchers.IO)`.
Nothing breaks, and Java keeps working, but every concept exists twice, the documentation explains both, every module picks one, and Bootable runs both.
The blocking interfaces would be deprecated at once, since nothing would need them, so (b) defers (a)'s break by a release, at the cost of carrying both until then.

3.1.0 is unreleased and already breaks the API (`priority()` became `ordering()`, Kotlin 2.3), so 3.1 is the cheapest release to break it again, and applications migrate once.

A blocking adapter is still worth a few lines, for Java, and its documentation:

[source,kotlin]
----
/** An [AppService] whose start and stop block, run on [Dispatchers.IO]: for Java, or code that only blocks. */
abstract class BlockingAppService : AppService {
  abstract fun startBlocking()
  abstract fun shutdownBlocking()
  final override suspend fun start() = withContext(Dispatchers.IO) { startBlocking() }
  final override suspend fun shutdown() = withContext(Dispatchers.IO) { shutdownBlocking() }
}
----

It is optional; I'd add it only if Raman wants Java implementers supported.

[#die]
=== 4. `die` under structured concurrency: a service scope

*Recommendation: `AdvancedAppService.start` gets a `ServiceScope`, a `CoroutineScope` that is a child of the application's, with `die`.*

[source,kotlin]
----
interface AdvancedAppService : AppService {
  @Deprecated("AdvancedAppService starts with start(scope)", level = DeprecationLevel.HIDDEN)
  override suspend fun start() {}

  /**
   * Starts the service. [scope] lives until the service has stopped: launch the service's background work in it.
   * If a coroutine in it fails, the application stops with exit code 1.
   */
  suspend fun start(scope: ServiceScope)
}

interface ServiceScope : CoroutineScope {
  /** Stops the application with [exitCode], such as because this service can't go on. Never blocks. */
  fun die(exitCode: Int = 1)
}
----

The scopes are layered:

[source]
----
run()                      the lifecycle: start, wait, stop, on the caller's thread (main, under boot)
└─ application scope       SupervisorJob + Dispatchers.Default + a handler that logs and calls stop(1)
   ├─ service scope (A)    Job + CoroutineName(A)
   │  ├─ A's coroutine
   │  └─ A's coroutine
   └─ service scope (B)    Job + CoroutineName(B)
----

* The application scope is a `SupervisorJob`, so that one service's failing coroutine doesn't cancel every other service's at once.
  The application stops in order instead, phase by phase in reverse, each service's `shutdown` running while what it depends on still runs, as with any other stop.
  Its handler logs the failure and calls `stop(1)`.
* Each service scope is a plain `Job`, a child of that supervisor: a failing coroutine cancels its siblings in the same service, which is broken now, and only them.
  Its exception goes to the application's handler, so it stops the application with exit code 1.
* After a service's `shutdown` returns, Bootable cancels its scope and joins it.
  A service whose background work is all in its scope needn't track, cancel or join its jobs: `PeriodicAppService` and `KubernetesLeaderElection` drop their scopes, handlers and `cancel` calls.
  A service that wants to finish its work gracefully, as `PeriodicAppService` lets a run finish, still does so in `shutdown`, before the scope is cancelled.
* `die(exitCode)` is `stop(exitCode)`, with a log line naming the service.
  It is for a service that notices it can't go on outside its scope, such as in a Ktor request handler; inside its scope, a service just throws.
* A service's scope doesn't carry the context its start ran in, such as the start's span: background work isn't part of the start.

What a failure means for the exit code:

[cols="3,1", options="header"]
|===
| What happened | Exit code
| A stop signal, or `stop()` | 0
| `stop(n)`, `normalStop(n)`, `die(n)` | n
| A coroutine in a service's scope failed | 1
| `run`'s own coroutine was cancelled, such as by an embedding host | 1
| A service failed to start | -1 (as today)
| The stop timed out (see <<forced-shutdown>>) | 1, whatever the stop asked for
|===

The first stop wins, so a failure while the application already stops changes no exit code; it is logged.
An exception from a service's `shutdown` is logged and ignored, as today.

Alternatives:

* A `SupervisorJob` per service too: a failing coroutine would leave its sibling coroutines running, in a service that might be half broken. A service that wants that, such as one running independent jobs, makes its own `supervisorScope` inside its scope.
* A plain `Job` for the application scope: a failure would cancel every service's background work at once, before any `shutdown` ran, so services would stop with their work already gone, and out of order.
* A `die` callback alone, without a scope: leaves services building unstructured scopes, as today.

[#forced-shutdown]
=== 5. Forced shutdown: a timeout that cancels, then a halt as the last resort

*Recommendation: the stop runs in `NonCancellable`, under a timeout that cancels it; if the stop doesn't return a short grace after that, a watchdog thread halts the process.*

[source,kotlin]
----
// in AppStartStopLifecycleController.appShutdown, after Health's drain, as today
val stopped = withTimeoutOrNull(maxShutdownTime) {
  serviceContext.startPlan.asReversed().forEach { serviceContext.serviceShutdown(it) }
}
if (stopped == null) log.warn { "Services didn't stop within $maxShutdownTime; cancelled the rest: $notStopped" }
----

[source,kotlin]
----
// in Bootable.run: the stop isn't cancelled by run's own cancellation, so an embedding host that cancels run
// still gets the services stopped
withContext(NonCancellable) {
  withHaltingWatchdog(maxShutdownTime + HALT_GRACE) { appShutdown(maxShutdownTime); appCleanup() }
}
----

In order:

. At `maxShutdownTime` after the services begin to stop (after the drain, as today), the timeout cancels the stop.
  The service stopping at that moment is cancelled: one that suspends, such as Ktor's `stopSuspend` or a join, returns at once.
  The services not yet stopped are skipped, and logged by name, along with the thread stacks, as the timer logs them today.
  Cleanup still runs, and `run` returns exit code 1, so `boot` exits the process through `exitProcess`: the JVM's shutdown hooks run, so an asynchronous logger flushes, and the stacks we just logged reach the log.
. A service blocked in code that ignores cancellation, such as a blocking call in `withContext(Dispatchers.IO)` or a `Thread.sleep`, doesn't return when cancelled, and `withTimeout` waits for it.
  So a watchdog, armed when the stop begins, on a daemon thread of its own rather than a coroutine, halts the process with exit code 1 if `run` hasn't returned `HALT_GRACE` (say 5 seconds) after the deadline.
  It is a thread so that it fires even when the service blocks the thread the lifecycle runs on.
  It logs the thread stacks before it halts, as today.
. The `die` path's separate 30-second timer goes away: `die` is a stop like any other, and the same timeout applies.
  A stop during a start that is blocked (see <<_a_stop_during_the_start_cancels_the_start>>) is bounded by the same watchdog, armed when the stop is asked for during the start.
. An embedding host, without `boot`, has no process to halt: `run` takes the halt as an internal parameter, which `boot` sets to `Runtime.halt`, and which is otherwise a log line, after which `run` returns 1 and leaves the blocked thread behind.

The drain stays outside the timeout, as `ReadinessConfig.drainDelay` documents, so the platform's grace period must still cover both.

Alternative: halt at the deadline, as today, without cancelling first.
It is simpler, but every hung stop loses the asynchronous logs, and skips the cleanup of the services that would have stopped.

[#dispatchers]
=== 6. Blocking work, and the dispatchers

*Recommendation: services wrap blocking calls in `withContext(Dispatchers.IO)`; `runInterruptible` only where an interrupt is known to be harmless.
The lifecycle runs on the thread that calls `run`; background work runs on `Dispatchers.Default`.*

The lifecycle (start, wait, stop) runs on the caller's thread: under `boot`, `runBlocking`'s event loop on the main thread.
That is one thread, so starts and stops run in order on it as today, and a service that forgets `withContext` and blocks works as today, only blocking the lifecycle, which waits for it anyway.

The application scope, and so every service scope, runs on `Dispatchers.Default`, not on that thread: background work must not queue behind a start or stop that blocks the main thread.
A service that wants another dispatcher launches with it, as `PeriodicAppService`'s `dispatcher` parameter does.

`withContext(Dispatchers.IO)`, not `runInterruptible`, by default, because interrupting a thread in JDBC or NIO code is not a cancellation:

* An interrupt during NIO IO closes the channel, which, in a JDBC driver, closes the connection, and HikariCP evicts it, or worse, sees it half-used.
* Interrupting Flyway mid-migration can leave a non-transactional migration (MySQL DDL) half applied.
* `Thread.sleep`, `Object.wait` and the like are where an interrupt is harmless, and the modules here have none in their starts or stops.

So a blocking start or stop ignores cancellation; the shutdown watchdog bounds it.

[#context]
=== 7. Context propagation: OpenTelemetry, and log4j's `ThreadContext`

OpenTelemetry's current `Context` is thread-local.
`ServiceStartTracing` today makes the span current with `span.makeCurrent().use { start() }`, which only works if `start` returns on the thread it began on.
A suspending start may resume on another thread, such as after `withContext(Dispatchers.IO)`, where the span isn't current, and the `Scope` would be closed on a thread it wasn't opened on.

So `ServiceStartTracing` puts the span in the coroutine context instead, with `opentelemetry-extension-kotlin`, already an `api` dependency of `boot-telemetry-otel`:

[source,kotlin]
----
override suspend fun aroundServiceStart(appService: AppService, start: suspend () -> Unit) {
  // the parent is the current context, which the `start application` span's context element made current
  val span = tracer.spanBuilder("start ${appService.name()}").startSpan()
  try {
    withContext(Context.current().with(span).asContextElement()) { start() }
  } catch (e: Throwable) {
    span.recordException(e); span.setStatus(StatusCode.ERROR); throw e
  } finally {
    span.end()
  }
}
----

`asContextElement()` makes the context current on every thread the coroutine resumes on, including inside `withContext(Dispatchers.IO)`, which inherits it.
The `start application` span is carried the same way, so each service's start span is its child.
The log4j context-data instrumentation reads the current context on each log call, so a service's log lines during its start keep their trace and span ids, on any thread.

`SeedEntriesService` in the `server-ktor-db` example carries the span itself today, `runBlocking(Context.current().asContextElement())`; with this, it becomes `override suspend fun start()`, and inherits it.

log4j's `ThreadContext` (MDC) is thread-local too, but nothing in Bootable sets it: the trace ids come from OpenTelemetry's context-data provider, not from `ThreadContext`.
An application that sets `ThreadContext` around a start would use log4j-api-kotlin's `CoroutineThreadContext` itself; Bootable needs nothing for it.

[#health]
=== 8. Health

`Health`'s drain `Thread.sleep(drainDelay)` becomes `delay(drainDelay)`, so it is virtual in tests, and cancellable.
Its `aroundAppStart` and `appShutdown` become `suspend`; the `LifecycleState` transitions are unchanged, including that a cancelled start, like a failed one, goes from `Starting` to `Stopping` without draining.

`HealthCheck.check()` stays blocking: `KtorHealth` already runs readiness in `withContext(Dispatchers.IO)`.
Making it `suspend` is a separate change, which would let a check call a suspending client with a timeout.

Optionally, `Health.state` can become backed by a `StateFlow<LifecycleState>`, so a test or a host awaits a state, rather than polling it as `HealthTest` and `KtorHealthTest` do.

=== 9. Migration

`boot` takes `kotlinx-coroutines-core` as an `api` dependency, since its API now has `suspend` functions and `CoroutineScope`; today only `boot-common` has it, as `implementation`.
Its tests take `kotlinx-coroutines-test`.

| `SchemaVerificationService` (`boot-db-exposed`)

| `DbSchedulerService` (`boot-scheduler-db`)
| `start`: `withContext(Dispatchers.IO)` around detecting the database and `scheduler.start()`.

| `PeriodicAppService` (`boot-periodic`)
| Already coroutine-based, it becomes a child of the application's scope: `start(scope)` launches its loop in `scope`, with its `dispatcher`, and it drops its own `SupervisorJob`, handler and `cancel`.
`shutdown` signals the loop and joins it within its own `shutdownTimeout`, without `runBlocking`; Bootable cancels what remains.
`FailureLimitAction.Shutdown` calls `scope.die()`.
A run's failure is still the run's, handled by its `PeriodicFailureHandler`, not the scope's: only an error that escapes the loop, such as a `VirtualMachineError`, fails the scope, and stops the application.

| `KubernetesLeaderElection` (`boot-leader-k8s`)
| Becomes an `AdvancedAppService`: `start(scope)` makes the first attempt directly, without `runBlocking`, then launches the election loop in `scope`.
`shutdown`: cancels and joins the loop, then releases the lease, without `runBlocking`.
Today a loop that fails unexpectedly makes the instance stop leading and leaves the application running; to keep that, the loop catches its own failure, rather than failing the scope.
Whether it should rather stop the application is worth deciding separately: an instance that can never lead again is arguably broken.

| `OpenTelemetryService` (`boot-telemetry-otel`)
| `shutdown`: `withContext(Dispatchers.IO)` around `sdk.shutdown().join(timeout)`.

| The examples: `GreetingService` (the `wiring-*` examples), `ReadyFileService` (`start-order`), `SsrRenderer` (`kilua`), `SeedEntriesService` (`server-ktor-db`)
| `override suspend fun`; the file IO of `ReadyFileService`, and `SeedEntriesService`'s repository, in `withContext(Dispatchers.IO)`.
`SeedEntriesService` drops its `runBlocking` and its explicit OTel context (see <<context>>).
|===

The Kodein modules and Metro bindings bind the same types, so they don't change.

==== Applications

The changelog's migration note, under the breaking changes:

* Add `suspend` to the overrides of `AppService.start` and `shutdown`, and of the `LifecycleController` hooks.
* Wrap blocking calls in them in `withContext(Dispatchers.IO)`; replace `runBlocking` in them with direct calls.
* Replace `AdvancedAppService.start(die)` with `start(scope)`: launch background work in `scope` rather than in a scope of the service's own, and call `scope.die()` for `die()`.
* `boot(maxShutdownTime = 30)` becomes `boot(maxShutdownTime = 30.seconds)`.
* A controller's `appShutdown` no longer gets an `exitProcess` callback.

=== 10. Testing

`kotlinx-coroutines-test`'s `runTest` runs `run` in virtual time, with `StandardTestDispatcher`, so the lifecycle's timing becomes exact and instant:

[source,kotlin]
----
test("readiness is down for the drain delay before the services stop") {
  runTest {
    val health = Health(config = ReadinessConfig(drainDelay = 5.seconds))
    val app = Bootable(setOf(service), setOf(AppStartStopLifecycleController(), health))
    val running = async { app.run() }
    runCurrent()
    assert(health.state == LifecycleState.Running)
    app.stop()
    advanceTimeBy(5.seconds - 1.milliseconds); runCurrent()
    assert(health.state == LifecycleState.Stopping && !service.stopped)
    advanceTimeBy(1.milliseconds); runCurrent()
    assert(service.stopped)
    assert(running.await() == 0)
  }
}
----

Which tests become deterministic:

[cols="3,4", options="header"]
|===
| Test today | In virtual time

| `HealthTest`: "readiness is down for the drain delay…", which sleeps 300 ms and allows 50 ms of slack
| Asserts the drain to the millisecond, as above, in no real time.

| `HealthTest`'s `runApp` and `Stopper`, which run the application on a thread and poll `awaitCondition` for `Running`
| `async { app.run() }`, `runCurrent()`, `app.stop()`: no thread, no polling.

| `BootableTest`: #96's "a stop asked for before the application waits for one…", which joins a thread for up to 10 s
| `stop(5)` during the start, then `run()` returns 5; the stop before `run`, during the start, while running, and twice, each a test of a few lines, none of which can hang the suite.

| None today: the shutdown timeout, which tests set to 1,000,000 s to stay away from
| A service whose `shutdown` is `awaitCancellation()`: at exactly `maxShutdownTime` the stop is cancelled, the rest skipped, and `run` returns 1.
The halt watchdog is a real thread, so its test injects the halt, with a short real timeout and a service that blocks in `Thread.sleep`.

| `KtorHealthTest`'s drain, against a real server
| Still real time, since Ktor's engine runs on real threads; awaits the `Stopping` state rather than polling, if `Health` exposes a `StateFlow`.

| `PeriodicAppService`'s tests, which run the loop on real dispatchers with `eventually`
| Can run the loop in a `runTest` scope's virtual time, by passing its scheduler's dispatcher; a separate change, not needed here.
|===

A test that boots a real server, a database, or Kubernetes's fake API server stays in real time: virtual time only skips `delay`, not IO.

== Summary of the decisions for Raman

. *3, the API:* change `AppService`, `AdvancedAppService` and `LifecycleController` to `suspend` in place, in 3.1, rather than adding suspending interfaces beside them.
  Optionally add a `BlockingAppService` adapter for Java.
. *4, `die`:* `AdvancedAppService.start(scope: ServiceScope)`; the application scope a `SupervisorJob` whose handler stops with exit code 1, each service's scope a plain `Job` under it, cancelled after its `shutdown`; `scope.die(exitCode = 1)` for a stop from outside the scope.
. *5, forced shutdown:* the timeout cancels the stop at `maxShutdownTime` (after the drain), skipping the services not yet stopped, and `run` returns 1, so the process exits normally and its logs flush; a watchdog thread halts only if the stop is still blocked a grace (5 s) later.
. Smaller ones, each recommended above: a stop during the start cancels the start (1); `run` and `stop` are public, and the shutdown hook moves to `boot` and waits for the stop (2); `maxShutdownTime` becomes a `Duration` (2).
