= Changelog

== 3.1.0 (unreleased)

=== Kotlin 2.3 or later

Bootable's modules are compiled for Kotlin API 2.3, rather than 2.1, so an application needs Kotlin 2.3 or later: Bootable supports the last two Kotlin versions.
The Metro flavors already required it.

=== Service start order: phases and milestones replace priorities

Services no longer order themselves with a global `priority()` number.
Each service declares an `ordering()`: a *phase*, and, within that phase, the *milestones* it provides and starts after.
Bootable computes a start plan from them before anything starts, logs it, and fails the boot if it can't be met.
See link:docs/service-ordering.adoc[Service ordering] for the design.

* Services start phase by phase, in the order `Telemetry`, `Infrastructure`, `Initialization`, `Application`, `Serving`, and stop in the reverse order.
`Telemetry` holds what everything else records into, so it starts first and stops last, and exports what the other phases record while they stop.
A service that declares nothing is in `Application`.
* `Ordering(phase, provides, after, requires)` orders a service within its phase against a `Milestone`, a role, rather than against another module's classes or numbers.
`after` is satisfied when nothing provides the milestone; `requires` fails the boot then.
* A `StartOrder`, passed to `Bootable`, defines the phases and how each service's ordering is read, so an app can add phases, replace them, or place a service it didn't write.
The default is `DefaultStartOrder`.
* Services left unordered start in the order of a `StartOrder.Tiebreaker`: `ByName` (the default), or `Shuffled(seed)`, which surfaces missing milestones and logs its seed.
`boot.service.order.tiebreaker._type = Shuffled` in config (or `BOOT_SERVICE_ORDER_TIEBREAKER=Shuffled`) shuffles them, e.g. in `application-local.conf` or test config, and `boot.service.order.tiebreaker.seed` replays a logged shuffle; `ServiceOrderConfig` holds these settings.
* `startPlan(services, startOrder, tiebreaker)` computes the order, so tests can check it.
A plan that can't be met throws a `StartOrderException` listing every problem: an unknown phase, a missing required milestone, a milestone provided in a later phase, or a cycle.
* `boot-db-jdbc` adds `DbMilestones.DataSourceReady` and `DbMilestones.SchemaMigrated`.
`boot-db-exposed`'s schema verification starts after `SchemaMigrated`, so it works with any migration module, or none.

==== Breaking changes

* `AppService.priority()` is removed.
Replace each `override fun priority()` with an `override fun ordering()`: a phase for a service that must start early or late, and a milestone where its order against another service in the same phase matters.
Services that only differed by priority within a phase now start by name.
* An app service that started before the database pool, with a priority above `JdbcDataSourceService.PRIORITY`, now starts after it unless it declares `DefaultPhase.Infrastructure`, or a phase of its own ahead of it.
* An app service that tied with `KtorService` at `Int.MIN_VALUE` now starts before it unless it declares `DefaultPhase.Serving`.
* The `PRIORITY` constants of `JdbcDataSourceService`, `FlywayMigrationService`, `ExposedDatabaseService`, and `SchemaVerificationService` are removed.
* `ServiceContext` has a new `startPlan` property, the services in start order, and its constructor takes it after `appServices`.
A custom `LifecycleController` that sorted `appServices` by `priority()` should iterate `startPlan`, and `startPlan.asReversed()` to stop.
* `Bootable` takes optional `startOrder` and `tiebreaker` arguments.
With Kodein, `bootableModule` uses `StartOrder` and `StartOrder.Tiebreaker` bindings if there are any, and otherwise reads the tiebreaker from the `boot.service.order` config section if there is a `ConfigBinder` binding; with Metro, `BootableDefaultBindings` does the same, with all three as optional bindings.
* `boot` now depends on `boot-config-common`, as an API dependency, for `ServiceOrderConfig`.

`LifecycleController.priority()` is unchanged.

`LifecycleController.aroundAppStart(serviceContext, timeline, start)` runs code around the application's start, which starts every service, and `aroundServiceStart(appService, start)` around each service's start, the highest-priority controller's outermost; the defaults run the start alone.
The `StartupTimeline` marks when the boot began and its stages before the services start: with `boot`, initializing the JVM classes for logging and configuration (setting up logging and running the `boot` lambda), planning the start, and initializing.

=== Telemetry with OpenTelemetry

New modules record traces and metrics with the OpenTelemetry SDK, tied to the application lifecycle; see the Telemetry section of the README.

* `boot-telemetry-otel`: `OpenTelemetryService` builds the SDK from `telemetry.sdk`, exports over OTLP, and, in the `Telemetry` phase, shuts down last, exporting what is still buffered.
Log events within a span carry its trace and span ids, which `boot-logging-log4j2`'s layouts print.
`OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_EXPORTER_OTLP_ENDPOINT`, and `OTEL_EXPORTER_OTLP_HEADERS` fill in what `telemetry.sdk` leaves unset.
* `boot-telemetry-otel-prometheus`: Prometheus export, and its scrape.
Its exemplars carry only the trace and span ids, within OpenMetrics's 128-character limit for an exemplar's labels.
* `boot-telemetry-otel-gcp`: GCP resource detection, and authenticated OTLP export to Google Cloud Trace and Cloud Monitoring.
* `boot-telemetry-otel-signoz`: OTLP export to SigNoz, authenticated for SigNoz Cloud, optionally with delta temporality.
* `boot-telemetry-otel-micrometer-bridge`: a Micrometer `MeterRegistry` that records into the SDK.
* `boot-server-http-ktor-otel`: traces and measures a Ktor server's requests, and serves the metrics scrape, on the server or a listener of its own.
* `boot-db-pool-hikari-otel`: records HikariCP's pool metrics through the application's OpenTelemetry, as a `HikariConfigCustomizer` the Kodein and Metro flavors add to the pool's customizers.
* `boot-telemetry-otel` adds `ServiceStartTracing`, a lifecycle controller that traces the application's start as one trace: a root span, from when `boot` was called until the application is running, with a span for each service's start, and what it does as it starts, such as a migration's queries, within that.
Kodein's `serviceStartTracingModule` and Metro's `ServiceStartTracingBindings`, named in the graph, add it.
* `ServiceStartTracing` records each stage of the `StartupTimeline` as a span under the root, and `OpenTelemetryService`'s sampler always samples the start's trace, whatever `sampleRatio` is.
* `withRootSpan(name, sample = Sample.Always)` always samples the trace it starts too: a root span with the `ALWAYS_SAMPLE` attribute, `bootable.sample.always`, is always sampled.
* `OpenTelemetryService` and `ServiceStartTracing` take a `kotlin.time.Clock`, `Clock.System` by default, which the SDK and the root span take their time from; with Kodein and Metro, a `Clock` binding, if there is one.
* `boot-db-jdbc-otel`: traces each JDBC query as a client span, under the span current where it runs, such as a request's, as a `DataSourceWrapper` the Kodein and Metro flavors add to `boot-db-jdbc`'s wrappers.
`jdbcTracing`'s `configure` lambda, Kodein's `jdbcTracingModule { ... }`, or a Metro `JdbcTelemetryConfigurer` binding changes the instrumentation's defaults.
`JdbcDataSourceService` takes the `DataSourceWrapper`, as its third argument; Kodein's `jdbcDataSourceModule` and Metro's `JdbcDataSourceBindings`, now an interface, collect a set of them.
* `boot-client-http-ktor-otel`: traces and measures each HTTP client request, as a child of the span current where the call is made, and carries the trace to the server called in a `traceparent` header, as a `KtorClientCustomizer` the Kodein and Metro flavors add to the clients' customizers.

=== HTTP clients (Ktor)

New modules provide the application's Ktor `HttpClient`s, tied to the application lifecycle; see the Client HTTP section of the README.

* `boot-client-http-ktor`: `KtorClientService` builds a default client, and any number of named ones, from `http.client`, and closes them, and their engines, when the application stops.
It is in the `Infrastructure` phase, so the services that make calls stop before the clients close, and provides `HttpClientMilestones.ClientsReady`.
* Each client's typed settings, `KtorClientConfig`: a base URL, connect, request and socket timeouts, default headers, retries through Ktor's `HttpRequestRetry`, and TLS material for mutual TLS, a key store and a trust store, each inline as base64 or from a file, the trust store as PKCS12, JKS, or PEM certificates.
A named client takes what it leaves unset from the default client.
A module can contribute a named client's default settings with `KtorClientDefaults`, which the application's config overrides.
* Retries are only of transient failures: a 5xx, 408 or 429 response, a timeout, or a failed connection, and only of idempotent methods unless configured otherwise.
`HttpStatusCode.isTransient()` and `Throwable.isTransient()` give the same classification to an application's own retries.
* The engine is the application's choice, through a `KtorClientEngine`: `CioClientEngine` (`boot-client-http-ktor-cio`), or `JavaClientEngine` (`boot-client-http-ktor-java`).
One that returns Ktor's `MockEngine` answers the clients' requests in a test, with no other change to the wiring.
* `KtorClientCustomizer`, a set binding, installs whatever else the application wants in each client, such as `ContentNegotiation`.

=== Liveness and readiness from the lifecycle

`boot` adds `Health`, a lifecycle controller that tracks the application's `LifecycleState`, `Starting`, `Running`, `Stopping`, and `Stopped`, and answers liveness and readiness from it; see the Health section of the README.

* Liveness is up until the application has stopped, and runs no checks.
* Readiness is up only while the application is running, from when every service has started until shutdown begins, and its `HealthCheck`s all pass.
* `health.readiness.drainDelay` (`ReadinessConfig`) waits, with readiness down, before the services stop, so load balancers stop routing first.
None by default.
* With Kodein, `bootableModule` binds `Health`, adds it to the lifecycle controllers, and opens a `Set<HealthCheck>`; with Metro, `BootableDefaultBindings` does the same, and `BootableGraph` has a `healthChecks` multibinding.
* `boot-db-jdbc` adds `JdbcHealthCheck`, which checks that a connection from the pool is valid, opt-in through Kodein's `jdbcHealthCheckModule` or Metro's `JdbcHealthCheckBindings`.
* `boot-server-http-ktor` adds `KtorHealth`, which serves liveness at `/health/live` and readiness at `/health/ready`, `200` or `503`, on the application's server or on a listener of their own, from the `health.ktor` config section (`KtorHealthConfig`).
It now has Kodein and Metro flavors, `boot-server-http-ktor-kodein` and `boot-server-http-ktor-metro`, which provide `KtorHealth`.
* `boot-server-http-ktor-otel` adds `KtorHealthConfig.excludeHealthFromTraces()`, which its Kodein and Metro flavors add to the SDK's customizers, so the probes aren't traced.

=== Periodic work, and leader election

New modules run periodic background work, on the elected leader only if you like; see the Periodic work and leader election section of the README.

* `boot-periodic`: `PeriodicAppService` runs a suspending function every `interval`, a fixed delay apart, on a coroutine of its own, in the `Serving` phase.
A run that fails is logged, or handed to a `PeriodicFailureHandler`, and the loop carries on, up to `maxConsecutiveFailures` runs in a row, after which it stops, or shuts the application down.
A `PeriodicGate`, such as `PeriodicGate.leader(leaderElection)` or `PeriodicGate.running(health)`, decides whether each run happens; the leader gate cancels a run in progress when this instance stops leading.
Shutdown waits up to `shutdownTimeout` for a run in progress, and then cancels it.
Each loop's settings are a `PeriodicConfig`, decoded from a config section of the application's choosing.
`PeriodicServices` holds what the loops share, for DI: Kodein's `periodicModule` and Metro's `PeriodicBindings` provide it, gated on the `LeaderElection` binding if there is one.
* `boot-periodic-otel`: `periodicTracing` makes each run a trace of its own, through `PeriodicRunInterceptor`, the hook any code can run around each run with.
* `boot-leader`: `LeaderElection`, whether this instance leads, as a `StateFlow<Boolean>`, and `AlwaysLeader`.
* `boot-leader-k8s`: `KubernetesLeaderElection` holds a `coordination.k8s.io/v1` Lease, following client-go's leader election, from the `leader.kubernetes` config section (`KubernetesLeaderElectionConfig`), and releases it on shutdown.
Two pods never lead at once, unless one pauses for longer than the margin between `leaseDuration` and `renewDeadline`: the leader steps down at the renew deadline, timed from when it sent its last renewal, even with a request in flight, and every expiry is timed by the monotonic clock.
It calls the API server's REST API through one of the application's `boot-client-http-ktor` clients, `kubernetes` by default (`leader.kubernetes.httpClient`), rather than a Kubernetes client library, so its TLS and HTTP settings are configured as every other client's are; in a cluster, `kubernetesClientDefaults` defaults that client's trust store to the service account's `ca.crt`, so `leaseName` is the only required setting.

=== Masked config values

`boot-config-common` adds `Masked`, for a config property of a Bootable module that holds a secret, such as a password, an API key, or an auth header.
Those modules' config classes don't depend on a config library, so they can't use Hoplite's `Secret`; an application's own config classes should.
Its `toString` is masked, and `hopliteConfigBinder` decodes it from a string or a number and masks it in its config report, whatever the secrets policy, including in a map, whose values Hoplite's report would otherwise list as unused, in plain text.
The JDBC modules' `password` is `Masked`.

=== Config enum values and sealed subtype names match in any case

`hopliteConfigBinder` matches enum values against the entries' names ignoring case, so `schemaVerification = fail`, `Fail`, and `FAIL` all read the same.
This applies to every enum in config, so config values needn't follow how a Kotlin enum's entries are cased.
Sealed subtype names match ignoring case too, so `Shuffled` and `shuffled` select the same subtype.

=== Environment variables select sealed subtypes

Bootable now uses Hoplite 3.0.7, where an environment variable selects a sealed type's subtype by naming it as the sealed type's own value, since no environment variable can spell `_type`: `_` separates the path.
For example, `tiebreaker { _type = Shuffled, seed = 42 }` in config, or `BOOT_SERVICE_ORDER_TIEBREAKER=Shuffled` and `BOOT_SERVICE_ORDER_TIEBREAKER_SEED=42`.
An environment variable that selects a subtype overrides the one config selects, and config can still set the subtype's properties.
An environment variable that overrides a map entry keeps the entry's key as config spells it, so `DB_JDBC_DATASOURCEPROPERTIES_SSLMODE` overrides `dataSourceProperties.sslMode` without renaming it `SSLMODE`.

=== Config substitutions use Hoplite's resolvers

`hopliteConfigBinder` now substitutes values with Hoplite's resolvers, `${{ context:path }}`, instead of its preprocessors, `${VAR}` and `{{key}}`.
Hoplite has deprecated preprocessors in favour of resolvers since 2023, and its maintainer has confirmed resolvers are the intended default.
Resolvers resolve a value only when it is bound, so a `${...}` elsewhere, such as in an exported shell variable like `PS1`, no longer fails loading.
That makes Bootable's filter of such environment variables unnecessary, so it is removed.

The substitutions map as follows:

[cols="1,1"]
|===
|Preprocessor |Resolver

|`${VAR}` (environment variable or system property)
|`${{ env:VAR }}`, or `${{ sysprop:name }}` for a system property

|`${VAR:-default}`
|`${{ env:VAR:-default }}`

|`{{key}}` or `${key}` (another config value)
|`${{ ref:key }}`

|`${random.int}`, `${random.int(10)}`, `${random.uuid}`, ...
|`${{ random:int }}`, `${{ random:int(10) }}`, `${{ random:uuid }}`, ...
|===

`${{ env:name }}` reads the environment that `hopliteConfigBinder`'s `environmentVariables` supplies, as the environment variables source does.

HOCON's own substitutions, unquoted `${VAR}`, `${?VAR}`, and `${a.b}`, are unaffected: HOCON resolves them when it parses the file, falling back to the environment for `${VAR}` and `${?VAR}`.
They are the recommended way to reference environment variables, and the only one inside maps and lists.

==== Breaking changes

* Preprocessor substitutions are no longer expanded.
They are not an error: a `${VAR}` or `{{key}}` is left in the value as literal text.
That includes a `${VAR}` inside a quoted HOCON string, which Hoplite's preprocessors used to expand and HOCON doesn't.
* A resolver resolves only a data class field whose value is a single string.
A `${{ ... }}` inside a map, list, or set, such as `dataSourceProperties`, Flyway's `placeholders`, `locations`, or `schemas`, or telemetry's `otlp.headers` or `resourceAttributes`, is left as literal text; use HOCON's `${?VAR}` there.
* A `${{ ... }}` that resolves to nothing fails the bind, even in a field with a default value.
Give an optional value a fallback, e.g. `${{ env:DB_HOST:-localhost }}`.
* Hoplite's module resolvers use different names from its module preprocessors: `awssm://` (and `${awssecret:...}`, `secretsmanager://`) is `aws-secrets-manager://`, `azurekeyvault://` is `azure-key-vault://`, and `gcpsm://` is `gcp-secrets-manager://`.
`vault://` and `consul://` are unchanged.
There is no resolver for AWS Parameter Store's `${ssm:key}` or `paramstore://`.
* Hoplite's module resolvers, for Vault, AWS, GCP, Azure, and Consul, can now be added in the `withConfigStageN` hooks with `addResolver`, which used to throw because Bootable had added preprocessors.
A preprocessor added there still runs, but an unresolved substitution is no longer reported, since Hoplite skips that check once there are resolvers.
* The config report shows values before resolvers run, so it shows `${{ env:DB_HOST }}` rather than the value it resolves to.
Resolvers don't mark values as secrets in the report the way some preprocessors did, but since the report shows the expression, it doesn't print the secret either.
* `isKnownNonConfigEnvVar` is removed.

=== A failed start shuts down the services that started

When a service's `start()` throws, Bootable now runs the normal shutdown before exiting with -1, instead of exiting at once.
The services that had started stop in reverse order, so, for example, the database pool is closed.
The service whose `start()` threw is not stopped: if it must release what it acquired, it cleans up before it throws.

==== Breaking changes

* A service is shut down only if its `start()` returned.
Previously Bootable called `shutdown()` on any service that a controller hadn't vetoed, whether or not it had started.
