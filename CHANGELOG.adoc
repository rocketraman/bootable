= Changelog

== 3.1.0 (unreleased)

=== Kotlin 2.3

* Modules target Kotlin API 2.3 (was 2.1), so applications need Kotlin 2.3 or later.

=== Service start order: phases and milestones

See link:docs/service-ordering.adoc[Service ordering].

* Services declare an `ordering()`: a phase, plus the milestones they provide or start after.
* Default phases start `Telemetry`, `Infrastructure`, `Initialization`, `Application`, `Serving`.
* Services stop in reverse phase order; a service that declares nothing is in `Application`.
* `after` a milestone nobody provides is a no-op; `requires` one fails the boot.
* The start plan is logged up front; an unmeetable plan throws `StartOrderException`.
* A custom `StartOrder` can add or replace phases, or place services the app didn't write.
* Unordered services tie-break `ByName` (default) or `Shuffled(seed)`, per `boot.service.order`.
* `startPlan(services, startOrder, tiebreaker)` exposes the computed order for tests.
* `boot-db-jdbc` adds the milestones `DbMilestones.DataSourceReady` and `SchemaMigrated`.
* `LifecycleController` gains `aroundAppStart` and `aroundServiceStart` hooks.
* `StartupTimeline` records when the boot began and its stages before services start.

==== Breaking changes

* `AppService.priority()` is removed; override `ordering()` with a phase or milestone.
* Services that started before the DB pool now start after it unless in `Infrastructure`.
* Services that tied with `KtorService` at `Int.MIN_VALUE` start before it unless in `Serving`.
* The `PRIORITY` constants of the JDBC, Flyway, and Exposed services are removed.
* `ServiceContext` gains `startPlan`; custom controllers iterate it instead of sorting.
* `Bootable` takes optional `startOrder` and `tiebreaker`; Kodein and Metro bind them if present.
* `boot` now has an API dependency on `boot-config-common`.

=== Telemetry with OpenTelemetry

See the Telemetry section of the README.

* `boot-telemetry-otel`: SDK lifecycle and OTLP export, from `telemetry.sdk` and `OTEL_*` vars.
* Log events within a span carry its trace and span ids, printed by `boot-logging-log4j2`.
* `boot-telemetry-otel-prometheus`: Prometheus scrape, with exemplars.
* `boot-telemetry-otel-gcp`: GCP resource detection and export to Cloud Trace and Monitoring.
* `boot-telemetry-otel-signoz`: export to SigNoz, including SigNoz Cloud authentication.
* `boot-telemetry-otel-micrometer-bridge`: a Micrometer `MeterRegistry` backed by the SDK.
* `boot-server-http-ktor-otel`: traces and metrics for Ktor server requests; serves the scrape.
* `boot-client-http-ktor-otel`: traces and metrics for Ktor client calls; sends `traceparent`.
* `boot-db-jdbc-otel`: a client span per JDBC query, through a new `DataSourceWrapper` hook.
* `boot-db-pool-hikari-otel`: HikariCP pool metrics.
* `ServiceStartTracing` traces the application's whole start as one always-sampled trace.
* `withRootSpan(name, sample = Sample.Always)` starts a root span that is always sampled.
* `OpenTelemetryService` and `ServiceStartTracing` take a `kotlin.time.Clock`.

==== Breaking changes

* `JdbcDataSourceService` takes ``DataSourceWrapper``s as its third argument.
* Metro's `JdbcDataSourceBindings` is now an interface.

=== HTTP clients (Ktor)

See the Client HTTP section of the README.

* `boot-client-http-ktor`: `KtorClientService` builds default and named clients from `http.client`.
* Per-client config: base URL, timeouts, headers, retries, and mutual TLS.
* Named clients inherit unset values from the default client.
* Modules can contribute named-client defaults with `KtorClientDefaults`.
* Retries cover only transient failures of idempotent methods, by default; see `isTransient()`.
* Pluggable engine: `boot-client-http-ktor-cio` or `-java`; Ktor's `MockEngine` works in tests.
* `KtorClientCustomizer` installs extra plugins, such as `ContentNegotiation`, in every client.

=== Liveness and readiness

See the Health section of the README.

* `Health` answers liveness and readiness from the lifecycle state and ``HealthCheck``s.
* `health.readiness.drainDelay` holds readiness down for a while before services stop.
* `boot-db-jdbc` adds an opt-in `JdbcHealthCheck`.
* `KtorHealth` serves `/health/live` and `/health/ready`, on the app server or its own listener.
* Health responses carry a JSON body: status and lifecycle state, plus each check for readiness.
* `boot-server-http-ktor` gains `-kodein` and `-metro` flavors.
* `excludeHealthFromTraces()` keeps health probes out of traces.
* `boot-telemetry-otel-common`: `withSpan` and `withRootSpan` over the OpenTelemetry API, without the SDK.
* `BuildInfo`, from the `build` config section, is served at `/health/info`.
* Telemetry's `serviceVersion` defaults to `build.version`.
* `HealthLiveReport`, `HealthReadyReport`, and `BuildInfo` are `@Serializable`, so clients can decode them; `boot` now depends on `kotlinx-serialization-core`.

=== Periodic work and leader election

See the Periodic work and leader election section of the README.

* `boot-periodic`: `PeriodicAppService` runs a suspending function on a fixed delay.
* Failed runs are logged or handled, and stop the loop after `maxConsecutiveFailures`.
* `PeriodicGate` gates runs, e.g. on leadership (cancelling a run on loss) or readiness.
* `PeriodicRunInterceptor` wraps every run; with an `OpenTelemetry`, each run is its own trace.
* `boot-leader-common`: `LeaderElection` as a `StateFlow<Boolean>`, with a fencing token; `AlwaysLeader`.
* `boot-leader-k8s`: Kubernetes Lease leader election, over a `boot-client-http-ktor` client.

=== Scheduled tasks with db-scheduler

See the Scheduled tasks section of the README.

* `boot-scheduler-db`: db-scheduler on `boot-db-jdbc`, running each task once across instances.
* Configured from `db.scheduler`; the SQL dialect is detected from the database.
* Task data is stored as JSON with kotlinx.serialization by default.
* `SerializableSchedule` and `PersistentScheduleData` store a recurring schedule with its data.
* Opt-in `DbSchedulerHealthCheck`.
* Flyway migrations for its table on PostgreSQL, MySQL, and SQLite.
* Kodein and Metro collect tasks from a `Set<DbSchedulerTaskProvider>`.
* With an `OpenTelemetry`, each task execution is its own trace.

=== Test helpers

See the Testing section of the README; the helpers test components without booting the app.

* `boot-test`: `checkShuffledStartPlans` checks start plans under shuffled tiebreakers.
* `captureLogs { … }` captures Log4j2 events, with their structured fields, for assertions.
* `TestClock` is a `kotlin.time.Clock` that tests set and advance.
* `boot-test-otel`: `InMemoryTelemetry` collects recorded spans and metrics in memory.

=== Config

* `Masked` hides secrets in Bootable modules' config; the JDBC `password` is now `Masked`.
* Enum values and sealed subtype names match ignoring case.
* Hoplite 3.0.7: env vars select sealed subtypes, e.g. `BOOT_SERVICE_ORDER_TIEBREAKER=Shuffled`.
* Env var overrides of map entries keep the key's case as config spells it.
* Substitutions use Hoplite's resolvers (`${{ env:VAR }}`) instead of preprocessors (`${VAR}`).
* A `${...}` in an unrelated env var, such as `PS1`, no longer breaks loading.
* HOCON's own `${VAR}` and `${?VAR}` substitutions are unaffected and remain recommended.

==== Breaking changes

* Preprocessor substitutions, `${VAR}` and `{{key}}`, stay literal text; migrate as below.
* Resolvers apply only to single-string fields; use HOCON's `${?VAR}` in maps and lists.
* A resolver that resolves to nothing fails the bind; add a fallback, e.g. `${{ env:X:-y }}`.
* Secret manager prefixes changed, e.g. `awssm://` is now `aws-secrets-manager://`.
* AWS Parameter Store (`${ssm:key}`, `paramstore://`) has no resolver.
* The config report shows `${{ ... }}` expressions, not their resolved values.
* `isKnownNonConfigEnvVar` is removed.

[cols="1,1"]
|===
|Preprocessor |Resolver

|`${VAR}`
|`${{ env:VAR }}` or `${{ sysprop:name }}`

|`${VAR:-default}`
|`${{ env:VAR:-default }}`

|`{{key}}` or `${key}`
|`${{ ref:key }}`

|`${random.int}`, `${random.uuid}`, ...
|`${{ random:int }}`, `${{ random:uuid }}`, ...
|===

=== Experimental Inara bindings

Kodein's authors are sunsetting it in favour of https://kosi-libs.org/inara/[Inara], a compile-time successor run by KSP.
Each module with Kodein bindings now also has experimental Inara bindings, as an `-inara` artifact (`boot-inara`, `boot-db-jdbc-inara`, …), for the application to compose into its own `@DIModule(composed = true)`.
`boot-config-common-inara` adds `ConfigModule`, and `config("prefix")`, which binds a config section in any module that is a `ConfigModule`.
`boot-config-hoplite-inara` adds `HopliteConfigModule()`, a `ConfigModule` that decodes with Hoplite.
An application without config uses the `EmptyConfigModule`, whose `EmptyConfigBinder` fails every read.
The other modules are partial modules, which require the modules they use, and have builder functions named as their Kodein counterparts are, such as `bootableModule()`, `jdbcDataSourceModule(configSource)`, `hikariPoolModule()`, `openTelemetryModule()`, or `ktorClientModule(engine)`.
`boot-inara`'s `BootableModule` provides the `Bootable`, `Health`, and `BuildInfo`, and its `@AppServices`, `@LifecycleControllers`, and `@HealthChecks` sets mark the members it runs; the other modules' sets, such as `@OpenTelemetryCustomizers`, are where Kodein opens one.
`jdbcDataSourceModule` takes a `JdbcConfigSource`, such as `SqliteConfigSource`, and requires a `ConnectionPoolModule`, such as `hikariPoolModule()`.
`boot-telemetry-otel-common-inara` adds `OpenTelemetryApiModule`, which the modules that trace require, with `NoopOpenTelemetryModule` for no telemetry, and `boot-leader-common-inara` adds `LeaderElectionModule`, with `AlwaysLeaderModule`.
See link:docs/wiring.adoc#inara-experimental[Wiring Bootable].

=== Fixes

* A stop requested during the start no longer deadlocks; it takes effect once running.
* A failed start now stops the services that had started, in reverse, before exiting.

==== Breaking changes

* A service is shut down only if its `start()` returned.
