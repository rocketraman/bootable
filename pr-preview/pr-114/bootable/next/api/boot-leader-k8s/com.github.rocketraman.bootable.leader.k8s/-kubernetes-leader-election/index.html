KubernetesLeaderElection

class KubernetesLeaderElection(config: KubernetesLeaderElectionConfig, httpClient: HttpClient, clock: Clock = Clock.System, environment: Map<String, String> = System.getenv()) : AppService, LeaderElection

A LeaderElection among the pods of an application in Kubernetes: the leader is the one that holds a coordination.k8s.io/v1 Lease, as Kubernetes's own controllers elect theirs, following client-go's leader election.

It is an AppService, in the DefaultPhase.Infrastructure phase, so it leads, if it can, before the services that ask it, such as boot-periodic's loops, start, and stops after them. Starting it makes the first attempt to take the Lease, and fails the start if the API server refuses it access (a 401 or 403 status), such as when the pod's service account lacks the permission; it then keeps trying, or renewing, every KubernetesLeaderElectionConfig.retryPeriod in the background, retrying whatever fails. On shutdown it stops, and the leader releases the Lease, so another pod takes over at once. The election runs in the service's scope.

Leadership is conservative, so that two instances never lead at once, as long as neither pauses, such as for a garbage collection, longer than the margin between the lease duration and the renew deadline:

  • A leader stops leading KubernetesLeaderElectionConfig.renewDeadline after it last sent a request that renewed the Lease, even if a request is still in flight then, while another instance takes the Lease only KubernetesLeaderElectionConfig.leaseDuration after it saw the renewal, which was after it was sent.

  • Both are timed by the monotonic clock, and the Lease's own times, by clock, are only informational, so neither the instances' clocks need to agree, nor a clock that jumps elects a second leader.

Within that margin, work that only the leader does must stop once leadership turns false: boot-periodic's PeriodicGate.leader cancels a run in progress then.

The fencingToken covers a pause longer than that margin, where the work writes: it is the Lease's spec.leaseTransitions as of the lease term this instance holds, which each new lease term increments, whether another instance takes the Lease, or this one takes it again after it stopped leading, and which renewals leave as it is. Deleting the Lease starts the count again, at 0, so a store that has seen a higher token would refuse every leader's writes.

It talks to the API server's REST API through httpClient, one of the application's Ktor clients from boot-client-http-ktor, such as the one named by KubernetesLeaderElectionConfig.httpClient, whose TLS settings trust the API server's certificate authority. Each request authenticates with the pod's service account token, read from its file for each request, since Kubernetes rotates it. The service account needs a Role that allows get, create, and update on leases in the coordination.k8s.io API group, in the Lease's namespace.
