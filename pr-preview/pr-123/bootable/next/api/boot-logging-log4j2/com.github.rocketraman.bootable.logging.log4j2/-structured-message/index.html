StructuredMessage

open class StructuredMessage(val text: String, fields: Map<String, Any?>) : MapMessage<StructuredMessage, Any>

A log message with a human-readable text, and typed key/value fields that a log backend can index.

Bootable's JSON layouts write each field as a top-level field of the event, alongside message, which holds only the text. A number or a boolean stays a JSON number or boolean; any other value is written as its toString(). The text layouts write the fields after the text, as {key=value, ...}.

A field whose value is null is left out. Name the fields after the backend's schema, such as the Elastic Common Schema's http.request.method or event.duration, so that it reads them without mapping. A field must not have the same name as a field the layout already writes, such as message or @timestamp. The event would then have two fields with that name. Bootable's logging documentation lists the fields each output type writes.

Log one through Log4j's API, like any other message:

log.info(StructuredMessage("order placed", "order.id" to order.id, "order.total" to order.total))
Content copied to clipboard

Or subclass it for an event of a type of your own, to take the fields from that type:

class OrderPlaced(order: Order) : StructuredMessage(
  "order ${order.id} placed",
  "order.id" to order.id,
  "order.total" to order.total,
  "customer.id" to order.customerId,
)

log.info(OrderPlaced(order))

Log4j's own StructuredDataMessage is for syslog's RFC 5424 structured data, as Log4j's Rfc5424Layout writes it. It needs a structured data id and an event type, limits keys to 32 printable ASCII characters, and holds only strings. Its message is the structured data in syslog's format, type [id key="value" ...] text, so a JSON layout's message holds that rather than the text. For JSON output, use a StructuredMessage: its message is the text alone, and its fields keep their types.
