= Server with a database example

A Ktor server that stores entries in a SQLite database, through a HikariCP pool, Flyway migrations, and Exposed, and traces and measures itself with OpenTelemetry.
Its `GET /relay/{name}` calls the server back through a lifecycle-managed Ktor `HttpClient`, as a call to another service would be made.
It is wired three ways, with the same server and config in `common`: `vanilla`, `kodein`, and `metro`.
`jib` builds the vanilla app into a container image, with its JVM AOT cache in it, and the repository's `server-ktor-db` https://dagger.io[Dagger] module does the same as a CI pipeline.
See the Database, Telemetry, and Client HTTP sections of the link:../../README.adoc[README] for the modules it uses.

== Running it

From the repository root:

[source,shell]
----
./gradlew :examples:server-ktor-db:vanilla:run
----

It serves http://localhost:8001, whose index lists the endpoints.
Store an entry with:

[source,shell]
----
curl -X PUT --data 'hello' http://localhost:8001/entries/greeting
----

Get it back through the HTTP client, which calls `GET /entries/greeting` on the server, as configured under `http.client.named.entries`:

[source,shell]
----
curl http://localhost:8001/relay/greeting
----

The config is in `common/src/main/resources/application.conf`.

=== Health

Liveness is at http://localhost:8001/health/live, and readiness at http://localhost:8001/health/ready, from Bootable's lifecycle: `200` and `UP`, or `503` and `DOWN`, with the lifecycle state and each readiness check.
Readiness is up only while the application is running, and the database answers its check:

[source,shell]
----
curl -i http://localhost:8001/health/ready
----

To see readiness go down before the server stops, set `health.readiness.drainDelay`, e.g. `HEALTH_READINESS_DRAINDELAY=10s`, stop the app with Ctrl-C, and ask for readiness again during the delay.

== Starting faster, with an AOT cache

The `vanilla` app has an `aotCache` task, which runs the installed app once, serving a few requests, to write its JVM AOT cache:

[source,shell]
----
./gradlew :examples:server-ktor-db:vanilla:aotCache
cd vanilla
JAVA_OPTS=-XX:AOTCache=build/aot/vanilla.aot build/install/vanilla/bin/vanilla
----

The `jib` app builds an image with the cache in it, trained in a container of the image itself:

[source,shell]
----
./gradlew :examples:server-ktor-db:jib:jibDockerBuild -PcontainerCli=podman
podman run --rm -p 8001:8001 bootable-examples/server-ktor-db-jib
----

The `server-ktor-db` Dagger module builds the app, trains the cache, and builds the image, each in a container, from anywhere in the repository:

[source,shell]
----
dagger check
dagger api call server-ktor-db image export --path=build/server-ktor-db.tar
podman load -i build/server-ktor-db.tar
----

See Faster Start in the link:../../README.adoc[README] for how it works, what has to match for the JVM to use the cache, and how much faster it starts.

== Seeing it locally

=== Metrics

Metrics are pulled, so they need nothing else running: Prometheus's scrape is at http://localhost:8001/metrics.
After a few requests, it has the server's request metrics, the pool's, the JVM's, and the example's own counter:

[source,shell]
----
curl -s http://localhost:8001/metrics | grep -E 'entries_stored|http_server_request_duration_seconds_count|db_client_connections_usage'
----

=== Traces and metrics, with Grafana

Traces are pushed, so they need somewhere to go; see Push and pull in the link:../../README.adoc[README].
Grafana's `otel-lgtm` image runs everything in one container: an OpenTelemetry collector, receiving OTLP on port 4318, with Prometheus, Tempo for traces, Loki for logs, and Grafana in front of them.

[source,shell]
----
podman run --rm -p 3000:3000 -p 4318:4318 docker.io/grafana/otel-lgtm
----

Then run the example with its OTLP endpoint, exporting metrics every 5 seconds rather than every minute:

[source,shell]
----
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 TELEMETRY_SDK_METRICS_INTERVAL=5s ./gradlew :examples:server-ktor-db:vanilla:run
----

After a few requests, open Grafana at http://localhost:3000, and in Explore:

* choose Tempo, and search for the service `entries`: each request is a trace, such as `PUT /entries/{name}`, with a span for the database operation within it, such as `entries.put`, and a client span for each of its queries within that, such as `INSERT entries.db.entry`, from `boot-db-jdbc-otel`; `GET /relay/{name}` has a client span, `GET`, from `boot-client-http-ktor-otel`, with the server's own `GET /entries/{name}` within it, since the client carries the trace in a `traceparent` header; the application's start is a trace too, `start application`, with a span for each service's start within it, such as `start FlywayMigrationService`, and the migrations' queries within that;
* choose Prometheus, and query the same metrics as the scrape, such as `entries_stored_total`, pushed over OTLP.

Spans are exported in batches, every few seconds, and whatever is still buffered is exported when the example stops.

=== Traces only, with Jaeger

Jaeger takes OTLP directly, and shows the traces at http://localhost:16686:

[source,shell]
----
podman run --rm -p 16686:16686 -p 4318:4318 docker.io/jaegertracing/jaeger:latest
----

Run the example with `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318`, as above.

=== Traces in the logs

Log lines written within a request carry its trace: the console shows `trace_id` and `span_id` among each line's context data, matching the trace in Tempo or Jaeger.
