= Bootable

image:https://img.shields.io/maven-central/v/com.github.rocketraman.bootable/boot[Maven Central,link="https://search.maven.org/search?q=g:com.github.rocketraman.bootable"]
image:https://img.shields.io/github/license/rocketraman/bootable["GitHub license",link="https://github.com/rocketraman/bootable/blob/HEAD/LICENSE"]

A simple, *unopinionated* framework for booting applications.
Intended to be much simpler than Spring Boot or even modern iterations like Quarkus and Micronaut, but still featureful enough to be useful.
Handles stopping, starting, lifecycle management, logging, configuration, and other basic reusable components.

Bootable's core is plain Kotlin and embeds *no* dependency-injection framework.
Its runtime takes two sets — your application services and your lifecycle controllers — and runs them; how you assemble those sets is entirely your choice.
Wire them by hand, use a DI solution provided by Bootable as optional add-on artifacts, or bring your own DI.
Bootable ships optional bindings for https://github.com/kosi-libs/Kodein[Kodein-DI] (clean DSL syntax but executes at runtime) and https://github.com/ZacSweers/metro[Metro] (complex annotation-based syntax, but executes and checks for a valid dependency graph at compile-time).
These are selectable per module, and you can just as easily integrate with any other DI, or none at all.

== Why Not Spring Boot?

An important element of simplicity is to prefer the use of explicit references and configuration.
Spring Boot's runtime discovery and configuration of components and plugins via annotation and reflection is https://www.youtube.com/watch?v=SxdOUGdseq4[easy but not simple].
To use Spring Boot, you have to understand two layers: the libraries underneath Spring, as well as all of Spring Boot's own auto-magic annotations.
Many users of Spring Boot fail to understand the hidden complexities, because they never really understand what Spring Boot's annotations are doing (ever seen `@Transactional` on a `private` method -- it silently does nothing at all, potentially making that code non-atomic).

Bootable aims to be both easy and simple.
The goal of Bootable is to provide a minimal framework for running Kotlin (or Java?) applications, and then gets out of your way.

Useful reading:

* https://dantanner.com/post/spring-rites/[Spring Rites: A caution against annotation-based web frameworks] by Dan Tanner

NOTE: Importing the Metro DI artifact does bring annotations to your application, BUT the annotations are limited to the DI layer — the application's own behavior is not controlled by annotations.

== Features

* Runs a set of application services and lifecycle controllers — assemble them however you like (plain Kotlin, Kodein, Metro, a service loader, …). Bootable embeds no DI framework; optional bindings for Kodein and Metro are available per module. See the `examples/` directory for one project per wiring style.
* Manages the lifecycle of application services.
* Allows registration of lifecycle controllers, which can be used to control the lifecycle of application services in various ways.
The basic built-in implementation of this is the `AppStartStopLifecycleController` which starts application services on app start, and shuts them down on app close, in reverse.
Services start phase by phase (telemetry, infrastructure, initialization, application, serving), and, within a phase, after the milestones they declare; see link:docs/service-ordering.adoc[Service ordering].
Services left unordered start by name, or shuffled with `boot.service.order.tiebreaker._type = Shuffled` in config (or `BOOT_SERVICE_ORDER_TIEBREAKER=Shuffled`).
Shuffling is useful in `application-local.conf` and test config, to surface services that rely on an order they don't declare.
An app can pass its own `StartOrder` to add phases; see link:./examples/start-order[examples/start-order], which adds a phase after `Serving` for a service that announces the app is ready once its server is listening.
Another basic implementation, intended to be used in conjunction with `AppStartStopLifecycleController`, is the `StopSignalHandlerLifecycleController`, which registers signal handlers, which, when received, cleanly shuts the system down.
Other implementations are possible: for example starting/stopping services at runtime based on a command system, like start/stop messages from RPCs or web requests.
A controller can also run code around the application's start, and each service's, by overriding `aroundAppStart` and `aroundServiceStart`, as `ServiceStartTracing` does to trace them.
* Tracks the application's lifecycle state, and answers liveness and readiness from it, with an optional drain delay before shutdown; see <<Health>>.
* Runs periodic background work, on the elected leader only if you like, with leader election through a Kubernetes Lease; see <<Periodic>>.
* Runs persistent scheduled tasks with db-scheduler, once across the application's instances; see <<Scheduler>>.

== Modules

Bootable is modular, and provides a number of modules to help you build your application.
The core module is simply `com.github.rocketraman.bootable:boot`, which provides the basic application lifecycle features of Bootable.
Add additional modules as you wish.

[[Configuration]]
=== Configuration

Bootable's own modules declare a config property that holds a secret, such as a password, an API key, or an auth header, as `Masked`, from `boot-config-common`, rather than `String`.
Their config classes don't depend on a config library, so they can't use the library's own type, such as Hoplite's `Secret`.
`Masked` has a masked `toString`, so a config class can be logged or printed safely, and `boot-config-hoplite` masks it in its config report.

Bootable doesn't aim to make config libraries interchangeable.
In your own config classes, declare secrets with your config library's type, such as Hoplite's `Secret`.

==== Hoplite

See https://github.com/sksamuel/hoplite[hoplite].

Add this module to your project to use Hoplite for configuration.
A config value can take an environment variable with HOCON's own `${?VAR}`, or with Hoplite's `${{ env:VAR }}` resolver, which works only in a field that holds a single string; see its documentation's substitutions section.

xref:./boot-config-hoplite/README.adoc[Documentation]

=== Database (JDBC)

`boot-db-jdbc` provides a database connection pool tied to the application lifecycle.
`JdbcDataSourceService` validates a connection when the app starts, so an unreachable database fails the boot, and closes the pool on shutdown.
It is in the `Infrastructure` phase, so services that use the database start after it and stop before it.

An application makes two choices, each its own dependency:

* A *driver*, which supplies the `JdbcConfig`: a driver module's typed config, or the generic `JdbcGenericConfig` (any database by JDBC URL, with the driver added separately).
** `boot-db-jdbc-sqlite`: `SqliteConfig` takes a file `path`, and defaults to WAL journaling, enforced foreign keys, a busy timeout, and a single-connection pool.
** `boot-db-jdbc-postgresql`: `PostgresqlConfig` takes a `host`, `port`, `database`, and credentials, plus typed driver settings such as `sslMode`, `currentSchema`, and `applicationName`.
** `boot-db-jdbc-mysql`: `MysqlConfig` takes a `host`, `port`, `database`, and credentials, plus typed driver settings such as `sslMode`, and defaults to Connector/J's prepared statement cache.
* A *pool*, which supplies the `ConnectionPoolFactory`, configured with its own typed settings.
** `boot-db-pool-hikari`: HikariCP, configured by `HikariPoolConfig`. For HikariCP settings it doesn't cover, add a `HikariConfigCustomizer` to its set binding (Kodein `inBindSet`, Metro `@IntoSet`).
`boot-db-pool-hikari-otel` adds one that records the pool's metrics through OpenTelemetry; see <<Telemetry>>.

On top of the pool, two optional modules use its `DataSource`:

* `boot-db-flyway`: `FlywayMigrationService` runs Flyway's `migrate` when the app starts, just after the pool, so a failed migration fails the boot and nothing uses an unmigrated schema.
Migrations come from `classpath:db/migration` unless `FlywayConfig.locations` says otherwise.
For Flyway settings `FlywayConfig` doesn't cover, add a `FlywayConfigurationCustomizer` to its set binding.
flyway-core supports SQLite itself; the PostgreSQL and MySQL driver modules bring their Flyway database modules.
* `boot-db-exposed`: `ExposedDatabaseService` owns an Exposed `Database` over the pool, configured by `ExposedConfig` (default isolation level, read-only, retries, query timeout, and so on), which applies to that `Database` only. On shutdown, before the pool closes, it unregisters the `Database` from Exposed's process-wide registry.
`db.withTransaction { … }` runs a suspending transaction on the `Database`'s dispatcher (`Dispatchers.IO` by default); called inside another, it joins it, so several calls make one unit of work.
`SchemaVerificationService` checks, after the migrations, that the schema matches the Exposed tables registered in its `Set<Table>` binding, and fails the boot listing the SQL the schema needs (or only warns, with `schemaVerification = WARN`).
For Exposed settings `ExposedConfig` doesn't cover, add an `ExposedConfigCustomizer` to its set binding.
Exposed logs SQL statements at DEBUG on its `Exposed` logger.

Each module reads its own subsection of `db`:

[source,hocon]
----
db {
  jdbc {
    path = "./app.db"
  }
  pool {
    connectionTimeout = 5s
  }
  flyway {
    locations = ["classpath:db/migration"]
  }
  exposed {
    defaultMaxAttempts = 1
    schemaVerification = FAIL
  }
}
----

With vanilla wiring, construct `JdbcDataSourceService(binder.config<SqliteConfig>("db.jdbc"), HikariConnectionPoolFactory(binder.config("db.pool")))`, pass it to `boot` as an app service, and hand its `dataSource` to whatever needs connections: e.g. `FlywayMigrationService(dataSource, binder.config("db.flyway"))`, and an `ExposedDatabaseService(dataSource, exposedConfig)`, as a service too, whose `database` goes to a `SchemaVerificationService` for its tables and to your repositories.
With Kodein, import `jdbcDataSourceModule`, a driver config module (`sqliteConfigModule`, `postgresqlConfigModule`, `mysqlConfigModule`, or `jdbcGenericConfigModule`), and a pool module (`hikariPoolModule`), plus `flywayMigrationModule` and `exposedDatabaseModule` as needed; register tables with `inBindSet<Table> { add { singleton { MyTable } } }`.
With Metro, the `-metro` driver, pool, Flyway, and Exposed modules contribute everything; for the generic config, add `JdbcGenericConfigBindings` to your graph's `bindingContainers`; register tables with `@Provides @IntoSet fun myTable(): Table = MyTable`.
A graph without a driver or a pool fails to compile with a missing binding.

To wrap the pool's `DataSource`, so that everything using it goes through the wrapper, give `JdbcDataSourceService` a `DataSourceWrapper`, or add one to its set binding (Kodein `inBindSet`, Metro `@IntoSet`).
`boot-db-jdbc-otel` adds one that traces each query through OpenTelemetry; see <<Telemetry>>.

See link:./examples/server-ktor-db[examples/server-ktor-db] for a small Ktor server that keeps entries in a SQLite database, through a HikariCP pool, with its schema created by a Flyway migration and its queries written with Exposed. Its server code is shared, and it is wired three ways: `vanilla`, `kodein`, and `metro`, each a runnable app, e.g. `./gradlew :examples:server-ktor-db:metro:run`.

=== Environment

WARNING: Over-using this abstraction is a code smell.

This module simply exposes a strongly-typed global `environment` variable to the system, which is initialized from configuration by a lifecycle controller before services start. With vanilla wiring, add `environmentInitializer(binder)` to the controllers you pass to `boot`; with Kodein or Metro, this module's optional bindings provide it for you.

This should be *rarely* used, but sometimes it is useful to have a way to identify the environment e.g. dev, test, prod, or other.
Good use cases are tagging metrics with the environment, or extremely complex environment-specific configuration that can't be easily abstracted using one of the <<Configuration>> modules.

Note that this is also useful in a JavaScript environment, where the environment may be bound to a global variable by something like https://github.com/mrsteele/dotenv-webpack[dotenv-webpack].
The environment abstraction may be used to abstract away the underlying details of this binding in a way that can be used in both frontend and backend in the common code source set.

NOTE: We currently do not publish multi-platform versions of these modules, but may do so in the future.

[[Health]]
=== Health (liveness and readiness)

`Health`, in the core `boot` module, is a lifecycle controller that tracks where the application is in its lifecycle, `Starting`, `Running`, `Stopping`, or `Stopped`, and answers liveness and readiness from that, such as for Kubernetes probes, a Cloud Run startup probe, or a load balancer's health check:

* *Liveness* is up until the application has stopped.
It runs no checks: an application whose database is down isn't helped by being restarted, and restarting every instance at once makes an outage worse.
* *Readiness* is up only while the application is running: once every service has started, and until shutdown begins.
Then, it runs the readiness checks too, and is up only if they all pass.

When shutdown begins, readiness goes down, and, if the application was running, `Health` waits for `health.readiness.drainDelay` before any service stops.
Load balancers take a few seconds to stop routing to an instance that is going away: Kubernetes, for one, removes a terminating pod from its endpoints asynchronously, and a server that stops before then refuses the requests still routed to it.
The delay is none by default; a few seconds suits Kubernetes.
It comes before the shutdown timeout starts, so the platform's grace period, such as `terminationGracePeriodSeconds`, must cover both.

[source,hocon]
----
health {
  readiness {
    drainDelay = 5s
  }
}
----

A readiness check is a `HealthCheck`, which returns `HealthStatus.Healthy` or `HealthStatus.Unhealthy(reason)`; one that throws is unhealthy.
A check runs on the thread asking for readiness, so it must bound its own wait.
`boot-db-jdbc` provides `JdbcHealthCheck`, which takes a connection from the pool and checks it is valid.
It is opt-in: readiness that depends on a shared database takes every instance out of rotation at once when the database is down, turning failing requests into refused ones, which is what you want only when the application can do nothing useful without it.

With vanilla wiring, construct `Health` and add it to the lifecycle controllers:

[source,kotlin]
----
val health = Health(setOf(JdbcHealthCheck(database.dataSource)), readinessConfig(binder))
Bootable(services, defaultLifecycleControllers() + health)
----

With Kodein, `bootableModule` binds `Health`, adds it to the lifecycle controllers, and opens a `Set<HealthCheck>`; import `jdbcHealthCheckModule` for the JDBC check.
With Metro, `BootableDefaultBindings` does the same, with a `Set<HealthCheck>` multibinding; name `JdbcHealthCheckBindings` in your graph's `bindingContainers` for the JDBC check.

`boot-server-http-ktor` serves them with `KtorHealth`: liveness at `/health/live` and readiness at `/health/ready`, each `200` when up and `503` when down, with a short plain-text body, such as `UP`, `state: Running`, and `jdbc: UP`.
Install it in your server's module with `installHealth(health)`, or add the routes anywhere with `healthRoutes(health)`.
`health.ktor` configures it:

[source,hocon]
----
health {
  ktor {
    livePath = /health/live
    readyPath = /health/ready
    # serve them on a listener of their own, rather than on the application's server
    hostPort = ":9091"
  }
}
----

On a listener of their own, add `KtorHealth.listener(engine)` to the application's services: it starts first and stops last, so liveness is answered while the other services start, such as during long migrations, and readiness is down until the application is running.
With Kodein, `ktorHealthModule` (from `boot-server-http-ktor-kodein`) provides `KtorHealth`; with Metro, `boot-server-http-ktor-metro` contributes it.

The Kodein and Metro flavors of `boot-server-http-ktor-otel` keep the probes on the application's server out of the traces, at the paths of `health.ktor`.
With vanilla wiring, add `ktorHealthConfig(binder).excludeHealthFromTraces()` to `OpenTelemetryService`'s customizers.

See link:./examples/server-ktor-db[examples/server-ktor-db], which serves them in all three wiring styles, with the JDBC check.

[[Periodic]]
=== Periodic work and leader election

Many applications run a loop in the background: every few seconds, send the notifications that are pending, or sweep what has expired.
`boot-periodic` provides that loop, `PeriodicAppService`, so an application writes only its work:

[source,kotlin]
----
PeriodicAppService("notifications", binder.config("notifications.loop"), PeriodicGate.leader(leaderElection)) {
  notifications.sendPending()
}
----

* It runs the work every `interval`, a fixed delay after the previous run ends, so runs never overlap, on a coroutine of its own under a `SupervisorJob`.
* A run that throws is logged, or handed to a `PeriodicFailureHandler`, and the loop carries on.
`maxConsecutiveFailures` guards against a poison pill, such as a record that fails every run: once that many runs in a row have failed, the loop stops, or, with `onFailureLimit = Shutdown`, shuts the application down, so that its platform restarts it.
`runTimeout` cancels a run that hangs.
* Before each run, it asks its `PeriodicGate`, and skips the run when the gate is closed.
`PeriodicGate.leader(leaderElection)` runs it on one instance of the application only, and `PeriodicGate.running(health)` only while the application is running; `and` combines gates.
A gate that closes while a run is in progress, as the leader gate does when this instance stops leading, cancels the run, which isn't counted as a failure.
Cancellation is cooperative: work that blocks, such as a JDBC call, stops at its next suspension point, unless it blocks in `runInterruptible`.
* `enabled = false` turns it off.
* On shutdown it starts no further run, and waits up to `shutdownTimeout` for a run in progress to finish before cancelling it.
* It is in the `Serving` phase, so it starts after what its work uses, and stops before it.
* `PeriodicRunInterceptor`s run around each run.
`boot-periodic-otel`'s `periodicTracing` makes each run a trace of its own, with a root span named for the service, such as `periodic notifications`, so the run's queries and log events belong to it.
* It notes, by the application's `kotlin.time.Clock`, when each run started, and when one last succeeded and failed.

Each loop has a config section of the application's choosing, decoded as a `PeriodicConfig`; every setting has a default:

[source,hocon]
----
notifications {
  loop {
    interval = 5s
    maxConsecutiveFailures = 10
  }
}
----

`PeriodicServices` holds what the application's loops share, their default gate, clock, interceptors, and failure handler, so each loop needs only its name, config, and work: `periodic.create("notifications", config) { … }`.
With Kodein, `periodicModule` binds it, gated on the `LeaderElection` binding if there is one, and opens a `Set<PeriodicRunInterceptor>`; import `periodicTracingModule()` from `boot-periodic-otel-kodein` to trace the runs.
With Metro, `boot-periodic-metro` contributes it, gated on the graph's `LeaderElection` if it has one, and `boot-periodic-otel-metro` contributes the tracing.

==== Leader election

`boot-leader` defines `LeaderElection`: whether this instance is the leader of the application's instances, as a `StateFlow<Boolean>`, with `isLeader()` and `awaitLeadership()`.
`AlwaysLeader` is the leader of an application that runs as one instance.

`boot-leader-k8s` provides `KubernetesLeaderElection`, which elects a leader among an application's pods with a `coordination.k8s.io/v1` Lease, as Kubernetes's own controllers do, following client-go's algorithm.
It is an app service in the `Infrastructure` phase, so it leads, if it can, before the loops that ask it start.
The leader renews the Lease every `retryPeriod`, and gives up leadership when it can't renew it within `renewDeadline`; another pod takes the Lease once it hasn't been renewed for `leaseDuration`.
On shutdown the leader releases the Lease, so another pod takes over at once.
Its first attempt is part of its start, which fails if the API server refuses access, such as for a missing permission; it retries every other failure.

It is configured from `leader.kubernetes`, where only the Lease's name is required:

[source,hocon]
----
leader {
  kubernetes {
    leaseName = notifications-leader
    # the pod's own namespace, from its service account, unless set
    # namespace = apps
    # the pod's name, from HOSTNAME, unless set
    # identity = ${POD_NAME}
    # leaseDuration = 15s
    # renewDeadline = 10s
    # retryPeriod = 2s
    # outside Kubernetes, such as when running locally, skip the election, and lead
    # assumeLeader = true
  }
}
----

The pod's service account needs a Role that allows `get`, `create`, and `update` on `leases` in the `coordination.k8s.io` API group:

[source,yaml]
----
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: leader-election
rules:
  - apiGroups: [coordination.k8s.io]
    resources: [leases]
    verbs: [get, create, update]
----

It talks to the API server's REST API through one of the application's own Ktor clients, from `boot-client-http-ktor` (see <<ClientHttp>>), rather than through a Kubernetes client library: leader election needs only three calls on one Lease.
So the API server's TLS, timeouts, retries, and tracing are configured, and debugged, as every other HTTP call the application makes is, and the engine is the application's choice.
It uses the client named by `leader.kubernetes.httpClient`, `kubernetes` by default, or the default client if there is none of that name.
In a cluster, that client trusts the API server with no TLS config of the application's: the module defaults its trust store to the service account's CA certificate, `ca.crt`, through `boot-client-http-ktor`'s `KtorClientDefaults`, so `leaseName` is the only setting the election needs.
The application's own config of the client, in `http.client.named.kubernetes`, applies over that default, and its `tls`, if it sets one, replaces it, e.g. to trust another CA:

[source,hocon]
----
http {
  client {
    named {
      kubernetes {
        requestTimeout = 5s
        tls {
          trustStore { path = "/etc/k8s/ca.crt", type = PEM }
        }
      }
    }
  }
}
----

With vanilla wiring, give `kubernetesClientDefaults(config)` to `KtorClientService`'s `defaults`; the Kodein and Metro flavors contribute it.

Each request authenticates with the pod's service account token, read from its file for each request, since Kubernetes rotates it.
The API server's address comes from `KUBERNETES_SERVICE_HOST` and `KUBERNETES_SERVICE_PORT`, which Kubernetes gives every pod, unless `leader.kubernetes.apiServer` is set.
The Lease is JSON with kotlinx-serialization, whose serializers are generated, so a native image needs nothing for it.
The election starts after the HTTP clients, in the same phase, so it stops, releasing its Lease, before they close.

With Kodein, import `kubernetesLeaderElectionModule`, which binds it as the `LeaderElection`, alongside `ktorClientModule`; with Metro, `boot-leader-k8s-metro` contributes it, and `boot-client-http-ktor-metro` the clients.

Two pods never lead at once, because a leader steps down before another pod can take over:

* The leader steps down `renewDeadline` after it sent its last successful renewal, even if a request is still in flight then.
* Another pod takes the Lease only `leaseDuration` after it saw that renewal, which was after it was sent.
* Both are timed by each pod's monotonic clock, so the pods' clocks need not agree, and a clock that jumps elects no second leader; the Lease's own times are only informational.

The leader's work must stop within the margin between the two, 5 seconds by default, once `leadership` turns false; the leader gate cancels a run in progress then, as above.
The guarantee holds as long as the leader doesn't pause, such as for a long garbage collection or a suspended VM, for longer than that margin, since a paused pod can't step down: it would then carry on as though it still led.
Work that db-scheduler runs needs no leader at all: it runs each execution on one instance by locking its row; see <<Scheduler>>.

See link:./examples/server-ktor-db[examples/server-ktor-db], whose loop logs the entry count, on the leader only, in all three wiring styles.

[[Scheduler]]
=== Scheduled tasks (db-scheduler)

`boot-scheduler-db` runs https://github.com/kagkarlsson/db-scheduler[db-scheduler] over the application's database: persistent tasks, recurring and one-time, kept in a table, so they survive restarts, and run once across all the application's instances.
Each execution runs on whichever instance locks its row first, so, unlike an in-process loop, a task needs no leader election.
Use it for work that must happen once, at a time, such as a reminder an hour from now, or a nightly report; use `boot-periodic` for work that polls, such as sending what is pending.

`DbSchedulerService` builds db-scheduler's `Scheduler` over `boot-db-jdbc`'s `DataSource`, with the application's tasks, and starts and stops it with the application:

[source,kotlin]
----
val reminder = Tasks.oneTime("reminder", Reminder::class.java).execute { instance, _ -> send(instance.data) }
val purge = Tasks.recurring("purge", fixedDelay(1.hours)).execute { _, _ -> purgeExpired() }
val scheduler = DbSchedulerService(database.dataSource, binder.config("db.scheduler"), listOf(reminder, purge))
…
scheduler.scheduler.schedule(reminder.instance(id, Reminder(user, text)), clock.now() + 1.hours)
----

* Its tasks are db-scheduler's own, from `Tasks`: a recurring task is scheduled when the scheduler starts, and a one-time task runs the executions the application schedules through the `Scheduler`, a `SchedulerClient`.
* It is in the `Serving` phase, after `DbMilestones.SchemaMigrated`, so it starts once its table is migrated and the services its tasks use have started, and stops before them.
Shutdown waits up to `shutdownMaxWait` for executing tasks: db-scheduler's default is 30 minutes, so set it within your platform's grace period.
* Task data is stored as JSON with kotlinx-serialization, by `KotlinxSerializationTaskDataSerializer`, rather than db-scheduler's default Java serialization.
A task's data class must be `@Serializable`; a sealed type's subclasses carry its discriminator, and must have a `@SerialName`.
* `SerializableSchedule` (`Cron`, `FixedDelay`, `DailyAt`) is a schedule stored with the task's data, for a recurring task whose schedule is chosen at runtime, with `Tasks.recurringWithPersistentSchedule`: implement `PersistentScheduleData` in the task's data class.
* `scheduledTo`, `schedule`, `scheduleIfNotExists`, `reschedule`, `fixedDelay`, and `exponentialBackoff` take Kotlin's `Instant` and `Duration`.
* The SQL dialect matches the database: from its JDBC URL when the service has it, as the DI flavors do, or else detected from the database when the scheduler starts.
`dialect` sets it explicitly.
* Creating it opens no connection, as with the rest of Bootable's database modules.
* `DbSchedulerHealthCheck`, opt-in, is healthy while the scheduler runs.

It is configured from `db.scheduler`; every setting is optional, and an unset one keeps db-scheduler's default:

[source,hocon]
----
db {
  scheduler {
    threads = 5
    pollingInterval = 5s
    # fetch and lock due executions in one statement, on PostgreSQL, MySQL 8, and the other databases that support it
    pollingStrategy = LockAndFetch
    shutdownMaxWait = 20s
    immediateExecution = true
  }
}
----

For anything else, such as a `SchedulerListener`, an `ExecutionInterceptor`, or another serializer, add a `DbSchedulerCustomizer`, which adjusts db-scheduler's `SchedulerBuilder` after the typed settings.

With DI, the application's tasks come from `DbSchedulerTaskProvider`s, rather than from a set of db-scheduler's own `Task<*>`.
A provider is usually the class whose work its tasks do: it provides them all, and exposes each typed, such as the `OneTimeTask<T>` that code schedules instances of, so a task needs no second binding.
A set of `Task<*>` would also miss, without a word, a task contributed as its own type, such as a `RecurringTask<Void>`.

[source,kotlin]
----
class Reminders(private val mailer: Mailer) : DbSchedulerTaskProvider {
  val send: OneTimeTask<Reminder> = Tasks.oneTime("send-reminder", Reminder::class.java).execute { i, _ -> mailer.send(i.data) }
  val sweep: RecurringTask<Void> = Tasks.recurring("sweep-reminders", fixedDelay(1.hours)).execute { _, _ -> mailer.sweep() }
  override fun tasks() = listOf(send, sweep)
}
----

With Kodein, import `dbSchedulerModule`, which binds the `Scheduler` and `SchedulerClient`, and opens a `Set<DbSchedulerTaskProvider>` and a `Set<DbSchedulerCustomizer>`; import `dbSchedulerHealthCheckModule` for the readiness check.
With Metro, `boot-scheduler-db-metro` contributes them; contribute tasks with `@Provides @IntoSet fun reminderTasks(reminders: Reminders): DbSchedulerTaskProvider`, and name `DbSchedulerHealthCheckBindings` in your graph's `bindingContainers` for the readiness check.
Without DI, pass the tasks to `DbSchedulerService` directly.

==== Its table

The module ships db-scheduler's table as a Flyway migration for PostgreSQL, MySQL 8 (and MariaDB), and SQLite: add its location to `db.flyway.locations`, alongside your own, which then needs naming too:

[source,hocon]
----
db {
  flyway {
    locations = ["classpath:db/migration", "classpath:bootable/db-scheduler/postgresql"]
  }
}
----

The locations are `classpath:bootable/db-scheduler/postgresql`, `…/mysql`, and `…/sqlite`.
Each is a repeatable migration, `R__bootable_db_scheduler.sql`, whose statements are all idempotent (`CREATE TABLE IF NOT EXISTS`), rather than a versioned one, whose version could clash with the application's own, or be out of order in a database that already has later ones.
It creates the table as `scheduled_tasks`, db-scheduler's default: with another `tableName`, create it with a migration of your own.
For another database, take db-scheduler's own DDL from its repository.

See link:./examples/server-ktor-db[examples/server-ktor-db], whose recurring task logs an entry digest, in all three wiring styles.

[[Telemetry]]
=== Telemetry (OpenTelemetry)

`boot-telemetry-otel` provides the application's https://opentelemetry.io/[OpenTelemetry] SDK, for traces and metrics, tied to the application lifecycle.
`OpenTelemetryService` internally manages the OpenTelemetry SDK, so its `openTelemetry` property can be handed to instrumentation right away, and shuts it down when the application stops, after exporting the spans and metrics still buffered, so the last interval isn't lost.
It is in the `Telemetry` phase, so every other service, the database pool included, starts after it and stops before it.

* The resource names the application: `serviceName`, `serviceVersion`, and `environment` (as `deployment.environment.name`), plus any other `resourceAttributes`.
`environment` defaults to `env.environment`, the key `boot-env` reads, so an application using `boot-env` gets it without depending on it here.
Each instance is told apart by its `service.instance.id`: `serviceInstanceId`, where the platform has a stable name for it, such as a pod's, which the Kubernetes downward API can set as `TELEMETRY_SDK_SERVICEINSTANCEID`, and otherwise a random one at each start.
* Traces and metrics are pushed over OTLP (HTTP and protobuf) to `otlp.endpoint`, such as an OpenTelemetry collector, Jaeger, or Google Cloud; see <<TelemetryPushPull>>.
Without an endpoint there is no OTLP export, so a local run sends nothing anywhere.
Each signal can be turned off, or kept off OTLP, and `traces.sampleRatio` samples traces, keeping a caller's sampling decision.
* It records the JVM's runtime metrics (memory, garbage collection, threads, classes, CPU) unless `metrics.runtime` is off.
* Log events within a span carry its `trace_id` and `span_id` in their context data, which `boot-logging-log4j2`'s layouts print: the plain layouts with the rest of the context, the JSON layout as labels, and the GCloud layout as the fields Cloud Logging links to the trace.
* Four of the standard `OTEL_*` environment variables fill in what the config leaves unset; see <<TelemetryOtelEnvironment>>.
* When the OpenTelemetry Java agent is attached, the service uses the agent's SDK instead of building its own, and leaves its lifecycle to the agent.

Logs aren't exported over OpenTelemetry for now: the SDK that `OpenTelemetryService` builds has no logger provider.
Logs go through `boot-logging-log4j2` as usual, with the trace and span ids above, so a backend can link them to their traces.
Ship them with the platform's log collection, such as Cloud Logging's, or an OpenTelemetry collector that reads the application's output.

`Tracer.withSpan(name) { span -> … }` runs a suspending block in a child span of the current one, which stays current across dispatchers, and records an exception as the span's error.
A span from `withSpan` is expected to have a parent: without one, it starts a trace of its own and logs a warning, once for each span name, since its caller's trace context usually didn't reach it, such as across a new `CoroutineScope` or a Java callback.
To start a trace on purpose, such as for a scheduled job or a consumed message, use `Tracer.withRootSpan(name) { span -> … }`, which can also link the trace to the operation that kicked it off.
`withRootSpan(name, sample = Sample.Always)` samples that trace whatever `sampleRatio` is, for a trace too rare or valuable to lose, such as a nightly job's; the application's start is always sampled the same way.
`ServiceStartTracing(openTelemetry)` is a lifecycle controller that traces the application's start as one trace, so its total time, and each service's share of it, can be seen: a root span, `start application`, with a child span for each service's start, such as `start FlywayMigrationService`, within which is what the service does as it starts, such as its queries.
The root span begins when `boot` was called, so it covers building the application, such as decoding its config, as well as starting its services, and ends when the application is running; it doesn't cover the JVM's own startup, before `main`.
The stages before the first service starts are spans under it too: `initialize JVM classes for logging and configuration`, `plan start`, and `initialize`.
The first covers setting up logging and the `boot` lambda, including the config and the DI graph: on a cold JVM, most of its time is loading and initializing the classes of the libraries these use, which a JVM AOT cache can cut sharply.
The start's trace is always sampled, whatever `sampleRatio` is, so a slow or failed start is never missing from the traces.
A start that fails records the exception, and an error status, on the service's span and on the root span.
Add it to the lifecycle controllers: `defaultLifecycleControllers() + ServiceStartTracing(openTelemetry)` with vanilla wiring, `serviceStartTracingModule` with Kodein, and `ServiceStartTracingBindings` in the graph's `bindingContainers` with Metro.
The span is current on the thread that calls `start`: a `start` that runs coroutines carries it into them with `runBlocking(Context.current().asContextElement()) { … }`.
The SDK times its spans and measurements, and `ServiceStartTracing` its root span, with a `kotlin.time.Clock`: `Clock.System` unless one is given to `OpenTelemetryService` and `ServiceStartTracing`, or bound, with Kodein or Metro, such as a fixed clock in a test.
For SDK settings the config doesn't cover, such as a span processor, a metric view, or another sampler, add an `OpenTelemetryCustomizer` to its set binding (Kodein `inBindSet`, Metro `@IntoSet`); this is also how the modules below plug in.
`excludeUrlPathsFromTraces(paths)` is one, which keeps requests such as health checks out of the traces.

[cols="3,2,3,6"]
|===
| Module | Signals | Config | What it adds

| `boot-telemetry-otel-prometheus` | Metrics | `PrometheusTelemetryConfig` | Prometheus export: `PrometheusTelemetry` registers a metric reader with the SDK, and renders the scrape, in the OpenMetrics or Prometheus text format, for an HTTP integration to serve.

`KtorTelemetry`, from `boot-server-http-ktor-otel`, installs OpenTelemetry's Ktor instrumentation, which traces every request, continuing the caller's trace when the request carries one, and records the standard HTTP server metrics, such as `http.server.request.duration`.
It also serves a pulled backend's scrape at `/metrics`, and keeps those scrapes out of the traces.
Call `installTelemetry(telemetry)` in your server's `module()`; the request's span is current while its route runs, so `withSpan` in a route starts a child of it.
To keep the scrape off a public server, set `telemetry.ktor.hostPort`: the scrape is then served on a listener of its own, `telemetry.listener(CIO)` (or another engine), which you add to the application's services.
Without `hostPort`, that listener is a service that does nothing, so it can be added either way.

`jdbcTracing`, from `boot-db-jdbc-otel`, wraps the pool's `DataSource` so that each statement is a client span, named for its operation, database, and table, such as `SELECT mydb.entry`.
The span's parent is the span current on the thread that runs the statement: within a request, or a `withSpan`, that is the coroutine's span, across Exposed's `withTransaction` dispatcher too, since a coroutine's children inherit its trace context.
A statement outside any span starts a trace of its own: at startup, such as Flyway's migrations, unless `ServiceStartTracing`, above, traces the start as one trace.
The query text is sanitized, with its literals replaced by `?`, and the parameters aren't recorded; `jdbcTracing(openTelemetry) { setCaptureQueryParameters(true) }` changes the instrumentation's defaults, but mind what that puts in the traces.
With Kodein, `jdbcTracingModule { ... }` takes the same configuration, and with Metro, a `JdbcTelemetryConfigurer { ... }` binding in the graph.
For example, `setDataSourceInstrumenterEnabled(true)` adds a span for each connection taken from the pool, which shows, in the start's trace, how long the pool takes to start and open its first connection.
The query text is in `db.statement`, of the semantic conventions' older database attributes, unless `OTEL_SEMCONV_STABILITY_OPT_IN=database` opts the JVM into the stable ones, such as `db.query.text`.
The `DataSource` the pool's consumers get is the instrumentation's wrapper, so reach the pool's own, such as a `HikariDataSource`, with `dataSource.unwrap(HikariDataSource::class.java)` rather than a cast.

For a library without a Bootable module that instruments it, such as `boot-server-http-ktor-otel` does Ktor, hand the application's `openTelemetry` to the library's OpenTelemetry instrumentation yourself, where you build its client.
HikariCP's pool has such a module, `boot-db-pool-hikari-otel`, in the table above, which link:./examples/server-ktor-db[examples/server-ktor-db] uses, wired each of the three ways.

Each module reads its own subsection of `telemetry`:

[source,hocon]
----
telemetry {

    serviceName = my-service
    otlp { endpoint = "http://otel-collector:4318" }
    traces { sampleRatio = 0.1 }
    metrics { interval = 30s }
  }
  prometheus {
    resourceAttributesAsLabels = [service.name]
  }
  gcp {
    projectId = my-project
  }
  signoz {
    ingestionKey = ${?SIGNOZ_INGESTION_KEY}
  }
  ktor {
    hostPort = ":9090"
  }
  httpClient {
    capturedResponseHeaders = [X-Request-Id]
  }
}
----

With vanilla wiring, build the customizers, then an `OpenTelemetryService(telemetryConfig(binder), listOf(prometheus, ktorConfig.excludeScrapeFromTraces()))`, pass it to `boot` as an app service, and hand its `openTelemetry` to whatever records telemetry: e.g. `KtorTelemetry(telemetry.openTelemetry, setOf(prometheus), ktorConfig)`.
With Kodein, import `openTelemetryModule`, then `prometheusTelemetryModule`, `gcpTelemetryModule`, `sigNozTelemetryModule`, `micrometerBridgeModule`, `ktorTelemetryModule`, and `httpClientTelemetryModule` (after `ktorClientModule`) as needed, and bind `OpenTelemetry` and `KtorTelemetry` where needed.
With Metro, the `-metro` modules contribute everything.

link:./examples/server-ktor-db[examples/server-ktor-db] traces its requests, with a span for each database operation within them, records its request, pool, and runtime metrics and a counter of its own, and serves them at http://localhost:8001/metrics, wired each of the three ways.
Its metrics are pulled, so they need nothing else running, but its traces are pushed: to see them, point `OTEL_EXPORTER_OTLP_ENDPOINT` at an OpenTelemetry collector or Jaeger (see <<TelemetryPushPull>>).
Its link:./examples/server-ktor-db/README.adoc[README] shows how to see both locally, with Grafana or Jaeger in a container.

[[TelemetryPushPull]]
==== Push and pull

Telemetry reaches a backend in one of two ways.
With push, the application sends it: the SDK exports spans as they finish, and metrics every `metrics.interval`, over OTLP to `otlp.endpoint`.
With pull, the backend fetches it: a scraper, such as Prometheus or VictoriaMetrics, fetches the application's `/metrics` on its own schedule, and the application only keeps each metric's current value.

Push over OTLP is OpenTelemetry's own model, and the only supported approach for traces.
Metrics can go either way: pushed over OTLP, pulled in the Prometheus format with `boot-telemetry-otel-prometheus`, or both at once.

Each has its strengths.
Pull keeps the application ignorant of where its metrics go, needs no credentials in it, and tells the backend when a target is down, because the scrape fails.
Push works where nothing can reach the application to scrape it: short-lived jobs, instances behind NAT, and platforms such as Cloud Run, whose instances have no stable address and stop when idle.

The application usually pushes to an OpenTelemetry collector beside it, such as a sidecar or a node agent, rather than straight to the backend.
The collector batches, retries, samples, and holds the backend's credentials, so the application needs only its address.
A collector can also scrape Prometheus endpoints, so the two models mix.
Some backends take OTLP directly, without a collector: Jaeger, for one, Google Cloud, with `boot-telemetry-otel-gcp`, and SigNoz, with `boot-telemetry-otel-signoz`.

Recommendations that work for most cases:

* With a pulling backend, such as Prometheus, already in place, let it pull the metrics, and push the traces over OTLP.
* With a collector, or a hosted backend, push both over OTLP, and leave Prometheus out.
* Locally, nothing needs to be running: without an endpoint nothing is pushed, and the metrics can still be pulled.

[[TelemetryOtelEnvironment]]
==== The standard environment variables

OpenTelemetry defines environment variables that platforms and tools set, such as the OpenTelemetry operator for Kubernetes, and that other OpenTelemetry SDKs read.
Settings are configured explicitly in `telemetry.sdk`, which `telemetryConfig` decodes, and Bootable falls back to four of the standard variables for the settings not explicitly configured:

[cols="2,2,3"]
|===
| Variable | Explicit configuration | When both are set

| `OTEL_SERVICE_NAME` | `serviceName` | The explicit `serviceName` wins. `OTEL_SERVICE_NAME` wins over a `service.name` in `resourceAttributes`, as it does in other SDKs.
| `OTEL_RESOURCE_ATTRIBUTES` | `resourceAttributes` | Merged by key; the explicit value wins for a key in both.
| `OTEL_EXPORTER_OTLP_ENDPOINT` | `otlp.endpoint` | The explicit `endpoint` wins.
| `OTEL_EXPORTER_OTLP_HEADERS` | `otlp.headers` | Merged by header name; the explicit value wins for a header in both.
|===

A variable that is set but empty, such as `OTEL_EXPORTER_OTLP_ENDPOINT=`, or only whitespace, is treated as unset, as the specification says.
The variables take their standard format, described in OpenTelemetry's https://opentelemetry.io/docs/specs/otel/configuration/sdk-environment-variables/[SDK environment variables] and https://opentelemetry.io/docs/specs/otel/protocol/exporter/[OTLP exporter] specifications.
Explicit configuration comes from any of Hoplite's sources, so a `TELEMETRY_SDK_*` environment variable, such as `TELEMETRY_SDK_SERVICENAME`, is explicit too, and wins over the matching `OTEL_*` one.
The values end up in the `TelemetryConfig` that `telemetryConfig` returns, with the headers `Masked`, but not in Hoplite's config report, which only lists what Hoplite decoded.

If you build a `TelemetryConfig` in code instead of with `telemetryConfig`, such as in a test, the variables are ignored, so it doesn't depend on the environment it runs in.
To apply them to it, call `withOtelEnvironment()` on it.
No other `OTEL_*` variable is read, such as `OTEL_TRACES_SAMPLER` or `OTEL_METRIC_EXPORT_INTERVAL`: set the matching config instead, which a HOCON substitution can take from any environment variable, e.g. `sampleRatio = ${?TRACES_SAMPLE_RATIO}`.

=== Server HTTP (Ktor)

Provides a basic Ktor service abstraction with Bootable lifecycle integration i.e. the server starts and stops with the application.
Does not attempt to configure Ktor in any significant way — this is left to the user.
To trace and measure requests, and serve a metrics scrape, see `boot-server-http-ktor-otel` under <<Telemetry>>.
To serve liveness and readiness probes, see `KtorHealth` under <<Health>>.
See https://github.com/rocketraman/bootable/blob/HEAD/boot-server-http-ktor/src/main/kotlin/com/github/rocketraman/bootable/server/http/ktor/KtorService.kt[KtorService].

The Ktor engine is your choice.
`boot-server-http-ktor` itself depends on no engine; depend on the module for the engine you want, which brings that engine with it, and extend its service class:

[cols="1,1,2"]
|===
| Module | Extend | Engine

| `boot-server-http-ktor-cio` | `CioKtorService` | CIO: pure Kotlin, and the engine to use for a GraalVM native image
| `boot-server-http-ktor-netty` | `NettyKtorService` | Netty
|===

[source,kotlin]
----
class MyServer(config: ServerConfig) : CioKtorService("my-server", config) {
  override fun Application.module() {
    routing { get("/") { call.respondText("hello") } }
  }
}
----

Any other engine, such as Jetty, works too: depend on `boot-server-http-ktor` and that engine, and extend `KtorService` with the engine's factory, e.g. `KtorService<JettyApplicationEngine, JettyApplicationEngineBase.Configuration>("my-server", config, Jetty)`.

Every engine is configured the same way: one connector at the service's `HostPort` (port 8080 if it has none), a 50 ms shutdown grace period, and a 1 s shutdown timeout.
To change those, add connectors, or set the engine's own options, override `configureEngine`, whose receiver is the engine's configuration type:

[source,kotlin]
----
override fun NettyApplicationEngine.Configuration.configureEngine() {
  shutdownTimeout = 5_000
  responseWriteTimeoutSeconds = 30
}
----

NOTE: Before 3.1, `KtorService` always ran on Netty, and `boot-server-http-ktor` brought Netty with it.
To upgrade, depend on `boot-server-http-ktor-netty` instead of `boot-server-http-ktor`, and extend `NettyKtorService` instead of `KtorService`; nothing else changes.

See link:./examples/compose-html[examples/compose-html] for a Kotlin web application end to end: a todo list whose browser client is written with https://github.com/JetBrains/compose-multiplatform#compose-html[Compose HTML], served by a Ktor server run by Bootable.
The API's models and validation rule live in a multiplatform `shared` module, compiled to JavaScript for the `client` and to the JVM for the `server`, so both sides agree on the JSON and on what makes a todo valid.
The server's build bundles the client's production JavaScript onto its classpath, so `./gradlew :examples:compose-html:server:run` serves the whole app at http://localhost:8002.

[[ClientHttp]]
=== Client HTTP (Ktor)

`boot-client-http-ktor` provides the application's Ktor `HttpClient`s, tied to the application lifecycle.
`KtorClientService` builds them when it is constructed, so they can be handed to other components right away, and a bad setting, such as an unreadable key store, fails the boot; it closes them, and their engines, when the application stops.
It is in the `Infrastructure` phase, so services that make calls, in later phases, stop before the clients close, and a call in flight isn't cut off.
Something in the same phase that uses the clients starts after the `HttpClientMilestones.ClientsReady` milestone.

There is a default client, `clients.default`, and any number of named ones, `clients["github"]`, each its own `HttpClient`, with its own connection pool and settings.
`clients.getOrDefault(name)` gives the named client if there is one, and the default otherwise, for e.g. a client per partner, where only some need settings of their own, such as their own client certificate.
They are plain Ktor clients: Bootable applies the typed settings through Ktor's own plugins, and wraps nothing.

[source,hocon]
----
http {
  client {
    default {
      connectTimeout = 5s
      requestTimeout = 30s
      retry { maxRetries = 3 }
    }
    named {
      github {
        baseUrl = "https://api.github.com/"
        headers { Accept = "application/vnd.github+json", Authorization = ${?GITHUB_AUTHORIZATION} }
      }
      partner {
        requestTimeout = 300s
        tls {
          keyStore { base64 = ${?PARTNER_KEYSTORE}, password = ${?PARTNER_KEYSTORE_PASSWORD} }
        }
      }
    }
  }
}
----

* `baseUrl`, through Ktor's `DefaultRequest`, is what relative request URLs resolve against: end it with a `/` to keep its last path segment.
* `connectTimeout`, `requestTimeout`, and `socketTimeout`, through Ktor's `HttpTimeout`; unset, the engine's own defaults apply.
* `headers` are sent with every request that doesn't set its own; they are `Masked`, since they often carry a token.
* `retry`, through Ktor's `HttpRequestRetry`, retries only transient failures: a 5xx, 408, or 429 response, a timeout, or a failed connection.
Any other 4xx is permanent, since the same request would fail the same way, and so is a failed TLS handshake.
Only the idempotent methods are retried, unless `methods` says otherwise, so a request that may have changed something isn't sent twice.
The delay grows exponentially, from `initialDelay` up to `maxDelay`, with some `jitter`, unless a `Retry-After` header says otherwise.
`HttpStatusCode.isTransient()` and `Throwable.isTransient()` give the same classification to code that decides for itself, such as a workflow activity's.
* `tls` holds the material for mutual TLS: the `keyStore` with the client certificate to present, the `keyAlias` of its key, if it holds several, and the `trustStore` of certificates to trust, if not the platform's.
Each store is inline, as `base64`, so it can come from an environment variable or a secret, or a file, at `path`, with its `password` and `type`, `PKCS12` by default.
A trust store can also be `PEM`: one or more certificates, such as a CA bundle, or a platform's mounted `ca.crt`.
The certificate is presented whatever certificate authorities the server asks for, so a self-signed one works too.

A named client takes every setting it leaves unset from the default client, adding to its headers, and taking `retry` and `tls` whole: an empty `tls {}` turns off a client certificate the default client has.

A module that calls a service of its own can contribute its named client's default settings with a `KtorClientDefaults`, in the service's `defaults` or its set binding (Kodein `inBindSet`, Metro `@IntoSet`): e.g. a trust store of the platform's mounted CA certificate, so the application needn't configure one.
The client exists whether or not the application configures it, and the application's `http.client.named.<name>` settings override the contributed ones the same way, field by field, with `tls` taken whole.
Two modules that default the same client fail the boot.

The engine is your choice: `boot-client-http-ktor` itself depends on none.
Depend on the module for the engine you want, which brings that engine with it, and give its `KtorClientEngine` to the service:

[cols="1,1,3"]
|===
| Module | Engine class | Engine

| `boot-client-http-ktor-cio` | `CioClientEngine` | CIO: pure Kotlin, and the engine to use for a GraalVM native image. Its own TLS supports TLS 1.2 but not 1.3 (https://youtrack.jetbrains.com/issue/KTOR-6737[KTOR-6737]). Unless the client sets a `requestTimeout`, CIO's own 15 seconds applies.
| `boot-client-http-ktor-java` | `JavaClientEngine` | The JDK's own `java.net.http.HttpClient`, with the JDK's TLS, including TLS 1.3, and HTTP/2, and no dependencies beyond Ktor's. It works in a native image too.
|===

Each engine class applies the client's TLS material in its engine's terms, and takes a lambda to set the engine's own options, e.g. `JavaClientEngine { protocolVersion = java.net.http.HttpClient.Version.HTTP_1_1 }`.
Between them they cover native images and TLS 1.3, so Bootable has no module for Apache5 or OkHttp.
For those, such as for the finer connection pool control of Apache HttpClient, or any other engine, give the service a `KtorClientEngine` of your own, a few lines that create the engine from its `KtorClientSpec`, applying its `tls.sslContext`.
A `KtorClientEngine` is also the seam for tests: one that returns Ktor's `MockEngine`, `KtorClientEngine { MockEngine { respond("hello") } }`, answers every client's requests, with no other change to the wiring.

For anything else, such as a plugin, add a `KtorClientCustomizer` to the service's customizers, or to its set binding (Kodein `inBindSet`, Metro `@IntoSet`).
It runs for each client after the typed settings, with the client's name, or `default`, and Ktor's own `HttpClientConfig`.
Bootable installs no `ContentNegotiation`, since which serialization library, and which `Json` settings, are the application's choice:

[source,kotlin]
----
KtorClientCustomizer { name, config ->
  config.install(ContentNegotiation) { json(Json { ignoreUnknownKeys = true }) }
  if (name == "github") config.expectSuccess = true
}
----

`boot-client-http-ktor-otel` adds one that traces and measures every request; see <<Telemetry>>.

With vanilla wiring, construct `KtorClientService(binder.config("http.client"), CioClientEngine(), customizer)`, pass it to `boot` as an app service, and hand its clients to whatever makes calls.
With Kodein, import `ktorClientModule`, which binds the `KtorClientService` and the default `HttpClient`, and bind the engine: `bindSingleton<KtorClientEngine> { CioClientEngine() }`.
With Metro, `boot-client-http-ktor-metro` contributes the service and the default `HttpClient`, and the graph provides the engine: `@Provides fun engine(): KtorClientEngine = CioClientEngine()`; a graph without one fails to compile with a missing binding.

link:./examples/server-ktor-db[examples/server-ktor-db]'s `GET /relay/{name}` gets an entry by calling the server back through a named client, so one trace shows the request, the client's call within it, and the server's handling of that call within that.

== How to Use

See xref:./docs/wiring.adoc[Wiring Bootable] for the full guide, and the projects in the `examples` directory — there is one per wiring style, so you can copy the one that matches your choice of DI (or no DI).

The essentials, regardless of wiring:

* Application components that have a lifecycle implement `AppService` or `AdvancedAppService`.
* You assemble a `Set<AppService>` and a `Set<LifecycleController>`, and hand them to the `boot` function, which runs them. With vanilla wiring that is just `boot { Bootable(setOf(MyService(...))) }` — `lifecycleControllers` defaults to `defaultLifecycleControllers()`.
* `defaultLifecycleControllers()` provides the built-in start/stop and signal-handling controllers. To run a custom lifecycle — e.g. starting/stopping services on command from an RPC or web request rather than at boot — pass your own controllers instead.

To use a DI framework, depend on the `-kodein` or `-metro` artifact of each module you use (e.g. `boot-kodein`, `boot-config-hoplite-kodein`, `boot-env-kodein`, or the `-metro` equivalents) and let it assemble the sets:

* *Kodein* (runtime): import the provided `bootableModule` / `hopliteConfigModule` / `environmentModule`, contribute your services with `bindAppService { … }`, and pass the resolved sets to `boot`.
* *Metro* (compile-time): declare a `@DependencyGraph` that extends `BootableGraph`, contribute your services with `@ContributesIntoSet`, and `boot { createGraph<AppGraph>().bootable }`.

== Faster Start: the JVM AOT Cache

On JDK 24 and later, an AOT cache (https://openjdk.org/jeps/483[JEP 483], with the one-step training of https://openjdk.org/jeps/514[JEP 514] in JDK 25) holds the classes an application loaded and linked during a training run, so the next start reads them from the cache instead of loading, verifying and linking them again.
A Bootable application's start loads thousands of classes, from Log4j, Hoplite, the database and telemetry libraries, and Ktor, so it gains a lot from one.
See Spring's https://docs.spring.io/spring-framework/reference/integration/aot-cache.html[guide to the AOT cache] for more on how it works.

=== Producing the cache

The training run starts the application with `-XX:AOTCacheOutput=<file>`, and the JVM writes the cache when the application exits.
The `bootable.aot-cache` plugin in link:./build-logic[build-logic] adds an `aotCache` task to an application, which does that with the installed distribution (`installDist`), by its start script, on the project's Java toolchain:

* it starts the application, and waits for Bootable's `+=> Running+` line, which it logs once every service has started;
* it sends the application the requests given to it, if any, so the cache also covers the request path, not just the start;
* it stops the application with SIGTERM, so it shuts down as it would in production, and the JVM writes the cache as it exits.

[source,kotlin]
----
plugins {
  application
  id("bootable.aot-cache")
}

tasks.aotCache {
  environment.put("SERVER_HOSTPORT", "127.0.0.1:18001")
  request("PUT", "http://127.0.0.1:18001/entries/trained", "by the AOT training run")
  request("GET", "http://127.0.0.1:18001/entries/trained")
  rounds = 20
}
----

Train with the configuration the application runs with in production, as the cache only holds the classes the training loaded.
Telemetry is the usual difference: with an OTLP endpoint, the OpenTelemetry SDK builds its OTLP exporters, and loads about 760 classes that a training run without one leaves out of the cache.
So the examples' training runs set `OTEL_EXPORTER_OTLP_ENDPOINT` to an address nothing listens on: the training exports nothing, and logs a failed export as it stops.
The Jib image below, started with an endpoint, loaded 914 classes from outside a cache trained without one, and 144 from outside one trained with one, as many as it does without an endpoint.

The plugin is one file, `AotCache.kt`, with no dependencies but Gradle's own, so an application outside this repository can copy it into its own `buildSrc` or build logic.
The task type, `AotCacheTraining`, runs any command that starts the application with `-XX:AOTCacheOutput`, such as a container, as the Jib example below does.
The training needs a JVM that writes the cache as it exits, on SIGTERM, so it runs on Linux and macOS, not Windows.

[source,shell]
----
./gradlew :examples:server-ktor-db:vanilla:aotCache
----

writes `examples/server-ktor-db/vanilla/build/aot/vanilla.aot`, and the application's output during the training next to it, in `vanilla.aot.log`.
The cache is about 66 MB for that example, or 60 MB for a training run that only starts it.

=== Running with the cache

Run the application with `-XX:AOTCache=<file>`, on the same JDK, from the same installed directory:

[source,shell]
----
cd examples/server-ktor-db/vanilla
JAVA_OPTS=-XX:AOTCache=build/aot/vanilla.aot build/install/vanilla/bin/vanilla
----

The JVM only uses the cache with the JDK build that wrote it, and the same class path, of the same jars, which it checks by their sizes and modification times.
On any difference, it warns, such as `The AOT cache was created by a different version or build of HotSpot`, or `This file is not the one used while building the AOT cache`, and runs without the cache.
So train with the application as it ships, and ship them together:

* the installed directory can move, but a copy of it has to keep the files' modification times, as `cp -a`, `rsync -a` or a tar archive of it do; a rerun of `installDist` writes new ones, so `aotCache` runs again after it;
* in a container image, train in a container of the image itself, as the Jib example below does.

`-XX:AOTMode=on` makes the JVM fail to start rather than run without the cache, which shows a mismatch at once.
`-Xlog:aot` logs whether the JVM opened the cache, and `-Xlog:class+load` logs each class that came from it with `source: shared objects file`.

=== The gain

On the vanilla link:./examples/server-ktor-db[examples/server-ktor-db] app, on JDK 25, the median of 7 starts:

[cols="2,1,1"]
|===
| | Without the cache | With the cache

| From launch to `+=> Running+`
| 721 ms
| 307 ms

| From `boot` to `+=> Running+`
| 690 ms
| 229 ms

| From `boot` to the services starting
| 485 ms
| 160 ms

| The first `PUT /entries/{name}`
| 44 ms
| 12 ms
|===

The cache held 8,217 of the 8,368 classes the application loaded through its start and those first requests.
A cache from a training run that only starts the application starts it as fast, but leaves the first request at 47 ms: the training's requests are what cover the request path.

=== In a container image, with Jib

link:./examples/server-ktor-db/jib[examples/server-ktor-db/jib] builds the vanilla app into a container image, with https://github.com/GoogleContainerTools/jib[Jib], with its AOT cache in it:

. `jibBuildTar` builds the image without a cache, and the container runtime loads it;
. `aotCache` runs that image once, in a container, with `-XX:AOTCacheOutput` in place of the image's `-XX:AOTCache`, and the cache's directory mounted from the build, so the training runs on the image's own JDK, with its class path, `-cp @/app/jib-classpath-file`;
. `jibDockerBuild`, or `jib` to push to a registry, builds the final image, with the cache as one more layer, at `/app/aot/server-ktor-db.aot`, and `-XX:AOTCache` in its JVM flags.

Jib's images are reproducible, with every file's modification time fixed, so the final image's jars are the same, to the JVM, as those the cache was trained with.
Two settings make the cache usable at all: `containerizingMode = "packaged"`, which puts the application's own classes in a jar, as the JVM won't use a cache with a non-empty directory on the class path, as Jib's default `/app/classes` is; and the training's entrypoint, the image's own but for the cache's flag, as the JVM takes only one of `-XX:AOTCache` and `-XX:AOTCacheOutput`.

[source,shell]
----
./gradlew :examples:server-ktor-db:jib:jibDockerBuild -PcontainerCli=podman
podman run --rm -p 8001:8001 bootable-examples/server-ktor-db-jib
----

`containerCli` is the container runtime's command, for loading and running the training image and for `jibDockerBuild`: `docker` by default, or `podman`.
The cache adds a 68 MB layer to the image, which used 9,406 of the 9,550 classes the application had loaded once it was running, and started from launch to `+=> Running+` in a median of 399 ms with the cache, and 896 ms without it, over 7 starts, each in a new container.
With an OTLP endpoint, it started in 400 ms with the cache, as `boot-telemetry-otel` creates the exporters' HTTP clients on their first export, after the start.

The JVM's choice of garbage collector, and so part of what the cache holds, depends on the container's memory and CPUs: train with the same limits the application runs with.

=== In a CI pipeline, with Dagger

The `server-ktor-db` https://dagger.io[Dagger] module, in `.dagger/modules/server-ktor-db/main.dang`, builds the Jib image above with its cache as a CI pipeline, in containers, with nothing on the host but the `dagger` CLI and a container runtime.
It is written in https://docs.dagger.io/reference/sdks/dang[Dang], Dagger's own language, and needs the Dagger 1.0 beta.
It is one file, with no generated code and no package manager.

Dagger needs a container runtime: Docker, or Podman with its socket enabled.
`mise install` provides the Dagger CLI.
The module needs the 1.0 beta, which the stable CLI downloads and runs when `DAGGER_X_RELEASE` names it; `.mise.toml` sets that variable.
Without mise, install a stable CLI of 0.21.3 or later, and export `DAGGER_X_RELEASE=v1.0.0-beta.28`.
Bootable sends no traces to Dagger Cloud unless you provide your own `DAGGER_CLOUD_TOKEN` or run `dagger login`.

[source,bash]
----
dagger check
dagger api call server-ktor-db image export --path=build/server-ktor-db.tar
podman load -i build/server-ktor-db.tar
----

`dagger check` runs every function marked `@check`, which here is `check`.
The other functions are called by name, as `dagger api call server-ktor-db <function>`.

[cols="1,3"]
|===
|Function |What it does

|`check`
|The pull request check: builds the image, and runs `verify`.
Publishes nothing.

|`jib-image`
|The Jib image, without a cache, as a tarball, from Gradle's `jibBuildTar`, built in `eclipse-temurin:25-jdk`, with Gradle's user home, and its build cache, and Jib's base image cache, in cache volumes.

|`runtime`
|`jib-image`, imported as a container.

|`aot-cache`
|The cache, from a training run of `runtime`: the app started as the image's entrypoint does, but with `-XX:AOTCacheOutput` in place of its `-XX:AOTCache`, then `+=> Running+`, the training requests, and SIGTERM.
`--requests` and `--rounds` change the requests.

|`image`
|`runtime`, with the cache where its entrypoint's `-XX:AOTCache` looks for it, at `/app/aot/server-ktor-db.aot`.
`image export --path=<file>.tar` writes it to disk.

|`verify`
|Starts `image`, and fails unless at least `--min-percent`, by default 90, of the classes it loads come from the cache.
`verify stdout` says how many.

|`dev`
|`image`, on port 8001; `dagger start` runs it, and tunnels the port to `localhost`.

|`lgtm`
|`image`, on port 8002, as `lgtm dev`, exporting its traces and metrics over OTLP to Grafana's `otel-lgtm` stack, as `lgtm stack`, which runs alongside it.
`dagger start server-ktor-db/lgtm` starts both, and tunnels the app's port, Grafana's, 3000, and the collector's, 4318, to `localhost`.

|`env`
|The build container before Gradle has run.
`dagger api call server-ktor-db env terminal` opens a shell in it.
|===

`dagger start` doesn't show the services' own output, such as the app's log: its view shows only the tunnels and the ports' health checks.
`dagger start --progress logs` prints it, under the function that defines each service, such as `ServerKtorDb.dev`.

Jib builds the image, without a container runtime, and the module trains the cache in a container of it, then adds the cache to that same container, so the JDK build, and the jars' sizes and modification times, are the training's by construction.
The image is defined once, in the Jib example's build, for both Gradle and Dagger: its base image, JVM flags, class path, port and environment.
The Jib build pins its base image, the JRE, by digest, so the JDK build only changes when the digest does, and the cache is trained again with it; `dagger.lock` pins the build's JDK image.

Dagger sets `OTEL_*` variables in every container, for its own tracing, and forwards what they collect to Dagger Cloud when the CLI is logged in to it.
The module unsets them before it starts the app, which would otherwise export its own telemetry there, and sets an OTLP endpoint of its own, on the container's localhost, where nothing listens, so the cache has the OTLP exporters' classes, as in the Gradle examples.

Its image used 9,404 of the 9,561 classes it loaded from its cache, and started from launch to `+=> Running+` in a median of 386 ms with the cache, and 900 ms without it, over 7 starts, each in a new container.

=== Which to use

* The `aotCache` task, for an application shipped as its installed distribution, or to try the cache locally: it trains on the build's own JDK toolchain, and needs nothing else.
* Jib, for a container image built by Gradle, without a Dockerfile: the training needs a container runtime, to run the image once.
* Dagger, for a CI pipeline that runs the same way on a laptop and on any CI service, where the build, the training and the image are each a cached, containerized step: it builds the same Jib image, so the host needs only Dagger and a container runtime, not a JDK, and the training runs on the image's own JDK by construction.

== Design

=== Non-Goals

Bootable provides useful capabilities on top of well-chosen libraries, not an abstraction over them.

* *Interchangeable libraries.*
Bootable doesn't aim to make the libraries it builds on, such as Hoplite for configuration, or Exposed and HikariCP for databases, interchangeable with others.
Use their types and APIs directly: Bootable exposes them rather than wrapping them.
That includes dependency injection: Bootable provides bindings for Kodein and Metro, not an abstraction over them, and an application uses its chosen DI directly.
* *Every feature of every library.*
Bootable's modules set up the common case.
For anything more, configure the library itself, through the hooks a module provides, such as `HikariConfigCustomizer`, `ExposedConfigCustomizer`, or ``hopliteConfigBinder``'s parameters.
* *Requiring Bootable's modules.*
Use Bootable's modules, or integrate the library directly, or use a different library if it fits your use case better.
Bootable's core is just application lifecycle management.

This philosophy is quite different from Spring Boot's, which attempts to abstract away libraries with common Spring Boot factories and APIs.
Users then have to understand two abstractions: the library's own, as well as Spring Boot's.
It makes leveraging each library's unique capabilities more difficult than necessary.
These capabilities are either unavailable or only exposed via a complex set of ostensibly library-independent customizers and injectors.
Swapping in your own component is difficult -- other components of Spring Boot assume you are using and configuring their abstraction.

=== Dependency Injection

Everyone has their own preferences: no DI at all, relying solely on constructor injection and context parameters, compile-time annotation-based frameworks like https://zacsweers.github.io/metro/[Metro], https://dagger.dev/[Dagger] or https://github.com/evant/kotlin-inject[kotlin-inject], or runtime DSL based options like https://kosi-libs.org/kodein/[Kodein] and https://insert-koin.io/[Koin].
We don't want to impose a choice on users.
Bootable is designed to be DI independent -- combine it with whichever DI you like, or no DI at all.

That being said, Bootable ships with bindings for two popular options: https://zacsweers.github.io/metro/[Metro] and https://kosi-libs.org/kodein/[Kodein].
Simply pull in the `-metro` or `-kodein` suffixed variants of each module to use them.

==== Which DI Should I Use?

The heavy-weight nature of DI frameworks like Spring has given DI a bit of a bad rap, and many people argue it is unnecessary in Kotlin — that constructor injection and https://kotlinlang.org/docs/context-parameters.html[context parameters] are enough.
This is absolutely true for small projects, but as a project grows the need for modularity arises: consider a multi-module app, each module of which exposes one or more `AppService` implementations without any central code being aware of them all.
Collecting those into a `Set<AppService>` is exactly what a DI container's multibindings do well — but it is also easy to do by hand, and different teams reasonably prefer different approaches.

We recommend most teams use https://zacsweers.github.io/metro/[Metro], which provides a strong feature-set with compile-time graph construction and validation via a set of DI-specific annotations.

NOTE: Unlike Spring, these annotations do not control or configure framework or application behavior.
They simply manage the dependency graph.

With Metro, missing dependencies or other dependency issues are a compile error, not a runtime error.
Also, while startup time differences are usually minimal, applications with large graphs will benefit from compile-time graph construction, which at runtime will have construction performance rivaling vanilla no-DI setups.

If a clean simple DSL is important to you, then consider https://kosi-libs.org/kodein/[Kodein].
Compared to Metro, it has no compile-time graph checking, and is slightly slower to initialize on application startup since it wires the graph at runtime via reflection.
But it is straightforward to use and produces readable DI module definitions.

See these three wiring options for example code:

* link:./examples/wiring-vanilla[examples/wiring-vanilla]
* link:./examples/wiring-kodein[examples/wiring-kodein]
* link:./examples/wiring-metro[examples/wiring-metro]

==== How Do I Integrate Random DI with Bootable?

Bootable's core is plain Kotlin: the `AppService` / `LifecycleController` interfaces, the built-in controllers, and the main framework class https://github.com/rocketraman/bootable/blob/HEAD/boot/src/main/kotlin/com/github/rocketraman/bootable/boot/Bootable.kt[Bootable.kt] carry no DI annotations, and `Bootable` takes its two sets through an ordinary constructor.
The seam is those two sets; how you fill them is up to you.

For convenience, each module that has anything to wire ships optional *Kodein* and *Metro* bindings as separate `-kodein` / `-metro` artifacts (e.g. `boot-metro`), each depending on the plain module, so you can opt into a batteries included DI framework by simply importing the selected dependencies with the suffix for the chosen DI.
