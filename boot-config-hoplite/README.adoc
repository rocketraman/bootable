# Bootable Configuration Module (Hoplite)

## Overview

## Usage

Include the default Hoplite `ConfigBinder` in your graph by naming `HopliteConfigBindings` in your
`@DependencyGraph(bindingContainers = [...])` (or, in magic mode, it is discovered automatically). No code is
required for the default behavior.

Bind config sections by extending `ConfigBinderProvider` from a contributed interface — each binding is just a type
and a key:

```kotlin
@ContributesTo(AppScope::class)
interface MyConfigBindings : ConfigBinderProvider {
  @Provides fun serverConfig(): ServerConfig = config("server")
  @Provides fun helloConfig(): HelloConfig = config("hello")
}
```

To customize config loading, do not include `HopliteConfigBindings`; instead provide your own `ConfigBinder`
built with the `hopliteConfigBinder(...)` factory, which accepts optional parameters for additional stage 1, 2,
or 3 config sources, config reporting, secrets policies, and obfuscators:

```kotlin
@BindingContainer
object MyConfigBinder {
  @Provides @SingleIn(BootScope::class)
  fun configBinder(): ConfigBinder = hopliteConfigBinder(withConfigStage1 = { /* ... */ }, report = false)
}
```

## Environment Variable Mapping Rules

Bootable injects a Hoplite `ParameterMapper` that maps configuration properties to environment variables https://docs.spring.io/spring-boot/docs/current/reference/htmlsingle/#features.external-config.typesafe-configuration-properties.relaxed-binding.environment-variables[in the same way that Spring Boot does], less the support for arrays/lists.

See also https://github.com/sksamuel/hoplite/issues/410[hoplite issue #410].

An environment variable overrides a map entry, or a property of one, keeping the entry's key as config spells it.
For example, with `http.client.named.myClient { baseUrl = "http://localhost:8001/" }` in config, `HTTP_CLIENT_NAMED_MYCLIENT_BASEURL=http://localhost:8002/` changes the `baseUrl` of the `myClient` client, rather than adding a client named `MYCLIENT`.
An entry that only the environment defines is keyed as the environment variable spells it, in upper case.

## Substitutions

A config value can reference an environment variable, a system property, or another config value with Hoplite's https://github.com/sksamuel/hoplite#resolvers[resolvers]:

```hocon
app.name = "orders"
db {
  host = "${{ env:DB_HOST }}"
  port = "${{ env:DB_PORT:-5432 }}"
  user = "${{ sysprop:db.user }}"
  name = "${{ ref:app.name }}"
}
```

A reference that resolves to nothing, without a `:-fallback`, fails the bind.
`${{ env:name }}` reads the environment variables passed to `hopliteConfigBinder(environmentVariables = ...)`, which default to the process environment.
Hoplite modules add resolvers for secret stores, such as Vault, AWS Secrets Manager, GCP Secret Manager, and Azure Key Vault; add them with `addResolver` in a `withConfigStageN` hook.

Resolvers resolve only a data class field whose value is a single string, not the entries of a map, list, or set.
There, and anywhere else, use HOCON's own substitutions, which HOCON resolves when it parses the file, falling back to the environment:

```hocon
db.dataSourceProperties {
  sslmode = ${?DB_SSLMODE}
}
```

Hoplite's deprecated preprocessor syntax, `${VAR}` in a quoted string or `{{key}}`, is not expanded and is left as literal text.

## Custom Types

Hoplite `Decoder` instances may be registered via the Java ServiceLoader framework, or passed to the `hopliteConfigBinder(...)` factory.

## Reporting

By default, Hoplite will report on all config values that are loaded.
This can be disabled by setting the `report = false` parameter of `hopliteConfigBinder(...)`.

A Hoplite `SecretsPolicy` passed to `hopliteConfigBinder(...)` will be used by the config loader.

By default, a value is considered a secret if any of the following are true:

* if a name contains "secret", "credential", or "pass" it is considered a secret
* if a config source provides metadata that indicates the value is a secret
* if the variable type is a Hoplite `Secret`.

Whatever the policy, a value of Bootable's `Masked` type, from `boot-config-common`, is masked: in a data class, a map, or a list.
Bootable's own modules use `Masked`, since their config classes don't depend on Hoplite.
In your own config classes, declare secrets as Hoplite's `Secret` to mark them explicitly, rather than relying on their names.

A Hoplite `Obfuscator` passed to `hopliteConfigBinder(...)` will be used by the config loader.

By default, values are strictly obfuscated.
